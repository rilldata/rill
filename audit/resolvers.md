# Resolvers — Code Review

**Scope:** `runtime/resolvers/*.go` (ai, annotations, api, builtin_metrics, builtin_metrics_sql, builtin_sql, glob, legacy_metrics, metrics, metrics_sql, metricsview_cache_key, metricsview_summary, metricsview_time_range, project_storage, resource_status, sql, text, union, util) plus the shared driver in `runtime/resolver.go` and supporting security/cache code it depends on.  |  **Health:** needs-attention

## Overview
The resolvers package implements a uniform `Resolver` interface (`Close`, `CacheKey`, `Refs`, `Validate`, `ResolveInteractive`, `ResolveExport`, `InferRequiredSecurityRules`) behind a single `runtime.Resolve` driver that layers on caching, security-claim hashing, and singleflight. The code is generally clean, small per-file, and consistent in how it acquires controllers/executors and applies metrics-view access policies (`ResolveSecurity` + `CanAccess`). The biggest risks are not in the individual resolvers' happy paths but at the edges: the shared query-result cache key hashes only `UserAttributes` and omits the rest of the security context (`AdditionalRules`, `SkipChecks`), which can leak more-privileged results across security contexts; the AI resolver unconditionally dereferences optional time-range pointers and panics for any report that omits them; and the `metrics_annotations` resolver is the one metrics-view-backed resolver that never checks `CanAccess()`, bypassing the metrics view's access policy. There is also a large amount of dead export code: `ResolveExport` has no callers anywhere and `ForExport` is never set true. Test coverage is missing for several of the riskiest files (`ai.go`, `annotations.go`, `metrics.go`).

## Findings

### resolvers-01 [HIGH] AI resolver panics when `time_range`/`comparison_time_range` are omitted

**Status (2026-07-25):** ✅ Fixed and merged in [#9703](https://github.com/rilldata/rill/pull/9703).

- **Category:** bug  **Confidence:** high  **Location:** `runtime/resolvers/ai.go:209-212`
- **Problem:** `ResolveInteractive` builds `AnalystAgentArgs` with `r.props.TimeRange.Start`, `r.props.TimeRange.End`, `r.props.ComparisonTimeRange.Start`, and `r.props.ComparisonTimeRange.End`. Both `TimeRange` and `ComparisonTimeRange` are `*metricsview.TimeRange` optional properties left nil by `WeakDecode` when absent. `newAI` never defaults them, and `resolveTimeRange` (called at lines 168/174) explicitly treats a nil pointer as a no-op — so a nil pointer flows straight into the unconditional dereference at 209-212. `TimeRange.Start`/`End` are plain `time.Time` fields (`runtime/metricsview/query.go:206`), so dereferencing a nil `*TimeRange` panics.
- **Failure scenario:** A report configured as `data: { ai: { prompt: "Summarize sales" } }` is parsed verbatim (`parse_partial_data.go:114-119` passes the `ai:` map through untouched) and executed by `report.go:triggerAIReport`, which builds props from the spec and never injects `time_range`/`comparison_time_range` (`report.go:727-744`). Because `comparison_time_range` is opt-in and almost never set, `r.props.ComparisonTimeRange.Start` dereferences nil → panic on essentially every AI report that does not explicitly configure a comparison range. The panic is caught by the controller's reconcile `recover()` (`runtime/controller.go:1319`), so it does not crash the process, but the report perpetually fails.
- **Recommendation:** Default both pointers to `&metricsview.TimeRange{}` in `newAI` (or guard each dereference), so absent time ranges produce zero `time.Time` values rather than a panic.

**Verification:** CONFIRMED — `runtime/resolvers/ai.go:209-212` unconditionally dereferences `r.props.TimeRange.Start/.End` and `r.props.ComparisonTimeRange.Start/.End`; both fields are `*metricsview.TimeRange` (`ai.go:30-31`), `newAI` (`ai.go:52-119`) never defaults them, and `resolveTimeRange` returns immediately on a nil pointer (`ai.go:283`), so a nil pointer reaches the dereference and panics.

**Manual Reproduction Steps (for QA):**
1. In a Rill project with AI enabled, create a report file (e.g. `reports/ai_report.yaml`) whose data section uses the AI resolver with only a prompt, for example: `data: { ai: { agent: analyst_agent, prompt: "Summarize sales", is_report: true } }` — do NOT set `time_range` or `comparison_time_range`.
2. Trigger the report (via its schedule, or the "Run now" / trigger action for the report resource).
3. Expected: the report executes and produces an AI summary. Actual: the report execution fails every time; the report resource shows a reconcile error and the runtime logs contain a recovered panic (nil pointer dereference) originating in `aiResolver.ResolveInteractive`. Setting only `time_range` but not `comparison_time_range` still fails (the second dereference at `ai.go:211` panics).

### resolvers-02 [HIGH] Query-result cache key omits `AdditionalRules`/`SkipChecks`, leaking results across security contexts

**Status (2026-07-25):** ✅ Fixed and merged in [#9704](https://github.com/rilldata/rill/pull/9704).

- **Category:** security  **Confidence:** high  **Location:** `runtime/resolver.go:210-238`
- **Problem:** When building the query cache key, `Resolve` hashes only `opts.Claims.UserAttributes` (lines 210-218) plus the resolver's own `CacheKey` and refs. It never incorporates `Claims.AdditionalRules`, `Claims.SkipChecks`, or `Claims.Permissions`. By contrast the security engine's own `computeCacheKey` (`runtime/security.go:892`) marshals the entire `claims` — its `MarshalJSON` (`security.go:103-121`) includes attributes, permissions, `AdditionalRules`, and `SkipChecks` — precisely because those fields materially change the resolved policy. Row-level filters derived from `AdditionalRules` are applied inside the executor via `ResolvedSecurity` (`security.go:325-326,746,773`; the executor builds its AST with `e.security`), and are *not* encoded in the `metricsview.Query` JSON that the metrics resolver uses as its key. The metrics resolver's `CacheKey` (`metrics.go:106-122`) is only `executor cache key + json.Marshal(query)`, and for a non-streaming Rill-managed metrics view `Executor.CacheKey` returns `("", true)` — a constant, security-independent value (`runtime/metricsview/executor/executor.go:112-124`). So two requests that differ only in `AdditionalRules`/`SkipChecks` produce identical keys. The same flaw exists in `annotations.go:81-97` (same `executor-key + query-JSON` pattern), and result caching is on by default for managed metrics views, making this a default-on exposure. The `metrics_sql` resolver inherits it because it delegates to the metrics resolver.
- **Failure scenario:** Precondition: two requests to the same instance/resolver with the same query and the same `UserAttributes` but different security context. Concretely: two magic-auth-token links to the same embedded dashboard, both with `UserAttributes = {}` (anonymous viewers) but different locked filters carried as `AdditionalRules` (e.g. `region = 'US'` vs `region = 'EU'`; magic tokens use `AdditionalRules` per the `SecurityClaims` doc comment). The first populates the cache under a key reflecting only the empty attributes; the second gets a cache hit and receives the first link's `US` rows. Equivalently, a `skip_nested_security` custom API sets `SkipChecks = true` (`runtime/server/api.go:72-73`) and can cache unfiltered results that a security-enforcing request with identical attributes later reads.
- **Recommendation:** Fold the full security context into the query cache key — hash the entire `Claims` (as `computeCacheKey` already does) or mix the resolved security identity (`AdditionalRules`, `SkipChecks`, resolved row filter) into the key alongside `UserAttributes`.

**Verification:** CONFIRMED — `runtime/resolver.go:210-218` hashes only `opts.Claims.UserAttributes` into the query cache key; `Claims.AdditionalRules`, `SkipChecks`, and `Permissions` are never mixed in. The metrics resolver's `CacheKey` is executor-key + query JSON only (`runtime/resolvers/metrics.go:106-122`), and `Executor.CacheKey` returns a constant `[]byte("")` for non-streaming Rill-managed metrics views (`runtime/metricsview/executor/executor.go:113-125`). The security engine's own `computeCacheKey` (`runtime/security.go:873-874`) marshals the full claims — `SecurityClaims.MarshalJSON` (`security.go:103-121`) includes `AdditionalRules` and `SkipChecks` — confirming those fields materially change the resolved policy. `runtime/server/api.go:73` sets `claims.SkipChecks = true` for `skip_nested_security` APIs. `annotations.go:81-97` uses the identical key pattern.

**Manual Reproduction Steps (for QA):**
1. Deploy a project to Rill Cloud with a metrics view on a Rill-managed table (default caching on) with a dimension such as `region`, and an explore dashboard on it.
2. From the dashboard's Share flow, create two public/magic-auth URLs for the same dashboard: URL A locked to filter `region = 'US'`, URL B locked to filter `region = 'EU'` (both are anonymous, so both carry empty user attributes; the locked filters travel as `AdditionalRules`).
3. Open URL A in an incognito window and note the totals (this populates the query cache).
4. Immediately open URL B in another incognito window and run the exact same view/query.
5. Expected: URL B shows EU-filtered numbers. Actual: URL B shows URL A's US-filtered numbers (cache hit on the identical key). Repeating in the opposite order flips which result "wins".
6. Alternative path: define two custom APIs over the same metrics query, one with `skip_nested_security: true` and one without; call the skipping one first, then the enforcing one with identical user attributes — the second returns the unfiltered cached result.

### resolvers-03 [HIGH] `metrics_annotations` resolver never checks `CanAccess()`, bypassing the metrics view's security policy

**Status (2026-07-25):** ✅ Fixed and merged in [#9705](https://github.com/rilldata/rill/pull/9705).

- **Category:** security  **Confidence:** high  **Location:** `runtime/resolvers/annotations.go:51-64`
- **Problem:** `newAnnotationsResolver` calls `ResolveSecurity` (line 51) but — unlike every other metrics-view-backed resolver (`metrics.go:76-78`, `metricsview_summary.go:73-75`, `metricsview_time_range.go:82-84`, `metricsview_cache_key.go:79-81`) — it never checks `if !security.CanAccess() { return ErrForbidden }`. It passes the resolved security to `executor.New` but `Executor.Annotations`/`executeAnnotationsQuery` (`runtime/metricsview/executor/executor.go:689,887`) neither check `e.security.CanAccess()` nor apply the row filter; they run `SELECT * FROM <annotation table> WHERE time >= ? …` directly. The public `MetricsViewAnnotations` handler (`runtime/server/queries_metrics.go:619-622`) only checks the coarse instance-level `ReadMetrics` permission, not the metrics view's own access policy — that fine-grained gate is exactly what the resolver's `CanAccess()` check is supposed to provide.
- **Failure scenario:** A viewer who holds `ReadMetrics` on the instance but is denied a specific metrics view by its `security_policy` (e.g. `access: "{{ .user.admin }}"`) calls `/queries/metrics-views/{name}/annotations` and receives that metrics view's annotation rows (labels, descriptions, time markers) despite being blocked from the view itself. The regular query path enforces this via the metrics resolver; only annotations leak.
- **Recommendation:** Add the `if !security.CanAccess() { return nil, runtime.ErrForbidden }` guard in `newAnnotationsResolver`, matching the sibling resolvers.

**Verification:** CONFIRMED — `runtime/resolvers/annotations.go:51-73` calls `ResolveSecurity` but has no `CanAccess()` check, while all four sibling resolvers do (`metrics.go:76`, `metricsview_summary.go:73`, `metricsview_time_range.go:82`, `metricsview_cache_key.go:79`). `Executor.Annotations` (`runtime/metricsview/executor/executor.go:689-723`) iterates annotations and runs `executeAnnotationsQuery` with no `e.security.CanAccess()` check (the executor's `CanAccess` checks at lines 274/336/486/563 are in other query paths). The server handler `MetricsViewAnnotations` (`runtime/server/queries_metrics.go:612-620`) only checks the coarse instance-level `claims.Can(runtime.ReadMetrics)`.

**Manual Reproduction Steps (for QA):**
1. In a project, create a metrics view with an `annotations:` section and a security policy that denies the test user, e.g. `security: { access: "{{ .user.admin }}" }`.
2. Deploy and log in as a non-admin user who has viewer (ReadMetrics) access to the project.
3. Control: query the metrics view normally (open its dashboard or POST to `/v1/instances/{id}/queries/metrics-views/{name}/aggregation`). Expected and actual: 403 / access denied.
4. Now POST to `/v1/instances/{id}/queries/metrics-views/{name}/annotations` with a body containing the annotation measures and a time range (or just measures).
5. Expected: 403 like the aggregation query. Actual: HTTP 200 with the metrics view's annotation rows (times, descriptions, labels), despite the user being denied access to the view.

### resolvers-04 [MEDIUM] Built-in `/metrics-sql` API silently ignores its documented `additional_where`
- **Category:** correctness  **Confidence:** high  **Location:** `runtime/resolvers/builtin_metrics_sql.go:40-73`
- **Problem:** The registered OpenAPI schema for `/metrics-sql` advertises an `additional_where` request property (`builtin_metrics_sql.go:28-37`). Request bodies become resolver `Args` (`runtime/server/api.go`), but `builtinMetricsSQLArgs` only decodes `sql` and `priority`; `additional_where` is dropped, and `newBuiltinMetricsSQL` forwards only `{"sql": args.SQL}` as properties to `newMetricsSQL`. Since `metrics_sql` reads `AdditionalWhere` from *properties* (`metrics_sql.go:28`), the filter never takes effect.
- **Failure scenario:** A caller of the built-in metrics-SQL API passes `additional_where` expecting the results to be filtered (e.g. to a tenant/region). The parameter is silently ignored and the full, unfiltered result set is returned, contradicting the documented contract.
- **Recommendation:** Decode `additional_where` from the args and pass it through to `newMetricsSQL`'s properties, or remove it from the OpenAPI schema if unsupported.

**Verification:** CONFIRMED — the OpenAPI request schema advertises `additional_where` (`runtime/resolvers/builtin_metrics_sql.go:28-36`), but `builtinMetricsSQLArgs` decodes only `sql` and `priority` (`builtin_metrics_sql.go:40-43`), and `newBuiltinMetricsSQL` forwards only `{"sql": args.SQL}` as properties (`builtin_metrics_sql.go:61-72`). The `metrics_sql` resolver reads `AdditionalWhere` from properties (`runtime/resolvers/metrics_sql.go:27-28`), so the request field is silently dropped. Note the endpoint requires admin claims unless `SkipChecks` (`builtin_metrics_sql.go:50`).

**Manual Reproduction Steps (for QA):**
1. As an admin user, POST to the built-in API endpoint `/v1/instances/{instance_id}/api/metrics-sql` with body: `{"sql": "SELECT region, total_sales FROM my_metrics_view"}`. Note the returned rows.
2. Repeat with an `additional_where` expression, e.g. `{"sql": "SELECT region, total_sales FROM my_metrics_view", "additional_where": {"cond": {"op": "OPERATOR_EQ", "exprs": [{"name": "region"}, {"val": "US"}]}}}`.
3. Expected: the second response contains only `region = 'US'` rows. Actual: both responses are byte-identical — the filter is silently ignored, with no error or warning.

### resolvers-05 [MEDIUM] SQL resolver cache key omits the connector, colliding across OLAP connectors
- **Category:** bug  **Confidence:** medium  **Location:** `runtime/resolvers/sql.go:147-152`
- **Problem:** `sqlResolver.CacheKey` returns `[]byte(r.sql)` (cacheable for DuckDB/ClickHouse) but does not include the connector name. The composite key in `Resolve` adds the instance ID, resolver name (`"sql"`), and refs, but never the connector. Because `resolveTemplate` always escapes `{{ ref }}` identifiers with DuckDB quoting (`sql.go:281-282`) and the limit-wrapping is identical for both dialects (`sql.go:122-130`, only MySQL differs), the resolved SQL text and the successfully-resolved refs can be identical for two different connectors.
- **Failure scenario:** A project with both a DuckDB and a ClickHouse connector exposes two SQL-backed APIs that run the same simple templated query text (e.g. `SELECT count(*) FROM {{ ref "events" }}`) against each connector. Both produce the same cache key; a cache hit from one connector returns the other connector's data. (Precondition: the query text is valid on both dialects, so the collision is real but narrow.)
- **Recommendation:** Include the connector name (or dialect) in `sqlResolver.CacheKey`.

**Verification:** CONFIRMED — `sqlResolver.CacheKey` (`runtime/resolvers/sql.go:147-152`) returns `[]byte(r.sql)` (cacheable for DuckDB/ClickHouse when refs are non-empty) with no connector identifier; the composite key in `runtime/resolver.go:240` adds only instance ID, the constant resolver name `"sql"`, and the hashed refs/attributes. Ref templating always escapes with DuckDB quoting regardless of connector (`sql.go:282` with its own TODO acknowledging this), and the limit wrapping is identical for DuckDB and ClickHouse (`sql.go:122-130`), so the final SQL text can be byte-identical across connectors. Note the precondition is narrow: same instance, same query text valid on both dialects, refs resolving to same-named resources.

**Manual Reproduction Steps (for QA):**
1. Create a project with both a DuckDB and a ClickHouse connector, each holding a model/table named `events` with different row counts (e.g. DuckDB model `events` and a ClickHouse table `events`).
2. Define two custom API files: `api_duck.yaml` with `sql: SELECT count(*) AS c FROM {{ ref "events" }}` and `connector: duckdb`, and `api_click.yaml` with the identical `sql` and `connector: clickhouse`.
3. Call `/v1/instances/{id}/api/api_duck` and note the count.
4. Immediately call `/v1/instances/{id}/api/api_click`.
5. Expected: each API returns its own connector's count. Actual: the second call returns the first connector's cached count (identical cache key), until the cache entry is invalidated by a resource state change.

### resolvers-06 [LOW] `union` and `api` resolvers mutate the caller's shared `Args` map
- **Category:** correctness  **Confidence:** medium  **Location:** `runtime/resolvers/union.go:51-53`, `runtime/resolvers/api.go:43-63`
- **Problem:** `newUnion` calls `delete(opts.Args, "partitions_model_id")` on the shared args map before initializing a glob entry, and `newAPI` writes static args and a `__internal__apis_visited` slice into `opts.Args`. Both mutate the map the caller passed in — and, for `union`, the same map handed to every sibling sub-resolver. This is not a data race (resolvers initialize sequentially within a single `Resolve` call), but it produces order-dependent behavior and leaks internal keys back to the caller. The sharpest case: a `union` listing two `api` entries passes the same `opts.Args` to both, so the static args and visited-list injected by the first `api` entry (`api.go:46-48,63`) are visible to the second, cross-contaminating sibling proxies.
- **Recommendation:** Clone `opts.Args` (e.g. `maps.Clone`) before mutating it, so each sub-resolver/recursion gets an independent copy.

**Verification:** CONFIRMED — `runtime/resolvers/union.go:52` calls `delete(opts.Args, "partitions_model_id")` on the shared map inside the per-entry loop, and `runtime/resolvers/api.go:47` (`opts.Args[k] = v` for static args) and `api.go:63` (`opts.Args[key] = visited` for `__internal__apis_visited`) write into the caller's map. The same `opts.Args` pointer is passed to every union sub-resolver (`union.go:58`), so a first `api` entry's static args and visited list are visible to subsequent siblings.

**Manual Reproduction Steps (for QA):**
1. Create a base custom API `base.yaml` whose SQL echoes an argument, e.g. `sql: SELECT '{{ .args.who }}' AS who`.
2. Create a proxy API `proxy_one.yaml` using the `api` resolver: `api: base` with static `args: { who: "one" }`.
3. Create a union API `u.yaml` whose `union` resolver lists two entries in order: first `{name: api, properties: {api: proxy_one}}`, then `{name: api, properties: {api: base}}` (the second entry defines no `who` arg).
4. Call `/v1/instances/{id}/api/u` with no query parameters.
5. Expected: the second entry's row has an empty/missing `who`. Actual: the second entry also returns `who = "one"`, because the first proxy's static args leaked into the shared args map. If the `union` resolver is not reachable from your project's API YAML, this is not user-reproducible; confirm in code at `runtime/resolvers/api.go:43-63` and `union.go:51-61` (shared `opts.Args` mutation).

## Product Improvements
- **`/metrics-sql` documents a filter that does nothing** (resolvers-04): users relying on `additional_where` for scoping silently get unfiltered data.
- **Resolver-based export is unavailable** (resolvers-07): custom APIs backed by `metrics`, `metrics_sql`, `union`, `glob`, or `text` cannot be exported/downloaded because the export path is unwired (`ExportReport` rejects everything except `legacy_metrics`, `downloads.go`). A user building a custom API for a scheduled CSV report cannot use the modern resolvers.
- **`metrics_sql` additional-where only targets the primary metrics view** (`metrics_sql.go:122-125`): a metrics-SQL query joining multiple metrics views cannot have per-view filters applied to the non-primary views.
- **`resource_status` only supports a boolean `where_error`** (`resource_status.go:34-38`): operators debugging a project cannot filter by kind (e.g. only models) or by non-error statuses (pending/running) without post-processing.

## New Feature Ideas
- **Cache-key debug/observability.** Return the computed cache key and hit/miss in a response header or debug field for resolver APIs. The singleflight/cache logic in `resolver.go` is opaque today; this would make the cache-poisoning/collision issues (resolvers-02, resolvers-05) diagnosable. Effort: S.
- **Wire up resolver exports.** Implement `ResolveExport` dispatch in `Resolve` for `metrics`/`metrics_sql`/`sql` and set `ForExport` on the download path, enabling CSV/XLSX/Parquet downloads for modern custom APIs. Effort: M.
- **Parallelize `project_storage` size estimation.** `resolveForConnector` runs sequentially per connector (`project_storage.go:104-130`); fan out with a bounded errgroup and per-connector timeouts so one slow connector doesn't stall the billing/storage UI. Effort: S.
- **Configurable AI agent in the `ai` resolver.** The resolver hard-rejects any agent other than `analyst_agent` (`ai.go:70-71`). Allow registering additional agents (e.g. a forecasting or anomaly agent) via the resolver props. Effort: L.
- **Per-view filters in `metrics_sql`.** Extend `AdditionalWhereByMetricsView` application to every metrics view referenced by a multi-view metrics-SQL query, not just the primary one. Effort: M.
- **Richer `resource_status` filtering/pagination.** Add kind/status filters and pagination so it scales to large projects and powers a proper "reconcile health" API. Effort: S.

## Notes & Missing Test Coverage
- **No unit tests** exist for `ai.go`, `annotations.go`, `metrics.go`, `legacy_metrics.go`, `metricsview_cache_key.go`, `metricsview_summary.go`, or `metricsview_time_range.go`. The AI crash (resolvers-01) and the annotations authz gap (resolvers-03) both live in untested files; a table-driven test that omits `time_range`/`comparison_time_range`, and one that resolves an annotations request under a denying security policy, would catch these.
- **Cache-key security (resolvers-02)** deserves a dedicated test: resolve the same metrics query twice with identical `UserAttributes` but different `AdditionalRules`, and assert the results (and cache keys) differ. The same key-omission also affects `metrics_summary`/`metrics_time_range` (whose executor cache key is security-independent) if their underlying queries ever apply the row filter.
- **`union` reads `res.Schema()` after `res.Close()`** (`union.go:128-130`). Verified safe today: `driverResolverResult`/`mapsResolverResult` both return a cached `Schema()` field that survives `Close()`. It remains a fragile ordering that a future streaming result type could break.
- **`glob.transformResult`** shadows the outer `err` inside the `WithConnection` callback (`glob.go:459` `rows, err := ...`) while a deferred cleanup assigns the outer `err`. Verified harmless: line 436 reassigns `err` from `WithConnection`'s return after the defer runs, so the DROP-TABLE error is only logged, not propagated.
