# Metrics View Engine — Code Review
**Scope:** `runtime/metricsview` (ast.go, astexpr.go, astsql.go, query*.go, timestamps.go, max_query_time_range.go), `runtime/metricsview/executor/*` (executor, rewrites, pivot, export, summary, validate, timestamps, rollup), `runtime/metricsview/metricssql/*`  |  **Health:** fair

## Overview
This package compiles a declarative `metricsview.Query` into dialect-specific SQL via an AST that is incrementally rewritten to accommodate measure types (simple / derived / time-comparison), spines, comparisons, rollups, pivots and per-dialect quirks (Druid exactify/groups, ClickHouse computed-time-dim wrapping). The core injection surface is well handled: user-supplied literals are always parameterized (`?` placeholders + args), and dimension/measure references are validated against the metrics view spec and escaped through the dialect before being emitted, so classic SQL injection is not a concern. Overall the code is careful and heavily commented, but it is also very intricate: the multi-pass AST rewrites carry a lot of implicit invariants, and several of the bugs below are places where one rewrite pass is inconsistent with another (offset handling) or where a code path indexes into user-controlled slices without a length guard. The biggest confirmed risks are (1) silent wrong results — unescaped LIKE→regex on Druid — and (2) fragile `percent_of_total` totals handling that both divides unsafely and hard-errors on an empty/NULL total.

## Findings

### metricsview-05 [medium] LIKE→regex conversion does not escape regex metacharacters (Druid ILIKE/search wrong results)
- **Category:** correctness  **Confidence:** high  **Location:** `runtime/metricsview/astexpr.go:787-796` (`convertLikeExpressionToRegexExpression`), used at `:450` for dialects with `SupportsRegexMatch()` (only Druid, `runtime/drivers/druid/dialect.go:26`)
- **Problem:** For Druid, ILIKE/NILIKE is emitted as `REGEXP_LIKE(col, '^(?i)<pattern>$')` where `<pattern>` is the user value with `%`→`.*` and nothing else. Regex metacharacters in the value (`.`, `(`, `)`, `[`, `+`, `?`, `\`, `|`, `^`, `$`) are passed through unescaped, so they take on regex meaning. LIKE `_` (single-char wildcard) is likewise treated as a literal underscore rather than translated to `.`. The value is still parameterized, so this is a correctness bug, not injection. Verified: Druid is the only dialect where `SupportsILike()==false` and `SupportsRegexMatch()==true`; Pinot/BigQuery (`SupportsILike()==false`, `SupportsRegexMatch()==false`) fall through to the `LOWER(...) LIKE` branch and are unaffected.
- **Failure scenario:** On Druid, searching a dimension for `"3.5"` also matches `"3x5"`; searching for `"(EU)"` or `"a+b"` produces an invalid regex and the query errors out. Dashboard search reaches this path too: for Druid, `Search` first tries native search (`executor.go:571-577`) and only falls back to the SQL `ILIKE` path (`whereExprForSearch` wraps the term in `%...%`, `executor.go:995-1024`) when native search is unimplemented — but any ordinary Druid `ILIKE` filter hits the buggy conversion unconditionally.
- **Recommendation:** Escape regex metacharacters in the literal segments before substituting `%`→`.*` (and translate `_`→`.`), e.g. split on `%`/`_`, `regexp.QuoteMeta` each literal chunk, then join with `.*`/`.`.

**Verification:** CONFIRMED — `convertLikeExpressionToRegexExpression` at `runtime/metricsview/astexpr.go:787-796` does only `strings.ReplaceAll(val, "%", ".*")` plus `^(?i)...$` wrapping, with no `regexp.QuoteMeta` and no `_` translation; it is invoked from the `SupportsRegexMatch()` branch at `astexpr.go:431/450`, and Druid is the only dialect returning true (`runtime/drivers/druid/dialect.go:26`; the base dialect returns false at `runtime/drivers/dialect.go:157`, Pinot/BigQuery only override `SupportsILike`). The search fallback path also checks out: `executor.go:574` falls back from native Druid search, and `whereExprForSearch` (`executor.go:995`) builds an `ilike` with `%term%`.

**Manual Reproduction Steps (for QA):**
1. Requires a project backed by a Druid connector (not reproducible on DuckDB/ClickHouse). Create a metrics view over a Druid table with a string dimension containing values such as `3.5`, `3x5`, and `(EU) West`.
2. Open the explore dashboard for that metrics view and, in the dimension's leaderboard, apply a "contains" filter (or use the dimension search box) with the term `3.5`.
3. Expected: only rows whose value contains the literal `3.5`. Actual: rows like `3x5` also match, because `.` acts as a regex wildcard inside `REGEXP_LIKE`.
4. Repeat with the term `(EU)` or `a+b`. Expected: literal substring match. Actual: the query errors out (invalid regex pattern) and the leaderboard shows an error.
5. Alternatively via the query API/MCP `query_metrics_view`: pass `where: {cond: {op: "ilike", exprs: [{name: "<dim>"}, {val: "%(EU)%"}]}}` against the Druid metrics view and observe the error / wrong matches.

### metricsview-06 [medium] `percent_of_total` divides by a raw, precision-truncated total literal (no safe-divide)
- **Category:** correctness  **Confidence:** medium  **Location:** `runtime/metricsview/ast.go:537`
- **Problem:** The percent-of-total expression is built as `fmt.Sprintf("%s/%#f", measureAlias, *total)`. Two issues: (1) unlike `comparison_ratio` (which uses `a.Dialect.SafeDivideExpression`, `ast.go:514`), this uses a bare `/`, so a total of `0` yields a divide-by-zero (NULL / `inf` / `nan` depending on dialect); and (2) `%#f` formats with the default 6 decimal places, so any total with magnitude `< ~5e-7` rounds to `0.000000`, which reintroduces the divide-by-zero and truncates precision on legitimate fractional totals.
- **Failure scenario:** A measure whose grand total is `0` (e.g. a signed measure that nets to zero over the range) or a very small fractional total makes every `percent_of_total` cell return `inf`/`nan`/NULL rather than a meaningful percentage.
- **Recommendation:** Route the division through `SafeDivideExpression` and pass the total as a bound arg (or format with full precision, e.g. `strconv.FormatFloat(v, 'g', -1, 64)`) instead of `%#f`.

**Verification:** CONFIRMED — `runtime/metricsview/ast.go:537` builds the expression as `fmt.Sprintf("%s/%#f", a.Dialect.EscapeAlias(m.Name), *qm.Compute.PercentOfTotal.Total)`: a bare `/` and `%#f` (6 decimal places by default). The contrast holds: `comparison_ratio` at `ast.go:514` routes through `a.Dialect.SafeDivideExpression`.

**Manual Reproduction Steps (for QA):**
1. Create a model with a signed column that nets to zero, e.g. `SELECT now() AS ts, 10 AS amt UNION ALL SELECT now(), -10`, and a metrics view over it with measure `net: SUM(amt)` (set `valid_percent_of_total: true` on the measure).
2. Query it with a percent-of-total computed measure, e.g. via the query API or a custom API using the `metrics` resolver: `measures: [{name: "net"}, {name: "net_pct", compute: {percent_of_total: {measure: "net"}}}]` with any dimension. (In the explore UI, enabling the percent-of-total context column on the measure exercises the same path.)
3. Expected: NULL/blank percentage cells when the grand total is 0. Actual: every `net_pct` cell is `inf`/`nan`/NULL-with-error depending on dialect, because the SQL contains a literal division by `0.000000`.
4. For the precision variant: make the total a tiny fraction (e.g. values `1e-8` and `2e-8`); the total formats as `0.000000` and the same divide-by-zero occurs even though the true total is non-zero.

### metricsview-09 [medium] `percent_of_total` totals query hard-errors when the total is NULL (empty or all-NULL filtered set)
- **Category:** correctness  **Confidence:** medium  **Location:** `runtime/metricsview/executor/executor_rewrite_percent_of_totals.go:82-88`
- **Problem:** The totals sub-query scans its single measure column into `new(float64)` (a non-nullable `*float64`). A global aggregate such as `SUM(col)` returns exactly one row whose value is SQL `NULL` whenever the filtered/time-ranged set is empty (or every measure value is NULL), because simple measures are only wrapped in `COALESCE` when `TreatNullsAs` is set (`ast.go:470-472`). `database/sql`'s `convertAssign` cannot store NULL into a `*float64`, so `res.Scan` returns `converting NULL to float64 is unsupported` and fails the **entire** query, not just the `percent_of_total` measure. Contrast `executor_summary.go:193-197`, which deliberately scans into `new(any)` to tolerate NULLs.
- **Failure scenario:** A dashboard with a `percent_of_total` measure plus a dimension filter or time range that currently matches no rows (or a measure that is NULL over that slice) surfaces a hard query error instead of blank/empty cells.
- **Recommendation:** Scan into a nullable destination (`sql.NullFloat64` or `**float64`) and treat NULL as an absent/zero total; combined with the safe-divide fix in metricsview-06 this yields NULL cells rather than an error.

**Verification:** CONFIRMED — `runtime/metricsview/executor/executor_rewrite_percent_of_totals.go:82-88` fills `vals[i] = new(float64)` and calls `res.Scan(vals...)` with no nullable wrapper; a NULL aggregate therefore fails the scan and the error propagates out of `rewritePercentOfTotals`, aborting the whole query (called from `executor.go:366/508` before AST construction). Simple measures are only COALESCE-wrapped when `TreatNullsAs` is set (`ast.go:470-472`), so `SUM(...)` over an empty set yields NULL.

**Manual Reproduction Steps (for QA):**
1. Use any metrics view (DuckDB is fine) with a simple `SUM` measure that has no `treat_nulls_as` configured.
2. Run a query with a percent-of-total computed measure plus a filter that matches no rows, e.g. via the query API/custom `metrics` API: `dimensions: [{name: "<dim>"}], measures: [{name: "m"}, {name: "m_pct", compute: {percent_of_total: {measure: "m"}}}], where: {cond: {op: "eq", exprs: [{name: "<dim>"}, {val: "value_that_does_not_exist"}]}}`.
3. Expected: an empty result set (zero rows). Actual: the entire query fails with a scan error along the lines of `converting NULL to float64 is unsupported`, because the totals sub-query returns one row with a NULL total.
4. In the explore UI the equivalent is: enable the percent-of-total context column for the measure, then apply a dimension filter (or time range) that matches no data, and observe a dashboard error instead of an empty table.

### metricsview-02 [medium] `writeCast` panics (index out of range) on a `cast` condition with fewer than two operands
- **Category:** bug  **Confidence:** medium  **Location:** `runtime/metricsview/astexpr.go:146-181` (indexes `cond.Expressions[0]` / `[1]`); dispatched from `writeCondition` at `:136`
- **Problem:** Unlike `writeBinaryCondition` (which guards `len(exprs) != 2`, `:226`), `writeCast` unconditionally reads `cond.Expressions[0]` and `cond.Expressions[1]`. `writeCondition` dispatches `OperatorCast` straight to `writeCast` with no operand-count check. The `metrics` resolver decodes user-supplied properties directly into `metricsview.Query` via `mapstructureutil.WeakDecode` (`runtime/resolvers/metrics.go:41-42`), and `Operator` is a bare `string` type whose `Valid()` accepts `"cast"` (`query.go:287,292`). A `where` of `{cond:{op:"cast", exprs:[]}}` (or with one element) therefore reaches `writeCast` and panics instead of returning an error. Note: the metrics-SQL parser only ever emits `cast` with exactly two operands (`filter_parser.go:515-519`), so the reachable path is the raw-`Query` resolver (custom APIs / direct query API), not metrics SQL.
- **Failure scenario:** A custom API / query whose `where` is `{"cond":{"op":"cast","exprs":[{"name":"x"}]}}` panics during SQL generation; at best this is recovered to a 500, at worst an unrecovered panic on the serving goroutine.
- **Recommendation:** Validate `len(cond.Expressions) == 2` at the top of `writeCast` (and ideally centralize an operand-count check in `writeCondition`), returning an error for malformed cast conditions.

**Verification:** CONFIRMED — `writeCast` (`runtime/metricsview/astexpr.go:146-181`) indexes `cond.Expressions[0]` and `cond.Expressions[1]` with no length guard, while `writeBinaryCondition` guards at `astexpr.go:226`; `writeCondition` dispatches `OperatorCast` straight to `writeCast` at `astexpr.go:136-137`. `Operator.Valid()` accepts `"cast"` (`query.go:287,292`), and the `metrics` resolver decodes arbitrary properties into `metricsview.Query` via `mapstructureutil.WeakDecode` (`runtime/resolvers/metrics.go:41-43`). The metrics-SQL parser only emits two-operand casts (`metricssql/filter_parser.go:515-522`), so the reachable path is the raw-`Query` resolver, as stated.

**Manual Reproduction Steps (for QA):**
1. In a Rill project, create a custom API using the metrics resolver, e.g. `apis/bad_cast.yaml` with: `metrics_sql` omitted, instead `type: api`, `metrics: {metrics_view: <mv>, measures: [{name: "m"}], where: {cond: {op: "cast", exprs: [{name: "some_dim"}]}}}` — or call the runtime `query` API / `metrics` resolver directly with those properties as JSON.
2. Invoke the API endpoint (locally: `GET http://localhost:9009/v1/instances/default/api/bad_cast`).
3. Expected: a 400-style validation error such as "cast condition must have exactly 2 expressions". Actual: an index-out-of-range panic during SQL generation, surfaced (at best) as a recovered 500 error with a stack trace in the runtime logs.

### metricsview-04 [medium] Invalid time grain panics when two time-floor dimensions share a base dimension
- **Category:** bug  **Confidence:** medium  **Location:** `runtime/metricsview/ast.go:211` (`tg.ToTimeutil()` in the min-grain pre-scan)
- **Problem:** The min-grain loop in `NewAST` (`ast.go:194-214`) runs before the `ResolveDimension` loop (`:220`) validates the grain. It skips only `TimeGrainUnspecified`, then at `:211` calls `tg.ToTimeutil()` / `minGrain.ToTimeutil()`, both of which `panic` on an unknown grain string (`query.go:344`). A single time-floor dimension is safe (the loop takes the early-continue branch that just assigns `minGrain`, and `ResolveDimension` later rejects the grain cleanly via `Grain.Valid()` at `ast.go:380`), but with two time-floor dimensions on the same base dimension the second one reaches the comparison branch and executes `ToTimeutil()` on the still-unvalidated grain, panicking.
- **Failure scenario:** A pivot-style query that floors the primary time column at two grains where one carries an unrecognized grain (e.g. `"fortnight"`, accepted by mapstructure since `TimeGrain` is a string) panics before validation runs. Flooring one time column at two grains is a legitimate pivot pattern, so this is not purely adversarial.
- **Recommendation:** Check `tg.Valid()` (skip or return an error on invalid) inside the min-grain loop, or move the `ResolveDimension` grain validation ahead of the pre-scan.

**Verification:** CONFIRMED — the min-grain pre-scan (`runtime/metricsview/ast.go:194-214`) skips only `TimeGrainUnspecified` and calls `tg.ToTimeutil()`/`minGrain.ToTimeutil()` at `ast.go:211`; `TimeGrain.ToTimeutil()` panics on unknown grains (`query.go:344` `panic(fmt.Errorf("invalid time grain %q", t))`). Grain validation via `Grain.Valid()` only happens later in `ResolveDimension` (`ast.go:380`), which runs in the second loop starting at `ast.go:220`. With a single time-floor dimension the loop assigns `minGrain` and continues without calling `ToTimeutil()`, so exactly the two-dimension case panics.

**Manual Reproduction Steps (for QA):**
1. Call the query API / a custom `metrics` API with two time-floor dimensions on the metrics view's primary time dimension, one carrying a bogus grain, e.g.: `dimensions: [{name: "t1", compute: {time_floor: {dimension: "<time_dim>", grain: "fortnight"}}}, {name: "t2", compute: {time_floor: {dimension: "<time_dim>", grain: "day"}}}], measures: [{name: "m"}]`.
2. Expected: a clean `invalid "grain"` error (which is what you get if you send only the single bogus-grain dimension). Actual: a Go panic (`invalid time grain "fortnight"`) inside `NewAST` before validation runs, surfaced as a 500/stack trace.
3. Control check: send the same query with only one time-floor dimension using grain `fortnight`; observe the clean error, confirming the discrepancy is specific to the two-dimension pre-scan path.

### metricsview-01 [medium] OFFSET can be dropped when limits are pushed into multi-level sub-queries
- **Category:** correctness  **Confidence:** low  **Location:** `runtime/metricsview/executor/executor_rewrite_limit_pushdown.go:44` (and `:55-72`)
- **Problem:** `rewriteLimitsIntoSubqueriesWalk` pushes the limit using the current node's `n.Limit` (which the previous push updated on that node) but always reads the offset from the global `ast.Root.Offset`. `rewriteLimitInSubquery` copies the offset onto the child and nils the parent's offset. On the first push it moves `Root.Offset` onto the spine child and sets `Root.Offset = nil`. If the walk recurses to a second spine level, it re-reads `ast.Root.Offset` — now `nil` — while clearing the first spine's offset as the new "parent". The limit survives on the innermost node (it is threaded through `n.Limit`), but the offset lands on no node and is silently lost. This is the asymmetry that `rewriteApproxComparisonsWalk` avoids by clearing ancestor offsets only after a single application (`executor_rewrite_approx_comparisons.go:38-41`).
- **Reachability caveat (why low confidence):** The bug only manifests when (a) the query has `OFFSET` + `ORDER BY` + `LIMIT` and no `HAVING`, (b) the first-level spine child itself has a nested spine that passes the push-down guards, producing a ≥2-level push-down, and (c) the offset was not already consumed earlier. When approximate comparisons are enabled they run first (`executor.go:394` before `:396`) and push/clear the offset for comparison queries, so this path is most relevant to non-comparison nested-spine queries. A concrete runtime query shape that produces a ≥2-level spine push-down with a non-nil offset was not confirmed; the code asymmetry is real but its exploitability today is unverified.
- **Recommendation:** Push the offset consistently with the limit — read it from the same node whose limit is being pushed, rather than re-reading `ast.Root.Offset` on every recursion — and add a multi-level spine + offset test.

**Verification:** PLAUSIBLE — the code asymmetry is exactly as described: `runtime/metricsview/executor/executor_rewrite_limit_pushdown.go:44` calls `rewriteLimitInSubquery(n, spineNode, ast.Root.OrderBy, n.Limit, ast.Root.Offset)` — limit threaded via `n.Limit`, offset re-read from `ast.Root.Offset` — and `rewriteLimitInSubquery` (`:55-74`) sets `child.Offset = offset; parent.Offset = nil`. On a second-level push, `ast.Root.Offset` is already nil while `parent.Offset = nil` wipes the offset placed on the first spine, so the offset lands nowhere. The contrast with `rewriteApproxComparisonsWalk` clearing ancestor offsets only after a rewrite (`executor_rewrite_approx_comparisons.go:38-41`) also holds. Kept at PLAUSIBLE because a concrete runtime query shape producing a ≥2-level spine push-down with a live offset was not demonstrated; the dashboard UI does not normally issue OFFSET queries.

**Manual Reproduction Steps (for QA):**
Not user-reproducible with confidence through the dashboard UI (explore does not emit OFFSET with nested spines). Confirm in code: `runtime/metricsview/executor/executor_rewrite_limit_pushdown.go:44` (offset read from `ast.Root.Offset` instead of `n.Offset`) and `:71-72` (child gets offset, parent cleared). A unit test that builds an AST with a two-level `SpineSelect` chain, `Limit`, `Offset`, and `OrderBy`, then runs `rewriteLimitsIntoSubqueries` and asserts some node still carries the offset, would settle reachability.

### metricsview-07 [low] Annotation validation never caches OLAP handles, acquiring one per annotation
- **Category:** performance  **Confidence:** high  **Location:** `runtime/metricsview/executor/executor_validate.go:653-663`
- **Problem:** `validateAndNormalizeAnnotations` builds `olaps := make(map[string]drivers.OLAPStore)` "to reuse connections", but on a cache miss it acquires a handle and appends the release to `olapReleases` without ever writing `olaps[annotation.Connector] = olap`. The map stays empty, so every annotation re-acquires a handle for its connector, and all handles are held (released only at `:698-700`) until the function returns.
- **Failure scenario:** A metrics view with many annotations on the same connector acquires N connector handles concurrently instead of one, amplifying connection-pool pressure during validation.
- **Recommendation:** Store the acquired handle back into the map (`olaps[annotation.Connector] = olap`) on the miss path.

**Verification:** CONFIRMED — in `validateAndNormalizeAnnotations` (`runtime/metricsview/executor/executor_validate.go`), the `olaps` map is created at the "Maintain a map to reuse connections" comment, read once at `:654` (`olap, ok := olaps[annotation.Connector]`), and never written anywhere (`grep 'olaps\['` finds only the read). Every annotation therefore takes the miss path, acquiring a fresh handle per annotation and holding all releases until `:698-700`.

**Manual Reproduction Steps (for QA):**
Not user-reproducible through the UI (no user-visible behavior change; it is connection-pool pressure during metrics-view validation). Confirm in code: `runtime/metricsview/executor/executor_validate.go:653-663` — the `if !ok` branch acquires via `e.rt.OLAP(...)` and appends to `olapReleases` but never assigns `olaps[annotation.Connector] = olap`, so the map stays empty. Optionally observe it live: create a metrics view YAML with several `annotations:` entries pointing at models on the same connector and log/count `runtime.OLAP` acquisitions during reconcile — it is N acquisitions instead of 1.

### metricsview-08 [low] Primary time dimension bypasses field-level access checks
- **Category:** security  **Confidence:** medium  **Location:** `runtime/metricsview/ast.go:620-632`
- **Problem:** `LookupDimension` returns the primary time dimension (and a synthetic spec when it is not explicitly declared) *before* evaluating `Security.CanAccessField` (`:634-637`). As a result a security policy that excludes the time dimension via field-access rules cannot prevent a query from selecting, grouping (via a `time_floor` compute), or filtering by it. This is intentional per the inline comment (`// not checking access if its primary time dimension`), but it is a real deviation from the field-access contract that a policy author reasoning about a restricted role would not expect.
- **Failure scenario:** A role whose `field_access` omits the time dimension can still `GROUP BY`/filter it and read its distinct values, even though the policy author expected it hidden.
- **Recommendation:** If time is meant to be always-accessible, document it prominently in the security-policy docs; otherwise honor `CanAccessField` for the time dimension (or gate the bypass behind an explicit option).

**Verification:** CONFIRMED — `LookupDimension` (`runtime/metricsview/ast.go:615-632`) returns the primary time dimension (or a synthetic `{Name, Column}` spec when undeclared) under the comment `// not checking access if its primary time dimension` at `:620-621`, before the `visible`/`Security.CanAccessField` gate at `:634-638`. Any select/group/filter on the time dimension (including via `time_floor`, since `ResolveDimension` routes through `LookupDimension` at `ast.go:387`) bypasses field-level access checks. Behavior is intentional per the comment, but the deviation from the field-access contract is real.

**Manual Reproduction Steps (for QA):**
1. Create a metrics view whose YAML declares the time column as an explicit dimension (e.g. dimension name equals `timeseries:` column) and a security policy that excludes it for a role, e.g. `security: {access: true, exclude: [{if: "'{{ .user.domain }}' != 'admin.com'", names: ["<time_dim_name>"]}]}` (or an `include` list omitting it).
2. Deploy/serve, and as a user matching the restricted rule, query the metrics view via the API or MCP `query_metrics_view` with `dimensions: [{name: "<time_dim_name>"}]` (or a `time_floor` compute on it), one measure, and optionally a `where` filter on the time dimension.
3. Expected (per the field-access contract a policy author assumes): `ErrForbidden` / the field rejected. Actual: the query succeeds and returns grouped time values.
4. Control check: apply the same exclude rule to a non-time dimension and confirm that querying it is correctly forbidden, demonstrating the time dimension is the exception.

## Product Improvements
- **metricsview-07** and **metricsview-08** above double as robustness/clarity improvements a policy author or operator would feel.
- `Executor.ValidateQuery` is a `panic("not implemented")` stub (`executor.go:166-169`). A real pre-flight validator (name resolution, grain validity, required-dimension checks) would let callers reject bad queries with a clear error before execution, and would have caught the panics in metricsview-02/04.
- Interactive pivots run an "inefficient shim" that exports to Parquet and re-reads via DuckDB (`executor.go:426-474`). Users doing interactive pivot exploration on medium result sets pay a disk round-trip and a fixed timeout.

## New Feature Ideas
- **Implement "per"-dimension derived measures.** `addDerivedMeasureWithPer` is a stub returning `support for "per" not implemented` (`ast.go:910-914`); wiring it up unlocks measures like "revenue per active user" natively. Effort: L.
- **Approx/two-phase comparison for delta sorts.** `rewriteApproxComparisonNode` bails on `sortDelta` (`executor_rewrite_approx_comparisons.go:171-173`) and `rewriteTwoPhaseComparisons` only supports base/compare-value sorts. Supporting delta/ratio sorts would make comparison dashboards sortable by change on high-cardinality dimensions without full scans. Effort: L.
- **Compute percent-of-total with a window function.** Replacing the separate totals round-trip query (`executor_rewrite_percent_of_totals.go`) with `SUM(m) OVER ()` where the dialect supports it removes an extra OLAP query per request and sidesteps both the zero-total/precision issue (metricsview-06) and the NULL-total scan error (metricsview-09). Effort: M.
- **Extend rollup routing coverage.** Rollups are skipped for non-primary time dimensions and for `URI`-measure-referenced dimensions that may not exist in the rollup table (`executor_rewrite_rollup.go`). Broadening routing (and validating measure-referenced dimensions) would let more queries benefit from pre-aggregation. Effort: M.
- **Native regex/wildcard filter operator.** Given metricsview-05, expose a first-class `regex`/`glob` filter operator (properly escaped per dialect) so search and advanced filters behave identically across DuckDB/ClickHouse/Druid/Pinot. Effort: M.
- **Structured query validation surface.** Build the `ValidateQuery` stub into an API that returns typed errors (unknown field, invalid grain, missing required dimension, cap exceeded) so the frontend/AI can correct queries before executing. Effort: M.

## Notes & Missing Test Coverage
- **Druid LIKE/search semantics (metricsview-05):** `convertLikeExpressionToRegexExpression` has no test asserting behavior for values containing `.`/`(`/`_`; add cases pinning the escaped output.
- **percent_of_total zero/near-zero total (metricsview-06) and NULL total (metricsview-09):** untested; add cases where the totals query returns `0` and where it returns NULL (empty filtered set).
- **Malformed-expression panics (metricsview-02/04):** no tests feed malformed `cast` conditions or invalid grains with duplicate time-floor dimensions. Both are reachable from the `metrics` resolver's `WeakDecode` of arbitrary properties.
- **Offset push-down (metricsview-01):** there are no tests exercising `OFFSET` through `rewriteLimitsIntoSubqueries`; a multi-level spine + offset test would either confirm the latent bug or demonstrate it is currently unreachable.
- `ExpressionToSQL`'s `writeSubquery` emits `s.Dimension.Name` unescaped and a hardcoded `FROM metrics_view` (`query_expression_sql.go:59-94`); this is used only for display/round-trip via `ConvertExpressionToMetricsSQL`, not execution, so it is a fidelity nit rather than an injection risk — but a dimension name with quotes/spaces would not round-trip back through the parser.

## Verification Notes
Independently re-verified every finding against the code at the cited locations.

- **Removed metricsview-03** (`date_add`/`date_sub` index `node.Args` without a length check) as a **false positive**. `date_add`/`date_sub` are reserved builtin function tokens in the TiDB/MySQL parser (`btFuncTokenMap`, consulted only when the identifier is immediately followed by `(`, `misc.go:1099-1110`). Their sole grammar production is `FunctionNameDateArith '(' Expression ',' "INTERVAL" Expression TimeUnit ')'` (`parser.y:7964-7974`), which always emits exactly 3 args; even `ADDDATE`/`SUBDATE`'s two-argument form injects a `DAY` `TimeUnitExpr` as the third arg (`:7942-7952`) and uses a different FnName. `date_add(ts)` is therefore a syntax error that never reaches the handler, so the reachable arg count is fixed at 3. The reviewer's contrast with `date_trunc` is actually the explanation for the asymmetry: `date_trunc` is a generic identifier function parsed by the variable-arity `FunctionCallGeneric` rule and genuinely needs its `len(node.Args) != 2` guard (`parser.go:296`), as do `time_range_start/end` (`time_range_parser.go:85`). No length guard on `date_add`/`date_sub` is dead code.

The code asymmetry (limit threaded via `n.Limit`, offset re-read from `ast.Root.Offset`) is real, but a runtime query producing a ≥2-level spine push-down with a non-nil offset was not confirmed, and approximate comparisons (when enabled) consume the offset earlier.
