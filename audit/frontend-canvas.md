# Canvas Dashboards — Code Review
**Scope:** `web-common/src/features/canvas` (stores, components, filters, tab groups, inspector, explore-link, AI generation) plus the tightly-coupled PDF export in `web-common/src/features/exports/pdf`  |  **Health:** fair

## Overview
The canvas feature implements free-form dashboards: a `CanvasEntity` owns per-canvas time/filter/layout state, a component registry, and a heterogeneous `layout` of plain rows and tab groups. The code is dense but generally well-commented, and the recent tab-group and PDF-export work is thoughtfully structured (stable-name matching across spec rebuilds, ref-counted `acquire`/`release`, off-screen export render). The biggest risks are (1) the PDF export path silently drops all tab-group content, (2) several Svelte "nested `derived(...).subscribe(set)`" patterns leak subscriptions on every dependency change, (3) async time-interval derivation has no request-sequencing so stale results can overwrite current ones, and (4) `lastVisitedState` is keyed by canvas name only while everything else is keyed by `instanceId::name`, allowing cross-project state bleed. Layout/filter logic carries meaningful legacy debt (self-described `wip`/`bgh` markers and a cluster of dead grid mutation methods). None of the issues block the happy path, but the tab-group export omission and the filter-mode bug are user-visible correctness defects.

## Findings

### frontend-canvas-01 [HIGH] PDF export omits all tab-group content

**Status (2026-07-25):** ✅ Fixed and merged in [#9722](https://github.com/rilldata/rill/pull/9722).

- **Category:** data-loss  **Confidence:** high  **Location:** `web-common/src/features/exports/pdf/CanvasPdfExportView.svelte:21,37`
- **Problem:** The export render iterates `rows = $_rows` (`{#each rows as row}`) and mounts `StaticCanvasRow` per row. `_rows` is the `Grid` of *free* rows only: `processLayout` builds it via `this._rows.updateFromCanvasRows(freeRows)` where `freeRows` explicitly excludes tab groups (`canvas-entity.ts:799-825`; tab groups go into `layout`/`this.tabGroups` instead). The live dashboard, by contrast, renders `blocks = $layout`, which contains both `row` and `tab-group` blocks and mounts `CanvasTabGroupView` for the latter (`CanvasDashboardEmbed.svelte:43,65-85`). `StaticCanvasRow` has no tab-group branch. Consequently the off-screen capture DOM (`#canvas-pdf-export-view`) contains no tab-group widgets, and `captureCanvasBlocks` (`capture.ts:111-113`) finds no `article.component-card` elements inside them to rasterize.
- **Failure scenario:** A canvas whose content lives inside one or more tab groups is exported to PDF. If the canvas mixes free rows and tab groups, the export succeeds but the PDF contains only the free rows (often just a header/KPI strip); every tabbed chart/table is silently missing. If the entire canvas is a single tab group and filters are not included, `captureCanvasBlocks` returns no blocks and `export-canvas-pdf.ts:45-46` throws "Nothing to export on this canvas." (With `includeFilters` on, you instead get a header-only PDF with no components.)
- **Recommendation:** Render `layout` blocks in `CanvasPdfExportView` the same way the live views do (reuse `CanvasTabGroupView`, or a static variant), and decide the intended semantics for tabs (export the active tab only, or expand every tab into sequential sections). `rowIndexFor`/pagination in `capture.ts`/`layout.ts` will also need to account for tab-group sections.

**Verification:** CONFIRMED — `CanvasPdfExportView.svelte:17,21,37` renders only `$_rows` via `StaticCanvasRow` (which contains no tab-group branch; verified by grep, zero "tab" references in `StaticCanvasRow.svelte`), while `canvas-entity.ts:799-825` (`processLayout`) routes `row.tabGroup` rows into `this.tabGroups` and only pushes non-tab rows into `freeRows` → `this._rows.updateFromCanvasRows(freeRows)` (`:825`). The live view renders both kinds: `CanvasDashboardEmbed.svelte:43,65-67` iterates `$layout` and mounts `CanvasTabGroupView` for tab-group blocks. `capture.ts:93,112` scrapes `article.component-card` inside `#canvas-pdf-export-view`, and `export-canvas-pdf.ts:46` throws "Nothing to export on this canvas." when no blocks are found.

**Manual Reproduction Steps (for QA):**
1. Create or open a canvas dashboard that contains at least one tab group (a row with multiple tabs, each holding charts/tables) plus at least one regular (non-tabbed) row.
2. Open the canvas in the dashboard view and trigger the PDF export (Export / Download as PDF action in the canvas toolbar menu).
3. Open the downloaded PDF. Expected: all widgets appear, including those inside the tab group. Actual: only the regular rows appear; every widget inside the tab group is missing.
4. Repeat with a canvas whose entire content is inside tab groups (no free rows) and filters not included in the export. Expected: a PDF of the tabbed content. Actual: export fails with the error "Nothing to export on this canvas." (with filters included, you instead get a PDF containing only the header/filter strip).

### frontend-canvas-02 [MEDIUM] In-list→Select conversion never clears the in-list marker (discarded `.filter()`)
- **Category:** bug  **Confidence:** high  **Location:** `web-common/src/features/canvas/stores/filter-state.ts:308-310`
- **Problem:** When a dimension in "in-list" mode is edited via `toggleDimensionValueSelections`, the code converts it to a Select expression and intends to drop the in-list marker: `if (wasInListFilter) { dimensionsWithInListFilter.filter((d) => d !== dimensionName); }`. `Array.prototype.filter` returns a new array and does not mutate; the result is discarded, so `dimensionName` stays in `dimensionsWithInListFilter`. The subsequent `getFilterParam(wf, ..., dimensionsWithInListFilter)` (`:326`) then serializes the dimension as `IN LIST` (`convertInExpressionToFilterParam` branches on `dimensionsWithInlistFilter.includes(column)`, `converters.ts:113-117`), and on the URL round-trip `getFiltersFromText`→`convertFilterParamToExpression` re-derives the in-list marker from the `IN LIST` token (`converters.ts:25-30`, `dimension-search-text-utils.ts:40-41`), so `getDimensionFilterItemsMap` re-applies `mode: InList` (`filter-state.ts:592-600`).
- **Failure scenario:** User has a dimension filter authored in in-list mode, then clicks a value to toggle it. A "Converted filter type to Select" toast appears, but the pill stays in in-list mode after the URL updates — the advertised conversion silently does not stick.
- **Recommendation:** Actually mutate the array, e.g. `const i = dimensionsWithInListFilter.indexOf(dimensionName); if (i !== -1) dimensionsWithInListFilter.splice(i, 1);` (or reassign the filtered result before passing it to `getFilterParam`).

**Verification:** CONFIRMED — `filter-state.ts:308-310` reads `if (wasInListFilter) { dimensionsWithInListFilter.filter((d) => d !== dimensionName); }`; the `.filter()` result is discarded, and the unmodified array is passed to `getFilterParam` at `:326-330`. `toggleDimensionValueSelections` is wired into the canvas filter pill UI via `CanvasFilters.svelte:39,248`.

**Manual Reproduction Steps (for QA):**
1. Open a canvas dashboard with filters enabled and add a dimension filter pill (e.g. on a country dimension).
2. Put the pill in in-list mode: open the pill and paste a comma- or newline-separated list of values into the search box (this switches the filter to "in list" mode).
3. Open the pill's value dropdown and click a value to toggle its selection.
4. Expected: a toast "Converted filter type to Select" appears and the pill becomes a normal Select filter. Actual: the toast appears, but after the URL updates the pill is still in in-list mode (the URL filter param still serializes as `IN LIST`).

### frontend-canvas-03 [MEDIUM] Async time-interval derivation has no request sequencing; stale results overwrite current ones
- **Category:** concurrency  **Confidence:** high  **Location:** `web-common/src/features/canvas/stores/time-state.ts:127-209`
- **Problem:** `interval` is a `derived([rangeStore, _metricsViews, timeZoneStore, hasTimeSeriesMap], (…, set) => {...})` that fires `Promise.all(deriveInterval(...))` and calls `set(latestInterval)` / `this.minMaxTimeStamps.set(...)` when it resolves. `deriveInterval` is `async` and awaits `fetchTimeRanges`, a runtime network call (`new-time-controls.ts:349,375`). The callback returns no cleanup function and there is no sequence/epoch guard, so when inputs change while a request is in flight, the older `Promise.all` can resolve *after* the newer one and clobber the store with a stale interval. Because `comparisonIntervalStore`, `grainStore`, and `canPanStore` all derive from `interval`, a stale value propagates to every chart query.
- **Failure scenario:** User switches time range from an uncached range to a cached one; the cached one resolves first and sets the interval, then the slower request resolves later and overwrites it. `rangeStore` now says one range while `interval` reflects another, until the next change. Rapid range/zone toggling makes this reproducible; query caching narrows the window for already-fetched ranges, but `deriveInterval` force-refetches any range containing `now` (`cacheBust`, `:373`), and cold-cache first fetches are always exposed.
- **Recommendation:** Guard the async resolution with a monotonically increasing token captured before the `await` and ignore results whose token is no longer current (or key the work through TanStack Query and read the latest). Apply the same guard to the `minMaxTimeStamps.set` inside the same block.

**Verification:** CONFIRMED — `time-state.ts:127-210`: the derived callback fires `Promise.all(promises)` (`:162`) built from async `deriveInterval` calls and invokes `set(latestInterval)` / `this.minMaxTimeStamps.set(...)` in the `.then` (`:199-206`) with no epoch/token guard and no cleanup function returned. `deriveInterval` (`new-time-controls.ts:349`) awaits `fetchTimeRanges` (`:375`) with `cacheBust` when the range contains "now" (`:373`), so network round-trips are common and out-of-order resolution can overwrite the current interval with a stale one. The defect is unconditional in code; observing it depends on network timing.

**Manual Reproduction Steps (for QA):**
1. Open a canvas dashboard with a time-range selector, with browser DevTools open and network throttling set to "Slow 3G" (to widen the race window).
2. Select an uncached time range A (one not yet visited this session), then immediately (before charts settle) switch to time range B whose data is already cached or resolves fast.
3. Expected: charts and the displayed interval always reflect B, the last selection. Actual (timing-dependent): once A's slower request resolves, the charts/interval snap back to A's interval while the time-range picker still shows B, until the next interaction.
4. If not reproduced after several attempts, this is timing-dependent; confirm in code: `web-common/src/features/canvas/stores/time-state.ts:162-209` — no request-sequencing token around the `Promise.all(...).then(set)`.

### frontend-canvas-04 [MEDIUM] `lastVisitedState` is keyed by canvas name only, leaking state across instances/projects
- **Category:** correctness  **Confidence:** high  **Location:** `web-common/src/features/canvas/stores/canvas-entity.ts:54,660,599`
- **Problem:** `lastVisitedState` is a module-level `Map<string,string>` written with `lastVisitedState.set(this.name, …)` (`saveSnapshot`, `:660`) and read with `lastVisitedState.get(canvasName)` where `canvasName === this.name` (`handleCanvasRedirect`, `:599`). Everything else that identifies a canvas is keyed by `instanceId::canvasName` (the registry `makeCanvasId`, `state-managers.ts:17`). Because the map is module-scoped (persists for the lifetime of the SPA, never cleared on `dispose`) and namespaced only by name, two canvases that share a name across different runtime instances collide.
- **Failure scenario:** In Rill Cloud, a user visits project A's canvas `overview` (saving its filter/URL snapshot under key `overview`), then client-side-navigates to project B's canvas `overview` (a different `instanceId`) with no query params. `handleCanvasRedirect` finds the snapshot and redirects project B's canvas to project A's saved filter string — cross-project state bleed, and potentially invalid filters for B's metrics views. Preconditions: two projects with a same-named canvas and SvelteKit client-side navigation between them (no full reload); the keying inconsistency itself is unconditional.
- **Recommendation:** Key `lastVisitedState` by `makeCanvasId(name, instanceId)` (or move it onto the per-instance registry) so snapshots cannot cross instance boundaries.

**Verification:** CONFIRMED — `canvas-entity.ts:54` declares module-level `export const lastVisitedState = new Map<string, string>()`; `saveSnapshot` writes `lastVisitedState.set(this.name, filterState)` (`:660`) and `handleCanvasRedirect` reads `lastVisitedState.get(canvasName)` (`:599`) and redirects to the snapshot with first priority (`:602-605`). The registry keys everything else by `instanceId::name` via `makeCanvasId` (`state-managers.ts:17`). The map is never cleared in `dispose`/`destroy`. The keying defect is unconditional; the user-visible bleed requires two same-named canvases across instances plus client-side navigation.

**Manual Reproduction Steps (for QA):**
1. In Rill Cloud, set up two projects (A and B) in the same org, each containing a canvas dashboard with the identical name (e.g. `overview`).
2. Open project A's `overview` canvas and apply a distinctive filter and time range (note the URL query params).
3. Without a full page reload, navigate within the app (breadcrumbs/org project list, client-side navigation) to project B's `overview` canvas, arriving with no query params in the URL.
4. Expected: project B's canvas opens with its own defaults. Actual: project B's canvas URL is rewritten with project A's saved filter/time params (which may reference dimensions that do not exist in B's metrics views).
5. Note: a full browser reload between steps 2 and 3 resets the module map and hides the bug; the navigation must stay client-side.

### frontend-canvas-05 [MEDIUM] Nested `derived(...).subscribe(set)` leaks a subscription on every dependency change
- **Category:** performance  **Confidence:** high  **Location:** `web-common/src/features/canvas/components/BaseCanvasComponent.ts:285,364` (also `components/markdown/util.ts:135-196` and `stores/filter-manager.ts:114-143,145-180,182-198`)
- **Problem:** These stores use the pattern `derived(outerDeps, (values, set) => { derived(innerDeps, …).subscribe(set); })`. The outer callback creates a fresh inner subscription every time it re-runs but never returns a cleanup function (the `derived(...).subscribe(set)` is a bare statement, not returned), so Svelte cannot tear the previous inner subscription down. In `timeAndFilterStore` the outer store has 17 dependencies (global + local time controls, filters, specs) that change on essentially every time/filter interaction, and it is exposed as a getter (`get timeAndFilterStore()`, `:184`) that also mints a new store per access — so inner subscriptions to `mvFilters.parsed` accumulate for as long as any consumer (ExploreLink, FiltersMapper, KPIGrid, LocalFiltersHeader, chart renderers, markdown templating) holds the store. The `filter-manager.ts` variants leak less often because their outer dependency (`metricsViewFilters`) changes rarely, but the pattern is identical.
- **Failure scenario:** A dashboard left open while the user pans/changes time and filters accrues one leaked `mvFilters.parsed` subscription per interaction per mounted consumer; memory and redundant recomputation grow monotonically over a long session.
- **Recommendation:** Return the inner unsubscribe from the outer callback (`return derived(innerDeps, …).subscribe(set);`) so Svelte cleans it up on re-run/last-unsubscribe, or flatten to a single `derived` over the union of dependencies. Convert `timeAndFilterStore` from a getter into a cached field so it is not re-created per access.

**Verification:** CONFIRMED — `BaseCanvasComponent.ts:285-364`: inside the outer derived callback, `derived([mvFilters.parsed], ...) .subscribe(set)` is a bare statement (`:364`) and the outer callback returns nothing, so the inner subscription is never torn down when the outer dependencies re-fire. `get timeAndFilterStore()` at `:184` mints a new store per property access. Same un-returned `subscribe(set)` pattern verified at `filter-manager.ts:141,178,196` and `markdown/util.ts:194`.

**Manual Reproduction Steps (for QA):**
1. Open a canvas dashboard with several charts/KPIs in Chrome with DevTools > Memory open; take a heap snapshot.
2. Interact heavily for a few minutes: repeatedly change the time range, toggle comparison, and add/remove/edit dimension filter values (each interaction re-fires the outer derived and leaks one inner subscription per mounted consumer).
3. Take a second heap snapshot and compare: retained closure/subscriber counts (e.g. objects referencing `parsedFilter`/derived stores) grow monotonically with interaction count and are not reclaimed by GC.
4. This is a memory/CPU-growth issue with no immediate visual symptom; primary confirmation is in code: `web-common/src/features/canvas/components/BaseCanvasComponent.ts:285,364` — inner `derived(...).subscribe(set)` not returned as the cleanup function.

### frontend-canvas-06 [LOW] `saveDefaultFilters` post-save subscription can leak when default params do not change
- **Category:** bug  **Confidence:** low  **Location:** `web-common/src/features/canvas/stores/canvas-entity.ts:476-484`
- **Problem:** After writing defaults to YAML, the code subscribes to `defaultUrlParamsStore`, skips the first (synchronous) emission, and on the *next* emission navigates and unsubscribes. `unsub()` is only called inside that second-emission branch. But `checkAndSetDefaultParams` only sets the store when the serialized value actually changes (`:281`), and `getDefaults` encodes only time range + filter expressions — not the pinned/required sets (`:1054-1090`). So if the save changed *only* pinned/required flags, `defaultUrlParamsStore` never re-emits: the subscription is never released and remains registered on the entity's store for its lifetime. The advertised post-save navigation is a no-op in that case, but harmlessly so, since the URL params are already canonical. The original "current state already matches defaults" trigger is largely blocked because `SaveDefaultsButton` is `disabled` whenever `viewingDefaults` is true (`SaveDefaultsButton.svelte:29`).
- **Failure scenario:** A user toggles only a filter's pin/required flag (so `viewingDefaults` is false and the button is enabled) and clicks "Save as default". The YAML `filters` block changes but `defaultUrlParamsStore` does not, so the second emission never arrives and the subscription dangles.
- **Recommendation:** Compute the target URL directly and navigate once (awaiting the artifact write) instead of racing a store emission; if the subscription approach is kept, add an immediate-unsub fallback so it cannot leak.

**Verification:** PLAUSIBLE — `canvas-entity.ts:476-484`: `unsub()` is called only inside the second-emission branch of the `defaultUrlParamsStore.subscribe` callback. `checkAndSetDefaultParams` (`:278-283`) sets the store only when the serialized params actually change, and `getDefaults` (`:1054-1090`) encodes only time range, comparison mode, and filter expressions — not pinned/required lists (those go to YAML via `setOrDeleteFilterList`). `SaveDefaultsButton.svelte:29` disables the button when `viewingDefaults`, blocking the trivial trigger. So the leak is real but requires a pin/required-only save; consequences are a single dangling subscription (benign in isolation).

**Manual Reproduction Steps (for QA):**
Not user-reproducible through visible symptoms — the missed navigation is a no-op because the URL is already canonical, and a single dangling subscription has no observable effect. Confirm in code: `web-common/src/features/canvas/stores/canvas-entity.ts:476-484` (unsub only inside the second emission), `:278-283` (store only set on change), and `:1054-1090` (`getDefaults` ignores pinned/required). To exercise the leaking path in the UI: on a canvas viewing non-default state, change only a filter's pin state and click "Save as default"; set a breakpoint on `:482` and observe it never fires.

### frontend-canvas-07 [LOW] Image component never revokes object URLs

**Verification:** CONFIRMED — `Image.svelte:56` calls `URL.createObjectURL(blob)`; there is no `URL.revokeObjectURL` anywhere in the file and no `onDestroy` import/handler. The reactive block at `:24-31` re-invokes `fetchImage(url)` on every `url` change, and `fetchImage` (`:33-41`) has no sequencing guard.

## New Feature Ideas
- **Tab-aware PDF/PNG export (S–M):** Once frontend-canvas-01 is fixed, let the export dialog choose "active tab only" vs. "all tabs as sections," with each tab labeled in the PDF. High value for teams that organize canvases into tabbed sections and currently get incomplete exports.
- **Per-widget "reset to canvas defaults" affordance (S):** Widgets can carry local `time_filters`/`dimension_filters`; expose a one-click reset on the widget header so viewers can clear an overriding local filter without editing YAML.
- **Filter-mode indicator + explicit toggle on pills (S):** Given the in-list/Select confusion (frontend-canvas-02), show the current mode on the pill and make conversion explicit rather than a side effect of a value click.
- **Shareable canvas view state via short links (M):** `lastVisitedState`/bookmarks already capture URL state; a "Copy link to this view" that snapshots time+filters+active tabs would make canvas sharing first-class (and would benefit from the instance-scoped keying in frontend-canvas-04).
- **Export progress + partial-failure report (M):** `captureCanvasBlocks` already degrades per-block failures to warnings; surface a post-export summary ("2 of 14 components could not be rendered") so silent omissions in a PDF are visible to the user.
- **Cross-widget "apply this filter globally" from pivot click-to-filter (M):** The pivot click-to-filter engine is powerful but scoped to self-filtering; a prompt to promote a click selection into a global canvas filter would streamline drill-down workflows.
