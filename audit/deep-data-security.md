# Data Security (access & row policies, data leaks) — Deep-Dive Audit

**Focus:** DATA SECURITY end-to-end — is every data-returning path gated by `CanAccess()` and does it actually apply the metrics-view `security_policy` (row filter + field access)? Row-filter SQL/template injection. Cross-context cache leakage. Token/claims scoping. Field-access removal.  |  **Scope:** `runtime/security.go`, `runtime/resolver.go`, `runtime/resolvers/{metrics,annotations,metricsview_summary,metricsview_time_range,metricsview_cache_key,sql,metrics_sql,builtin_*,union}.go`, `runtime/metricsview/{ast.go,astexpr.go,executor/*}`, `runtime/server/{queries_metrics,api,downloads}.go`, `runtime/server/auth/*`, `runtime/ai/*` (MCP tools), `admin/server/{magic_tokens,runtime_jwt,deployment,server}.go`  |  **Health:** needs-attention

## Overview

I traced every data-returning surface from claims resolution (`resolveSecurity`) through the executor's SQL construction to the shipped resolvers, the legacy gRPC query handlers, and the MCP/AI tools. The **access gate** (`CanAccess()`) is applied consistently on the query, export, search, summary, schema, and time-range paths (executor and resolvers), and `list_metrics_views`/`get_metrics_view` correctly strip field-access-excluded dimensions/measures from the spec they return. `SkipChecks` is reachable only via auth-disabled local mode (`interceptors.go:121`) or a superuser-minted `ManageInstances` token (`claims.go:44-50`) — not by ordinary cloud callers — so the "SkipChecks in cloud" worry is not borne out. Magic-token and embed row filters travel as **parameterized** proto `Expression`s, which are injection-safe.

The headline problem is **the metrics-view *metadata* paths silently skip the row-level security filter while still enforcing field access.** `Executor.Summary` and `Executor.Timestamps` build their SQL directly against the physical table (not through `NewAST` → `buildWhereForUnderlyingTable`), so they never emit `Security.RowFilter()` or `Security.QueryFilter()`. `Summary` returns per-dimension **example / min / max values computed over every row in the table**, ignoring the tenant/row restriction — a concrete cross-security-context data leak that is reachable through the shipped MCP/AI `query_metrics_view_summary` tool and any `metrics_summary` custom API. This is *worse* than, and independent of, the already-tracked resolver-cache-key bug (A.1): even with a correct cache key, the summary result itself leaks.

Secondarily, raw-SQL row filters interpolate claim **attribute values without any SQL escaping** (Go `text/template`, emitted as raw SQL with no bound args), so a policy that templates a user-influenceable attribute (notably `.user.name`, the OIDC display name) into a raw-SQL row filter is injectable / bypassable.

I confirmed rather than re-filed the tracked items: A.1 (resolver cache key omits security context, `resolver.go:210-218`), A.2 (`annotations` resolver missing `CanAccess`), and the Tier-2 magic-token `admin` flag replay all still stand.

## Findings

### deep-data-security-01 [HIGH] Metrics-view Summary leaks per-dimension example/min/max values across the row-level security filter

**Status (2026-07-25):** ✅ Fixed and merged in [#9717](https://github.com/rilldata/rill/pull/9717).

- **Category:** data-leak  **Confidence:** high  **Novelty:** new (expands the resolvers-02/A.1 speculation into a confirmed, cache-independent bypass)  **Must-fix:** yes  **Location:** `runtime/metricsview/executor/executor_summary.go:152-174` (SQL built with no security filter) and `:218-225` (values returned); reached via `runtime/resolvers/metricsview_summary.go:113-117` and `runtime/ai/metrics_view_summary.go:55-82`
- **Problem:** `Executor.Summary` gates on `CanAccess()` (`:41`) and honours **field** access (`:49` skips dimensions failing `CanAccessField`), but the categorical-dimension summary query is assembled by hand — `SELECT <min/max/has_nulls/ANY_VALUE> ... FROM <table> [WHERE <timeDim> >= ?] LIMIT 1` (`:163-174`) — and the only `WHERE` it ever adds is the `SummarySampleInterval` time clause (`:153-161`). It never calls `e.security.RowFilter()` or `e.security.QueryFilter()`. Every other executor path (`Query`, `Export`, `Search`, `Schema`) routes through `metricsview.NewAST` → `buildWhereForUnderlyingTable` (`runtime/metricsview/ast.go:1045-1046`), which is the *only* place the row filter is applied. `Summary` bypasses `NewAST` entirely, so the row filter is dropped. The returned `DimensionSummary` carries `MinValue`, `MaxValue`, and `ExampleValue` (`ANY_VALUE(dim)`) for each accessible dimension (`:216-225`).
- **Failure scenario / perf impact:** A SaaS embeds a shared-table dashboard per customer with row-level security (`security_policy` row filter or a magic-token/embed `Expression` filter restricting to `tenant_id = X`). The embed JWT grants `ReadMetrics` + `UseAI` (`admin/server/runtime_jwt.go:190-195`), so the end user can invoke the MCP/AI `query_metrics_view_summary` tool (`runtime/ai/metrics_view_summary.go`), which calls the `metrics_summary` resolver with the embed's claims. The resolver checks `CanAccess()` (passes — the tenant *can* see the view) and returns `ANY_VALUE`, `MIN`, `MAX` for every accessible dimension **computed over all tenants' rows**. For a `customer_email` / `account_id` / `salary` dimension this discloses another tenant's concrete value (the example) plus the global range. The same leak is reachable without AI via any custom API declared with `resolver: metrics_summary`. Field-access exclusion does not help: for *included* dimensions the row filter is the control that is missing.
- **Recommendation:** Build the summary query through the same security-aware path as the other executor methods, or explicitly append `e.security.RowFilter()` and compile `e.security.QueryFilter()` into the `WHERE`/args of the summary SQL (and the per-time-dimension `Timestamps` calls it makes). Add a test that a metrics view with a row filter returns summary example/min/max scoped to the filtered rows. Note: fixing the resolver cache key (A.1) alone does **not** fix this — the underlying result is already wrong.

### deep-data-security-02 [MEDIUM] Raw-SQL row filters interpolate claim attribute values with no SQL escaping (row-filter bypass / injection)
- **Category:** security  **Confidence:** medium  **Novelty:** new (prior `metricsview.md` scoped its "no SQL injection" conclusion to the query-builder literal path; the row-filter template path is unescaped)  **Must-fix:** no  **Location:** `runtime/security.go:757-769` (`applySecurityRuleRowFilter` → `parser.ResolveTemplate(rule.Sql, td, false)` → `res.rowFilter`), emitted as raw SQL at `runtime/metricsview/ast.go:1045-1046` (`res.And(rf, nil)` — no bound args)
- **Problem:** A `security_policy` raw-SQL row filter (e.g. `sql: "owner = '{{ .user.name }}'"`) is resolved with Go `text/template` (`runtime/parser/template.go:214-373`), which performs **no** SQL/quote escaping, and the resulting string is concatenated verbatim into the `WHERE` clause with `Args: nil`. The template values come from `claims.UserAttributes`. Several of those attributes are user-influenceable: `name` is the raw OIDC `name` claim stored unsanitized as `DisplayName` (`admin/server/auth/handlers.go:301,327` → `admin/user.go:141-142`, exposed as `.user.name` in `admin/server/server.go:381`), and embed attributes provided via `GetIFrame`/`GetDeploymentCredentials` are the integrator's map verbatim (`admin/server/deployment.go:563,669` → `runtime_jwt.go:148-149`), which integrators commonly populate from *their* end users' input.
- **Failure scenario / perf impact:** A viewer whose metrics view is restricted by `sql: "region = '{{ .user.name }}'"` (or any raw-SQL filter over a controllable attribute) sets their profile display name to `x' OR '1'='1' --`. The compiled filter becomes `region = 'x' OR '1'='1' --'`, defeating the row restriction and returning all rows; a subquery payload can exfiltrate arbitrary columns. In the embed case, an integrator forwarding an unsanitized username as a custom attribute lets their end user do the same. Rill offers no defense-in-depth here because the value is never escaped or parameterized. (The magic-token `MetricsViewFilters` and the query-builder `where` are unaffected — those are parameterized `Expression`s.)
- **Recommendation:** SQL-escape string attribute values when resolving raw-SQL row-filter templates (e.g. a template `funcMap` that single-quote-escapes, or reject metacharacters), or steer policy authors to the `Expression`-based row filter (already parameterized). At minimum, document loudly that raw-SQL row filters must not template untrusted attributes, and sanitize `DisplayName` on ingest.

### deep-data-security-03 [LOW] Time-range (Timestamps) min/max/watermark ignores the row filter — same root cause as -01
- **Category:** data-leak  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_timestamps.go:43-51` (`resolveWithTimestampQuery`; the ClickHouse/Pinot/Druid/BigQuery variants at `:85,:136,:191,:322` are equivalent), reached via `runtime/resolvers/metricsview_time_range.go:140` and the legacy `MetricsViewTimeRange` handler (`runtime/server/queries_metrics.go:404`)
- **Problem:** `Executor.Timestamps` computes `SELECT min(t), max(t), <watermark> FROM <table>` with no security predicate, so a row-restricted caller receives the **global** temporal bounds of the underlying table rather than the bounds of their permitted rows. This is the same architectural gap as -01 (metadata query bypasses `buildWhereForUnderlyingTable`). It is lower severity because temporal bounds are far less sensitive than dimension values and are shown on every dashboard load by design.
- **Failure scenario / perf impact:** A tenant whose rows only span Jan 2024 sees a dashboard/time-range endpoint reporting the full 2010–2024 extent of the shared table, disclosing that other data exists and its time span. No row *values* leak, only the min/max/watermark timestamps.
- **Recommendation:** Decide explicitly whether time bounds should be security-scoped. If yes, apply the row filter to the timestamp query (or derive bounds from a filtered subquery); if the current global-bounds behavior is intended, document it so policy authors don't assume time is row-scoped.

## Confirmations / refutations of prior findings (no re-file)

- **A.1 / runtime-core-01 / resolvers-02 — resolver query cache key omits the security context (`runtime/resolver.go:210-218`): CONFIRMED, and deepened.** The composite key hashes only `opts.Claims.UserAttributes` (via `hashstructure`); `AdditionalRules`, `Permissions`, and `SkipChecks` are excluded, while the security engine's own key marshals the full claims (`security.go:892` + `MarshalJSON` at `:103-121`). New root-cause note for the fixers: the `metrics_summary` and `metrics_time_range` resolvers use `cacheKeyForMetricsView` (security-independent), and — per finding -01/-03 — their *results already ignore the row filter*. So the A.1 cache-key fix (PR #9704) secures the `metrics` resolver but will **not** stop the summary/time-range leak; those need the row filter applied at the executor. The cache-key lint harness proposed in runtime-core.md should assert distinct keys **and** distinct results for two claims differing only in `AdditionalRules`.
- **A.2 / resolvers-03 — `metrics_annotations` resolver missing `CanAccess` (`runtime/resolvers/annotations.go:51-64`): CONFIRMED via a second call path.** The legacy gRPC `MetricsViewAnnotations` handler (`runtime/server/queries_metrics.go:612-671`) checks only the coarse instance-level `ReadMetrics` and then delegates to the same ungated `metrics_annotations` resolver, so both the resolver-API surface and the legacy query surface leak annotation rows to a viewer denied the view by its `security_policy`. `Executor.Annotations`/`executeAnnotationsQuery` (`executor.go:689,887`) apply neither `CanAccess()` nor the row filter.
- **Tier-2 magic-token `admin`-flag replay (`admin/server/magic_tokens.go:90-100`, `runtime_jwt.go:113-119`): CONFIRMED, unchanged.** A magic token created by a project admin still captures `admin:true` (`jwtAttributesForUser` sets `"admin": projectPermissions.ManageProject`, `server.go:385`) and replays it verbatim (`runtime_jwt.go:119 attr = mdl.Attributes`), subverting `{{ .user.admin }}` policies.
- **"SkipChecks reachable in cloud": REFUTED.** `SkipChecks=true` is set only when auth is disabled (`interceptors.go:114-123`, local Developer) or when the JWT carries `ManageInstances` (`claims.go:44-50`), which is granted solely via `grantManageAll` gated on `claims.Superuser(ctx)` (`runtime_jwt.go:223-234`). The `skip_nested_security` custom-API path (`runtime/server/api.go:72-73`) sets `SkipChecks` on a freshly-returned per-call `*SecurityClaims` (`jwtClaims.Claims` returns a new struct each call), so it does not leak across requests — though its cached result is still exposed by the A.1 key bug.
- **Field-access removal from spec surfaces: CONFIRMED CORRECT.** `ApplySecurityPolicy` → `applyMetricsViewSpecSecurity` (`runtime/resources.go:220-277`) strips excluded dimensions/measures from both `Spec` and `State.ValidSpec`, and the AI `get_metrics_view`/`list_metrics_views` tools call it. `LookupDimension`/`LookupMeasure` return `ErrForbidden` for hidden fields (`ast.go:635-637,653-655`), and because `CanAccessField` returns false for both hidden and non-existent names, there is no forbidden-vs-not-found enumeration oracle when a field-access policy is present.

## Verification Notes

Adversarial re-verification (staff-level, second pass). I opened every cited file and traced each finding's hot path end-to-end. **All three findings survive unchanged** — severities, categories, confidences, must-fix flags, and file:line references are accurate. **Removed: 0. Added: 0.**

**-01 (Summary leak) — CONFIRMED HIGH / high / must-fix.**
- The row filter is applied in exactly one place: `AST.buildWhereForUnderlyingTable` (`ast.go:1027-1050`), which emits both `Security.QueryFilter()` (`:1036-1043`) and `Security.RowFilter()` (`:1045-1046`). It is wired into the base SELECT via `ast.go:305-310` (`ast.underlyingWhere = buildWhereForUnderlyingTable(...)`) → `buildBaseSelect` `Where: a.underlyingWhere` (`:1060`). `Query`/`Export`/`Search`/`Schema` all route through `NewAST`; `Summary` and `Timestamps` do **not**.
- `Executor.Summary` (`executor_summary.go`) consults `e.security` only at `:41` (`CanAccess`) and `:49` (`CanAccessField`). The categorical query (`:122-174`) is hand-built and its only `WHERE` is the `SummarySampleInterval` time clause (`:152-161`); neither `RowFilter()` nor `QueryFilter()` is ever called. It returns `MinValue`/`MaxValue`/`ExampleValue`=`ANY_VALUE(dim)` per accessible dimension (`:218-225`). Because *both* filter forms are dropped, the leak covers raw-SQL row filters, `Expression` query filters, **and** magic-token/embed `MetricsViewFilters` alike.
- Reachability re-confirmed: `metrics_summary` resolver checks `CanAccess()` then calls `executor.Summary` and returns the result verbatim (`metricsview_summary.go:73-75,113-131`); the shipped MCP/AI tool `query_metrics_view_summary` gates on `Can(ReadMetrics)` and invokes it with the session claims (`ai/metrics_view_summary.go:50-82`); deployment/embed JWTs grant `ReadMetrics`+`UseAI` (`runtime_jwt.go:190-195`). Also reachable via any custom API declared `resolver: metrics_summary`. Only dimensions are summarized (no measure aggregates), matching the finding's scope.

**-02 (raw-SQL row-filter injection) — CONFIRMED MEDIUM / medium / not-must-fix.**
- `parser.ResolveTemplate` (`template.go:214-373`) is Go `text/template`; its `funcMap` adds `ref`/`lookup`/`env`/`configure`/`dependency` only — no SQL/quote escaping. `applySecurityRuleRowFilter` stores the rendered string verbatim into `res.rowFilter` (`security.go:758-769`), emitted with `res.And(rf, nil)` — no bound args (`ast.go:1045-1046`).
- The scoping is correct: the `Expression`/value path is fully parameterized — every literal is written as `?` with a bound arg (`astexpr.go:77-81`, `:603-614`, `:691-697`), so magic-token/query-builder `where` filters are injection-safe. The `skipMetricsViewSecurity` used for security-policy subqueries (`astexpr.go:107-110`) is intentional (the trusted policy filter does not re-apply security) and is not a bypass.
- Attribute controllability re-confirmed: `.user.name` = `user.DisplayName` (`server.go:381`) sourced from the unsanitized OIDC `name` claim (`handlers.go:301` → `CreateOrUpdateUser`), and embed attributes are merged verbatim into JWT attrs (`runtime_jwt.go:164-174`). Exploitation still requires a policy author to template a controllable attribute into a **raw-SQL** row filter, so medium/not-must-fix stands.

**-03 (Timestamps leak) — CONFIRMED LOW / high / not-must-fix.**
- All dialect variants in `executor_timestamps.go` build `SELECT min/max/watermark FROM <table>` with no security predicate (`:43-51` DuckDB/Snowflake/Databricks/StarRocks, `:85` ClickHouse, `:136` Pinot, `:191` Druid, `:322` BigQuery). Low is right: only temporal bounds leak, and the row filter still applies to the actual data query (via `NewAST`), so widened default ranges do not themselves leak rows.
