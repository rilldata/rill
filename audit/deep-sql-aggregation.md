# SQL & Aggregation Layer — Deep-Dive Audit
**Focus:** SQL generation + aggregation correctness and performance: per-dialect quoting, comparison math (deltas/%-change/two-phase/approx), rollup routing + grain, percent-of-total, limit/offset/having, NULL/zero handling, timezone/DST, LIKE→regex, Druid exactify/groups, cap enforcement; query shape and round-trip counts.  |  **Scope:** `runtime/metricsview/{ast,astexpr,astsql,query,timestamps,max_query_time_range,query_search}.go`, `runtime/metricsview/executor/*` (all rewrites incl. `rollup_grain.go`), `runtime/metricsview/metricssql/*`, `runtime/queries/{metricsview_*,column_*}.go`, cross-referenced `runtime/drivers/{dialect,duckdb,clickhouse,druid,pinot,starrocks}/dialect.go`, `runtime/resolvers/{metrics,metricsview_time_range,legacy_metrics}.go`, `runtime/pkg/rilltime`, and the `web-common` dashboard query builders for reachability.  |  **Health:** needs-attention

## Overview
I traced the interactive query hot path end-to-end: adapter (`runtime/queries/*` or `runtime/resolvers/metrics.go`) → `Executor.Query` → pre-AST rewrites (`rewriteQueryEnforceCaps` → pivot → `RewriteQueryTimeRanges` → `enforceQueryLimits` → `rewritePercentOfTotals` → Druid exactify → rollup routing) → `NewAST` → post-AST rewrites (two-phase comparisons → approx comparisons → limit pushdown → Druid groups → ClickHouse time-dim wrap) → `AST.SQL()` → OLAP. I verified rewrite-flag defaults in `runtime/drivers/registry.go:205-215`: row cap 10 000, **approximate comparisons ON**, **two-phase comparisons ON for `limit ≤ 250`** (i.e. every comparison leaderboard/table), CTE rewrite and Druid exactify opt-in, pivot export column limit 15 000.

Headline conclusions: (1) the **two-phase comparison rewrite — on by default for the most common comparison query shape — is not composition-safe**: it silently drops `HAVING` from the phase-1 top-N (wrong/under-filled results) and produces invalid SQL when a `percent_of_total` measure rides along with comparison measures; (2) **cap/guard enforcement has directional holes**: `max_query_time_range` (and the AI `max_time_range_days` limit) is bypassed by start-only time ranges, and rollup routing silently serves stale/truncated data for half-open ranges; (3) several malformed-but-API-reachable inputs still **panic inside `NewAST`/`RewriteQueryTimeRanges`** (same class as prior metricsview-02/04, different sites); (4) DST-crossing period comparisons mis-join on fixed-interval engines (DuckDB/Druid); (5) **pre-bound timestamp caches never carry `Now`**, so `now`-anchored rill-time expressions (the implicit anchor for new-format expressions without `as of`) silently evaluate against the zero time on the metrics-resolver/MCP paths and return empty results. Performance-wise, the dominant avoidable costs are the unguarded FULL-JOIN shape for delta-sorted comparisons, the extra totals round-trip for percent-of-total (which also never benefits from rollups), and unbounded staging for interactive pivots.

Prior claims re-verified with no change: metricsview-05 (Druid LIKE→regex unescaped, `astexpr.go:787-796`), metricsview-06/09 (percent-of-total literal divide + NULL-total scan, `ast.go:537`, `executor_rewrite_percent_of_totals.go:78-98`), queries-01 (aggregation `Export` nil-`TimeRange` panic, `metricsview_aggregation.go:166` — already on MUST-FIX C). None are re-filed below.

## Findings

### deep-sql-aggregation-01 [HIGH] Two-phase comparison rewrite emits invalid SQL when `percent_of_total` is combined with comparison measures
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_rewrite_two_phase_comparisons.go:30` (bm exclusion) and `:100-107` (inline replacement)
- **Problem:** Two-phase runs by default whenever a comparison query has 1 dimension, 1 sort, and `limit ≤ 250` (`MetricsApproxComparisonTwoPhaseLimit` default 250, `registry.go:212`). The base-measure list `bm` excludes any measure whose compute is `PercentOfTotal` (line 30), so the phase-1 base query returns only `[dim, base measures]`. When sorting by a base measure or the dimension, the rewrite replaces the AST's base node with an inline `VALUES`/`UNION ALL SELECT` node carrying exactly those columns (`:100-107`; `SelectInlineResults` aliases columns by the phase-1 result schema names, `drivers/dialect.go:318-366`). But `NewAST` computed the `percent_of_total` measure *inside* the base node (`addDerivedMeasure` pushes it into `FromSelect` when a comparison join exists, `ast.go:853-873`; when the pct measure precedes the comparison measure it lands in the node that `WrapSelect` turns into "base" — broken in both measure orders), so the root still selects `base."m_pct"` — a column that does not exist in the inline node. The final SQL fails with an unknown-column error on every dialect. (Sorting by a `comparison_value` measure replaces the comparison node instead and is unaffected; sorting by the pct measure itself bails out at `:43`.)
- **Failure scenario:** Query API / MCP `query_metrics_view` / custom API: `dimensions:[d]`, `measures:[m, {m_prev: comparison_value m}, {m_pct: percent_of_total m}]`, `sort:[m]`, `limit: 10`, base+comparison time ranges → `rewritePercentOfTotals` succeeds, `NewAST` succeeds, two-phase rewrites, and the OLAP returns `Referenced column "m_pct" not found` (DuckDB wording). The explore UI computes % of total client-side so it is unaffected, but the aggregation API schema documents all three computes side by side, and AI/MCP-generated queries ("top 10 regions with % of total vs last period") hit it in the default config.
- **Recommendation:** In `rewriteTwoPhaseComparisons`, bail out (`return false, nil`) when any query measure has a compute that is excluded from `bm` but is not a comparison compute (i.e. `PercentOfTotal`), or include the pct measure in `bm` so the inline result carries the column. Add a two-phase test matrix over compute types.

### deep-sql-aggregation-02 [HIGH] Comparison rewrites apply top-N/limit/offset before HAVING, silently dropping qualifying rows
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_rewrite_two_phase_comparisons.go:58` (`Having: nil`); `runtime/metricsview/executor/executor_rewrite_approx_comparisons.go:109-170` (no `Having` guard)
- **Problem:** `rewriteLimitsIntoSubqueries` explicitly refuses to push limits when a HAVING exists — "that may filter out rows that may satisfy the having later, which would change the results" (`executor_rewrite_limit_pushdown.go:9-11`). The two other rewrites that push the root limit into a sub-select lack that guard: (a) two-phase executes the phase-1 base query with `Having: nil` and `Limit: ogLimit` (`:58-59`), so the top-N window is computed on the *unfiltered* set; the outer query then applies HAVING (compiled as a WHERE on the wrapper node, `ast.go:334-349`) to those ≤N rows, returning fewer than N rows even when more qualifying rows exist beyond the window. (b) `rewriteApproxComparisonNode` pushes `a.Root.Limit`/`a.Root.Offset` into `FromSelect`/`JoinComparisonSelect` (`:114-116`, `:135-137`, `:155-157`) even when the root is a HAVING wrapper, with the same effect (and OFFSET consumed pre-HAVING shifts pages; the walk then clears the wrapper's offset at `:38-41`). Both rewrites are enabled by default; the approx half also applies to `Executor.Export` (`executor.go:531`).
- **Failure scenario:** `MetricsViewComparison` with `having` (mapped at `queries/metricsview_comparison_toplist.go:403-406`; this legacy comparison-toplist API is what the `legacy_metrics` resolver used by persisted alerts/reports wraps, `resolvers/legacy_metrics.go:144`), or a `metrics` resolver query with `having` + comparison + 1 sort + limit ≤ 250: "top 20 dims where measure > X vs. previous period" returns e.g. 7 rows although 20 qualify — silently. In an alert criteria query this yields missed or spurious alerts. The current explore UI encodes measure filters as where-subqueries rather than `having`, which is why this has gone unnoticed.
- **Recommendation:** Mirror the limit-pushdown guard: skip two-phase and the approx limit/offset pushdown when `ast.Query.Having != nil` (or, better, push the HAVING into phase 1 when it references only base measures). This borders on ship-blocker for deployments that evaluate alerts via `MetricsViewComparison` with having.

### deep-sql-aggregation-03 [MEDIUM] `max_query_time_range` and AI `max_time_range_days` caps are bypassed by start-only time ranges
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_enforce_query_limits.go:51` (`tr.End.Sub(tr.Start) > maxDur`)
- **Problem:** After `RewriteQueryTimeRanges`, a time range with only `start` set keeps `End == time.Time{}` (`resolveISOTimeRange` only defaults `End` when *both* are zero, `executor_rewrite_time.go:118-128`). `enforceMaxTimeRange` then computes `End.Sub(Start)` = a large negative duration → never exceeds the cap → passes, and `sqlForTimeRange` emits only `ts >= ?` (`ast.go:1401-1418`), i.e. an unbounded scan to the end of data. The check is asymmetric: an end-only range computes `end - zeroTime` ≈ 2000 years and is always (over-)rejected. `QueryLimits.RequireTimeRange` is also satisfied by a start-only range (`:13`, since `TimeRange.IsZero()` at `query.go:216-218` is false when `Start` is set), so the AI guardrails (`rill.ai.max_time_range_days`) don't bound the scan either.
- **Failure scenario:** A metrics view over a multi-TB Druid/ClickHouse table sets `max_query_time_range: P90D` precisely to prevent full scans. Any API/MCP/AI caller sends `time_range: {start: "2000-01-01T00:00:00Z"}` and gets a full-history scan; the cap the operator configured does nothing.
- **Recommendation:** In `enforceMaxTimeRange`, treat a zero `End` as "now/max" (or reject half-open ranges when a cap is configured); apply the equivalent logic for zero `Start`. Add tests for start-only and end-only ranges (the existing `TestEnforceQueryLimits` only builds closed ranges).

### deep-sql-aggregation-04 [MEDIUM] Rollup routing silently serves stale/truncated data for half-open time ranges
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_rewrite_rollup.go:507-537` (`checkRangeCoverage`), contrast `:220-223`
- **Problem:** When the query has *no* time range, the code deliberately substitutes `{baseMin, baseMax}` as the coverage range so "a partial rollup would [not] silently truncate the result" (`:218-223`). But for *half-open* ranges the same hazard is unguarded (`hasTimeRange` at `:132` is true when either bound is set, so the normalization does not apply): with `End` zero, `effectiveEnd` stays zero and the end-coverage check (`rollupEffEnd.Before(effectiveEnd)`) is skipped (`:520-535`), so a rollup whose max lags the base table is still selected and the query silently misses the freshest rows. Symmetrically, with `Start` zero the start-coverage check is skipped (`:512-514`, `:524`) and a rollup that begins later than the base silently truncates history. `checkEndAlignment` also passes for zero ends (`:543`).
- **Failure scenario:** Rollup refreshed hourly, base table streaming. API query `time_range: {start: <aligned 30d ago>}` (no end) on a rollup-enabled metrics view → served from the rollup; the last hour of data present in the base table is missing from every measure, with no error and no indication. Same class of silent-wrong-data the no-range guard was written to prevent.
- **Recommendation:** In `rewriteQueryForRollup`, substitute `baseMax` for a zero `End` and `baseMin` for a zero `Start` before calling `checkRangeCoverage`/`checkEndAlignment` (i.e. extend the `!hasTimeRange` normalization to each half-open side).

### deep-sql-aggregation-05 [MEDIUM] `comparison_time` measure without a comparison time range panics while building the error message
- **Category:** bug  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/ast.go:570-573`
- **Problem:** In `ResolveMeasure`'s `ComparisonTime` branch, the guard condition correctly short-circuits on `a.Query.ComparisonTimeRange == nil`, but the *error message arguments* evaluate `a.Query.ComparisonTimeRange.TimeDimension` eagerly (`:572`) — so the nil case panics with a nil-pointer dereference while building the error it was about to return. Nothing upstream requires a comparison time range for this compute: `MeasureCompute.Validate` (`query.go:121-154`) only checks compute exclusivity, and `Query.Validate` only rejects a *non-zero* `comparison_time_range` without a `time_range` (`query.go:110`). (Note: the later `a.Query.TimeRange.Start` dereference at `:587` is *not* independently reachable — any query that passes the `:571` guard has a non-nil `ComparisonTimeRange`, and the dimension loop in `NewAST` then already returns a clean error from `sqlForExpressionAdjustedByComparisonTimeRangeOffset` (`:1505-1507`) whenever `TimeRange` is nil or has a zero start, before the measures loop runs.)
- **Failure scenario:** `metrics` resolver / MCP `query_metrics_view` / aggregation API (`MetricsViewAggregationMeasure_ComparisonTime` is mapped at `metricsview_aggregation.go:350-353`) with `measures: [{name: "ct", compute: {comparison_time: {dimension: "<time dim>"}}}]` and no comparison time range → panic in `NewAST` on the serving goroutine (at best a recovered 500 with stack trace). Same class as metricsview-02/04.
- **Recommendation:** Capture the comparison time dimension into a local before the guard (empty when nil) for the error message; optionally add an explicit `TimeRange != nil && !Start.IsZero()` check in the branch for defense in depth.

### deep-sql-aggregation-06 [MEDIUM] Time-spine rewrite panics when the query has a spine but no time range
- **Category:** bug  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_rewrite_time.go:52-53`
- **Problem:** `RewriteQueryTimeRanges` unconditionally copies `qry.TimeRange.Start/End` into the spine (`qry.Spine.TimeRange.Start = qry.TimeRange.Start`) after only checking `qry.Spine != nil && qry.Spine.TimeRange != nil` and that exactly one time-floor dimension exists. `qry.TimeRange` can be nil at this point: the aggregation adapter guards this (`FillMissing` requires a time range), but the `metrics` resolver decodes arbitrary properties straight into `metricsview.Query` (`resolvers/metrics.go:41-42`) and `Query.Validate` has no spine checks (`query.go:88-119`).
- **Failure scenario:** MCP/custom-API query `{dimensions: [{name: "t", compute: {time_floor: {dimension: "<ts>", grain: "day"}}}], measures: [...], spine: {time: {grain: "day"}}}` with no `time_range` (a plausible AI construction: "fill missing days") → nil-pointer panic inside `RewriteQueryTimeRanges` before any SQL is built.
- **Recommendation:** Return a clean error ("spine.time requires time_range") when `qry.TimeRange` is nil/zero before the copy.

### deep-sql-aggregation-07 [MEDIUM] DST-crossing period comparisons mis-join time buckets on DuckDB and Druid
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/ast.go:1504-1551` (`sqlForExpressionAdjustedByComparisonTimeRangeOffset`), `runtime/drivers/duckdb/dialect.go:102-109` (`DateDiff`/`IntervalSubtract`), same pattern in `druid/dialect.go:108-115`
- **Problem:** The comparison sub-select aligns its time-floor dimension to the base period by subtracting a *fixed* interval: `DATEDIFF(grain, base_start, comp_start)` grains, applied with `ts - INTERVAL (n) grain`. On DuckDB the truncated bucket is a naive-UTC `TIMESTAMP` (`timezone(tz, date_trunc(...))::TIMESTAMP`, `duckdb/dialect.go:91` — i.e. the UTC instant of local midnight) and the subtraction shifts the instant by exactly `n*24h`; Druid interval arithmetic is likewise fixed-width. When the base and comparison periods span a DST transition in the dashboard timezone, the local-midnight buckets are 23/25 hours apart, so the shifted comparison key differs from the base key by ±1h and the FULL JOIN on the dialect's null-safe equality (`astsql.go:273-283`) misses: the result shows the base bucket with NULL comparison values plus a phantom bucket (via the `COALESCE(base.ts, comparison.ts)` dim, `ast.go:936-939`) holding only comparison values. Under the default two-phase rewrite the damage is worse: the phase-1 `IN` filter is compiled against the comparison node's *adjusted* time expression (`executor_rewrite_two_phase_comparisons.go:164`), so mismatched buckets are excluded from the comparison side entirely. ClickHouse is likely unaffected because `DateTime64(tz) - INTERVAL n DAY` is calendar-aware in the column timezone (`clickhouse/dialect.go:137-148`; not exhaustively verified). The inline comment acknowledges the estimate is "best effort", but the user-visible effect is a broken comparison result, not an approximation.
- **Failure scenario:** Any comparison query grouped by a day-grain time-floor dimension with `timezone: America/New_York` whose base or comparison period spans Mar 8 2026 (aggregation API, canvas/AI comparison timeseries, pivots): post-transition days show NULL comparison values plus phantom rows; deltas and %-changes for those days are NULL or nonsensical.
- **Recommendation:** Perform the shift in local time before truncation (e.g. DuckDB: shift inside the `timezone(tz, …)` naive space, as the week/year `shift` variant at `duckdb/dialect.go:93` already does), or compute the comparison key as `date_trunc(tz, ts_shifted_by_calendar_offset)`. Add a DST-boundary comparison test per dialect.

### deep-sql-aggregation-08 [MEDIUM] Druid native search queries dimension *names* instead of physical columns (silently empty results)
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor.go:830-846` (`dims = append(dims, f.Name)` at `:844`), request built at `runtime/drivers/druid/native_query.go:151-174`
- **Problem:** `executeSearchInDruid` builds the native `search` query's `searchDimensions` from the metrics-view dimension *name* whenever the dimension has no `expression` — but the physical Druid column is `dim.Column`, which may differ from the name (`- name: campaign, column: campaign_name`). Druid returns zero hits for unknown dimensions rather than erroring. The virtual-column path (expression dims) handles this correctly; the plain-column path does not. Additionally, when the resolved time range has a zero `End` (a literal start-only range survives `RewriteQueryTimeRanges` half-open), the interval becomes `start/0001-01-01T00:00:00Z` (`native_query.go:169-171`), which matches nothing.
- **Failure scenario:** Metrics view on Druid declares `- name: campaign, column: campaign_name`. Dashboard search for "acme" returns no values for that dimension even though the SQL fallback path would find them — silent, per-dimension data loss in search.
- **Recommendation:** Use `dim.Column` (fall back to name) for `searchDimensions`, map results back to the dimension name, and fall back to the SQL path when `TimeRange.End` is zero.

### deep-sql-aggregation-09 [MEDIUM] ClickHouse computed-time-dim wrap corrupts CTE nodes (unknown-table SQL) when the CTE comparison rewrite is enabled
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_wrap_clickhouse_computed_time_dim.go:83` (`a.WrapSelect(n, …)` on a leaf) + `runtime/metricsview/ast.go:677-728` (`WrapSelect` does not reset `IsCTE`/`RawSelect` on the inner copy)
- **Problem:** With `rill.metrics.approximate_comparisons_cte: true` (off by default; built for high-cardinality Druid/CH deployments), `rewriteApproxComparisonNode` converts the base or comparison leaf into a CTE (`ConvertToCTE`, `ast.go:731-738`), leaving the node linked in the tree with `IsCTE=true` and registered in `a.CTEs`. The ClickHouse wrap then runs (`executor.go:404`), finds the CTE leaf has a computed time dimension (the walk does not check `IsCTE`, `:50-83`), and calls `WrapSelect` on it. `WrapSelect` copies the node (`cpy := *s`, `ast.go:678`) without clearing `cpy.IsCTE`, so the inner copy claims to be a CTE under a fresh alias `tN`. `writeSelect` then emits `WITH <cte> AS (SELECT … FROM tN)` — skipping the inner body because `FromSelect.IsCTE` is true (`astsql.go:148-157`), and `tN` is never defined since `a.CTEs` holds only the outer pointer — and the query fails with `UNKNOWN_TABLE tN`. (`WrapSelect` similarly fails to clear `RawSelect` on the outer node, which currently only makes wrapping inline-VALUES nodes a silent render no-op, `astsql.go:93-97` — harmless today.)
- **Failure scenario:** ClickHouse + `approximate_comparisons_cte` enabled + any comparison query grouped by a time-floor dimension (name == column, the normal case) with a single sort and no limit ≤ 250 two-phase takeover (e.g. a comparison timeseries with no limit) → hard SQL error on a mainstream dashboard shape for that configuration.
- **Recommendation:** In `WrapSelect`, reset `cpy.IsCTE = false` (transferring CTE-ness is the outer node's job since `a.CTEs` holds the outer pointer) and clear/carry `RawSelect` explicitly; alternatively make the CH wrap skip `IsCTE` nodes. Add a CH+CTE+time-dim SQL-generation test.

### deep-sql-aggregation-10 [MEDIUM] Interactive pivots stage an unbounded underlying result; the row cap only applies post-pivot
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor.go:346-353` (caps before pivot rewrite) + `executor_pivot.go:98-103` (limit moved to pivotAST, `qry.Limit = nil` at `:101`) + `:152-186` (staging before the column check)
- **Problem:** `rewriteQueryEnforceCaps` sets `limit = cap+1` on the query, then `rewriteQueryForPivot` moves that limit into the *post-pivot* `pivotAST.limit` and nils the underlying query's limit. The underlying query — whose row count is (kept-dim combinations × pivoted-dim combinations) — therefore runs with no LIMIT at all and is fully materialized into a temp table (`CREATE TEMPORARY TABLE … AS (…)`, `:158-165`) before `checkPivotColumns` even runs (`:184`; that check also queries the staged table, and only bounds *columns* — default `MetricsPivotExportColumnLimit` 15 000). `res.SetCap(rowsCap)` bounds only the final pivoted rows.
- **Perf impact:** An interactive pivot (Query path) without an explicit limit against a high-cardinality dimension stages an arbitrarily large result into DuckDB (disk + memory + transfer from the source OLAP) and only errors after the fact — the 10 000-row interactive cap provides no resource bound for exactly the query type most likely to explode. Even with a user limit, the underlying staged result is unbounded because the limit applies post-pivot. The UI always sends limits; the query API/MCP need not.
- **Recommendation:** Derive a row bound for the underlying query (e.g. `cap × max pivot column limit`, or run `checkPivotColumns` against the source before staging) and fail fast; at minimum add `LIMIT <hard bound>` plus an exceeded check on the staging SELECT.

### deep-sql-aggregation-11 [LOW] Druid exactify inner query keeps HAVING but drops its measures → hard error (flag-gated)
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_rewrite_druid_exactify.go:44` (`Having: qry.Having`) + `:56-62` (only the sort measure is added)
- **Problem:** With `rill.metrics.exactify_druid_topn` enabled, the inner exactify query copies the outer `Having` but includes only the sort measure (or none when sorting by the dimension). `NewAST`'s pseudo-HAVING compilation requires every referenced name to be in the node's fields (`astexpr.go:772-784`), so a HAVING that references any other measure fails AST construction, and `rewriteQueryDruidExactify` propagates the error (`:65-68`) — failing the entire query that would have succeeded without the flag. Sorting by the dimension with any measure-HAVING always fails.
- **Failure scenario:** Druid deployment with exactify enabled: leaderboard-shaped query (1 dim, 1 sort, limit ≤ 1000) sorted alphabetically with a measure filter expressed as HAVING → "druid exactify: failed to build inner query AST: … name … is not a dimension or measure available in the current context".
- **Recommendation:** Add HAVING-referenced measures to `inner.Measures` (they are cheap in the inner TopN), or skip exactify when `qry.Having` references measures outside the inner set.

### deep-sql-aggregation-12 [LOW] Two-phase comparisons double-apply OFFSET when approximate comparisons are disabled
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_rewrite_two_phase_comparisons.go:60` (`Offset: qry.Offset`); only `rewriteApproxComparisonsWalk` clears the root offset (`executor_rewrite_approx_comparisons.go:38-41`)
- **Problem:** Phase 1 consumes the offset (base query returns rows `[offset, offset+limit)`), but the rewrite never clears `ast.Root.Offset` (set from `Query.Offset` at `ast.go:361`). In the default config the subsequent approx rewrite clears it as a side effect (the offsets it pushes into the inline `RawSelect` node are ignored at render time, `astsql.go:93-97`, so the default path applies the offset exactly once). With `rill.metrics.approximate_comparisons: false` (while two-phase stays enabled at its default 250), nothing clears the root offset: `rewriteLimitsIntoSubqueries` bails on the FULL comparison join (`executor_rewrite_limit_pushdown.go:29-38`), and the emitted SQL applies `OFFSET` again over the already-offset inline rows, returning the wrong page (rows `[offset, limit)` of the already-paged result, usually near-empty). Related to (but distinct from) prior finding metricsview-01: this is the reachable variant of "offset applied in two places".
- **Recommendation:** Clear `ast.Root.Offset` (and the redundant root `Limit`) inside `rewriteTwoPhaseComparisons` itself instead of relying on the approx walk; add an offset test with approx disabled.

### deep-sql-aggregation-13 [LOW] Sub-day rollup eligibility skips the timezone check — fractional-offset timezones silently mis-bucket hourly rollups
- **Category:** correctness  **Confidence:** medium  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/executor/executor_rewrite_rollup.go:320-334` (tz match only for day+ grains), `:347-356` (start alignment only when start non-zero); `runtime/metricsview/executor/rollup_grain.go:96-105` (`timeAligned` sub-day cases contradict the `:87` doc comment "alignment is checked in UTC")
- **Problem:** Rollup eligibility skips the timezone-match check for sub-day grains entirely ("hour boundaries are the same everywhere", `:321`) — untrue for the fractional-offset zones (IST +5:30, Nepal +5:45, Chatham +12:45), whose hour boundaries fall at :30/:45 UTC. An hour-grain query in such a timezone can therefore be routed to an hourly rollup whose buckets are whole-hour aligned; re-truncating the rollup's bucket timestamps with `date_trunc('hour', …, 'Asia/Kolkata')` attributes each 60-minute UTC bucket wholly to one half-shifted IST hour — silently wrong hourly aggregates versus the base table, with range edges dropping/gaining half-buckets. The `timeAligned` start-alignment gate does not reliably block this: (a) it is skipped entirely when the query has no time range or a zero start (`:347`), and (b) it checks sub-day alignment in the timestamp's *own* location rather than UTC (`rollup_grain.go:104-105`, contradicting its own doc comment) — mostly neutralized because rilltime returns UTC-located times (`rilltime/rilltime.go:425`) and proto timestamps arrive UTC via `AsTime()`, but JSON-decoded literal starts preserve their offset (`mapstructureutil` uses `StringToTimeHookFunc`), so `"2026-07-01T00:00:00+05:30"` passes the hour gate while being 18:30 UTC.
- **Failure scenario:** Hourly rollup + `metrics` resolver query with an hour time-floor in `Asia/Kolkata` and either no time range or an offset-bearing literal start → served from the rollup with each hourly value composed of the wrong half-hours; the same query against the base table returns different numbers.
- **Recommendation:** For sub-day grains, reject rollups when the query timezone has a non-whole-hour offset (cheap check via `Zone()` offset % 3600), and convert to UTC in the sub-day `timeAligned` branches (matching the comment).

### deep-sql-aggregation-14 [LOW] Multi-grain comparison adjustment rebuilds the time expression from the dimension *name*, ignoring column/expression
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/ast.go:1535` (`tc := a.Dialect.EscapeIdentifier(timeDim)` in the `g != mg` branch)
- **Problem:** When a comparison query floors the time dimension at two different grains (pivot-style, e.g. year+month), the coarser grain's comparison expression is rebuilt from scratch using `EscapeIdentifier(timeDim)` — the dimension *name* — instead of `MetricsViewDimensionExpression` (which resolves `column:`/`expression:`). For a time dimension declared with a differing column or an expression, the generated comparison sub-select references a non-existent column (SQL error) or, worse, a same-named unrelated column (wrong data). The single-grain path (`g == mg`, `:1520-1525` and `:1550`) correctly adjusts the already-resolved `f.Expr`.
- **Failure scenario:** Metrics view with `timeseries: event_time` declared as a dimension `- name: event_time, expression: CAST(ts_ms/1000 AS TIMESTAMP)`; pivot with year+month time dims and comparison enabled → comparison sub-select emits `date_trunc('year', ("event_time" - INTERVAL …))` where `event_time` is not a physical column.
- **Recommendation:** Resolve the dimension via `LookupDimension` + `MetricsViewDimensionExpression` before applying `IntervalSubtract` in the `g != mg` branch.

### deep-sql-aggregation-15 [LOW] NIN on unnest dimensions via array-contains excludes NULL-array rows, inconsistent with scalar NIN
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/metricsview/astexpr.go:662-702` (`writeArrayContainsCondition`), contrast `:644-655` (scalar NIN adds `OR … IS NULL`)
- **Problem:** For DuckDB/ClickHouse unnest dimensions not included in the query's dimension list, IN/NIN compiles to `[NOT] list_has_any(col, [...])`/`hasAny` (`:282-284`). For NIN, rows where the array itself is NULL evaluate `NOT NULL → NULL` and are excluded — while every scalar NOT-IN/NOT-ILIKE path deliberately appends `OR col IS NULL` to include NULLs (`:644-655`, `:505-517`). The in-code comment (`:689-690`) discusses NULL *elements* but not the NULL-array row case, which is fixable (`OR col IS NULL` on the array column is well-defined).
- **Failure scenario:** Excluding value "x" on a list-typed dimension silently also removes all rows whose list is NULL from every other leaderboard/total, diverging from the exclude semantics everywhere else in the product.
- **Recommendation:** For the `not` branch, emit `(NOT list_has_any(col, […]) OR col IS NULL)`.

### deep-sql-aggregation-16 [MEDIUM] Pre-bound timestamps never carry `Now` — `now`-anchored rill-time expressions silently return empty results on the metrics-resolver/MCP paths
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/resolvers/metricsview_time_range.go:193-253` and `runtime/queries/metricsview_aggregation.go:230-284` (`resolveTimestampResult`/`ResolveTimestampResult` populate Min/Max/Watermark/Rollups but never `Now`); `runtime/metricsview/executor/executor.go:178-180` (`Timestamps` cache hit returns the bound value verbatim; `res.Now = time.Now()` at `:206` runs only on the probe path), `:258-270` (`BindQuery`); consumed at `executor_rewrite_time.go:95-102`
- **Problem:** The `metrics` resolver *always* pre-binds timestamps when the metrics view has a time dimension (`resolvers/metrics.go:139-153`), and the aggregation/timeseries adapters pre-bind when rollups are configured (`metricsview_aggregation.go:106-116`). The bound `TimestampsResult` has `Now == time.Time{}`. When the query's time range uses a rill-time `expression`, `ResolveTimeRange` evaluates it with `Now: ts.Now` (`executor_rewrite_time.go:95-102`). In rilltime, `ref` — the default anchor for every *new-format* expression without an explicit `as of` (e.g. `7d`, `-30d`, `-2d to now`, `now/d`) — defaults to `EvalOptions.Now` (`rilltime/rilltime.go:402-404`); only legacy ISO durations get an automatic `as of watermark` override (`:311-319`). With a zero `Now`, the range evaluates to year 0001 and the emitted SQL (`ts >= $1 AND ts < $2` with year-1 bounds) silently returns zero rows. Alerts/reports are unaffected because they pass `execution_time`, which overwrites `ts.Now` (`executor_rewrite_time.go:79-84`); legacy ISO presets (`PT24H`, `P7D`) and watermark-anchored shorthands (`TD`, `MTD`, …) are also unaffected — which is why this has gone unnoticed since the binding was introduced (#6413, Jan 2025).
- **Failure scenario:** MCP `query_metrics_view` (routes to the `metrics` resolver with no execution time, `runtime/ai/metrics_view_query.go:264-269`) or a custom `type: metrics` API with `time_range: {expression: "7d"}` → empty result, no error; the AI then reports "no data in the last 7 days" against a table full of data. Same for `now`-anchored expressions in canvas YAML when evaluated server-side.
- **Recommendation:** Set `Now: time.Now()` in `resolveTimestampResult`/`ResolveTimestampResult` (or default `ts.Now` to `time.Now()` at the `Eval` call sites when zero). Add a metrics-resolver test with a new-format `now`-anchored expression over a bound executor.

## Performance Notes
Ranked latency/cost contributors observed on the hot path (with the fix that addresses each):

1. **Delta/ratio-sorted comparison queries run the worst possible shape**: both `rewriteTwoPhaseComparisons` (sort-compute check, `:42-44`) and `rewriteApproxComparisonNode` (`sortDelta → return false`, `:171-173`) bail, leaving a FULL OUTER JOIN of two *unlimited* GROUP BYs over base and comparison ranges (`rewriteLimitsIntoSubqueries` also bails on FULL joins, `executor_rewrite_limit_pushdown.go:29-38`). On a 1M-cardinality dimension this is easily 10-100× the cost of the base-sorted variant (which gets LEFT JOIN + limit pushdown). This is the single biggest interactive cost cliff users can trigger with one click (sort by Δ). Fix: approximate delta sort via top-K union of both sides (already listed as a feature idea in the prior audit; re-ranked here as the top perf item).
2. **`percent_of_total` adds one full-scan aggregate round-trip per query** (`executor_rewrite_percent_of_totals.go:66-75`) and — because it runs *before* rollup routing and builds its AST directly against `e.metricsView` (`:49`) — the totals query **never uses rollup tables**, even when the totals-only shape (no dimensions, plain measures) is exactly what rollups accelerate best. (The `rewriteQueryDruidExactify` call at `:56` mutates `totalsQry` *after* the AST was built and is dead code besides — exactify always skips the zero-dimension shape.) Fix: route the totals query through `rewriteQueryForRollup`, or compute pct-of-total with `SUM(m) OVER ()` where supported (also fixes metricsview-06/09).
3. **Interactive pivot staging is unbounded** (finding 10): full underlying materialization into a DuckDB temp table + a `COUNT(DISTINCT …)` scan over it + PIVOT + Parquet write + DuckDB re-read (`executor.go:426-474`). For non-DuckDB OLAPs, add one full Parquet export hop on top.
4. **Timestamps probing**: every executor resolving a relative time range pays one `min/max/watermark` aggregation per (executor, time-dim) — on Druid this is 2-3 *separate parallel queries* (`executor_timestamps.go:191-320`). Mitigations already present: per-executor memoization, `BindQuery` pre-binding from the `metrics_time_range` resolver (cached), and `data_time_range` declarations that skip the probe entirely; ensure new call sites always pre-bind (the aggregation `Export` path binds unconditionally — see prior queries-11 for the redundant probe on non-rollup views). Note finding 16: the pre-bound result must also carry `Now`.
5. **Druid search fallback**: when a WHERE exists, the native-search path first runs `EXPLAIN PLAN FOR SELECT 1 …` as an extra round-trip to translate the filter (`executor.go:779-821`); a failed translation then falls back to the full UNION-ALL SQL search, tripling round-trips for complex-filtered searches.
6. **Two-phase comparisons cost 2 round-trips by design** but bound the comparison side with a ≤250-value IN list — a good trade. The inline `VALUES`/`UNION ALL SELECT` (base dialect, `dialect.go:318-366`) grows one SELECT per row × columns; at the 250-row default cap this is fine, but raising `MetricsApproxComparisonTwoPhaseLimit` significantly would produce multi-thousand-parameter statements (ClickHouse/Druid parser cost).
7. **Druid exactify** (opt-in) doubles round-trips for TopN-shaped queries by design; combined with finding 11 it should also skip when it cannot represent the query.
