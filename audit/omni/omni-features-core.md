# Omni Analytics — Modeling, Querying, Connections & Developer Workflow Inventory

Sources: docs.omni.co sitemap (1,091 pages enumerated), raw markdown fetched per page (Mintlify `.md` endpoints), verified 2026-08.

## 1. Data Modeling / Semantic Layer

### Layered model architecture — MAJOR PILLAR
- **Three-layer model**: (1) **schema model** auto-generated to mirror the database; (2) **shared model** — the governed, virtualized org-wide model ("model extension"); (3) **workbook model** — per-workbook extension of the shared model for ad hoc logic. Branches act as a fourth layer between shared and workbook when in branch mode.
- **Just-in-time modeling / promotion** — MAJOR PILLAR. Changes made in a workbook (fields, joins, topics, calculations) can be reviewed in a "workbook model changes" drawer (Summary + YAML diff tabs), selectively checked, and **promoted to the shared model** with one click. Excel calculations can be promoted to modeled fields. "Remove unused" cleans unreferenced workbook-layer objects. Direct IDE edits publish to the shared model on save.
- **Model generation** — MAJOR. Connecting a database auto-generates the model: views for every table, dimensions for every column, inferred primary keys, and auto-inferred join relationships (via column-name matching heuristics and, on Postgres/Snowflake, foreign-key constraints; configurable per connection: Both / FK only / column names only / None).
- **Browse modes** (minor): IDE shows Combined (all layers merged) vs Model (extension only) modes; in branches: Staged / Merged / Combined / Fully Resolved views.

### Topics — MAJOR PILLAR
- Curated datasets defined per model: a base view + a tree of joins, field curation, metadata. All AI/natural-language querying is required to go through topics. Built visually in workbooks (topic editor with join diagram) or as YAML in the model IDE; can also be auto-created from CSV/XLSX uploads.
- Topic parameters (full list): `access_filters` (row-level security via user attributes, with `values_for_unfiltered` and SQL LIKE wildcards), `ai_context`, `ai_fields`, `always_having_filters`/`always_having_sql`, `always_where_filters`/`always_where_sql`, `auto_run`, `base_view`, `base_view_label`, `cache_policy`, `default_filters`, `default_row_limit`, `description`, `display_order`, `extends` (topic inheritance), `fields` (include/exclude directives), `group_label`, `hidden`, `joins` (nested join tree, topic-scoped joins), `label`, `owners`, `relationships` (topic-scoped relationship overrides), `required_access_grants`, `sample_queries`, `skills`, `tags`, `template`, `views` (topic-scoped view/field customization), `warehouse_override`.
- **Composite topics (beta)** — MAJOR (new). Multi-fact analysis: combine 2+ topics into one result set; each topic aggregates in its own subquery, stitched with FULL OUTER JOIN on declared `shared_dimensions`/`shared_views` (CROSS JOIN if none selected); `shared_measures` computed post-join; correct grain per fact, no fan-out. Params: `topics`, `shared_dimensions` (with per-topic `mappings`), `shared_measures`, `shared_views`, `default_filters`, `always_join_all_topics`, `fields`, `label`, `description`, `sample_queries`.

### Views — MAJOR
- Views = virtualized representations of DB tables; auto-generated; every field belongs to a view. Parameters: `ai_context`, `aliases`, `catalog`, `custom_compound_primary_key_sql`, `default_drill_fields`, `default_drill_query`, `description`, `display_order`, `extends`, `fill_fields`, `folder`, `hidden`, `ignored`, `label`, `materialized_query` (aggregate awareness), `name`, `query`, `renamed_from`, `required_access_grants`, `schema`, `schema_label`, `sql`, `table_name`, `tags`, `template`, `uploaded_table_name`.
- **View aliasing** (minor): reference a view by additional names — handles table renames and duplicate views for self-joins.
- **Query views** — MAJOR. Workbook queries saved as reusable views (`.query.view` files), compiled as CTEs at query time. Two flavors: point-and-click (`query:` param) and SQL-backed (`sql:` param). Parameters include `base_view`, `bind`, `bind_all_filters` (pushes outer-query filters into the inner query when a join path exists), `bind_outer_context`, `calculations`, `default_group_by`, `dimensions`/`measures`, `fields`, `fill_fields`, `filters`, `join_via_map`, `limit`, `sorts`, `topic`, `schema`, `hidden`, `ignored`. Promotable to shared model.

### Dimensions — MAJOR
- Attributes per row; typed implicitly from SQL/dialect. Parameter list: `ai_context`, `aliases`, `all_values`, `bin_boundaries`, `colors`, `convert_tz`, `custom_primary_key_sql_for_quick_aggs`, `description`, `display_order`, `drill_fields`, `duration` (time-between-timestamps fields with multiple intervals), `dynamic_top_n`, `extends`, `faceting`, `filter_single_select_only`, `format`, `group_label`, `groups`, `hidden`, `ignore_from_extended`, `ignored`, `label`, `level_of_detail`, `links`, `markdown`, `mask_unless_access_grants` (column masking), `order_by_field`, `parent_field`, `primary_key`, `required_access_grants`, `sample_values`, `skip_parent_label`, `sql`, `suggest_from_field`, `suggest_from_topic`, `suggestion_list`, `synonyms`, `tags`, `timeframes`, `view_label`.
- **Timeframes** (major sub-feature): date fields expand to grains — raw, date, week, month, quarter, year, day_of_month/quarter/week_name/week_num/year, hour, hour_of_day, minute, second, millisecond, month_name/num, quarter_of_year, fiscal_quarter/fiscal_year (with `fiscal_month_offset`). Referenced as `field[timeframe]`.
- **Level-of-Detail (LoD) fields** — MAJOR: `level_of_detail` with `aggregate_type` + grouping strategy (`fixed`, `always_include`, `always_exclude`), optional filters and `custom_primary_key_sql`; compiles to a joined subquery (Tableau-LOD-style). Creatable in workbook UI or YAML.
- **JSON field parsing** (minor): right-click a result cell → "Create fields from JSON" auto-creates fields from JSON/stringified JSON.
- **Field-value masking via user attributes** (minor): `{{omni_attributes.x}}` inside dimension SQL for conditional masking/hashing.

### Measures — MAJOR
- Defined via `aggregate_type` (sum, count, count_distinct, average, min, max, median, list, percentile, sum_distinct_on, average_distinct_on, median_distinct_on, percentile_distinct_on) or raw SQL aggregate. Parameters: `aggregate_type`, `ai_context`, `aliases`, `all_values`, `colors`, `custom_primary_key_sql`, `description`, `display_order`, `drill_fields`, `drill_queries`, `filters` (filtered measures), `format`, `group_label`, `hidden`, `ignored`, `label`, `level_of_detail`, `links`, `markdown`, `required_access_grants`, `required_fields`, `sample_values`, `sql`, `suggest_from_field`, `suggestion_list`, `synonyms`, `tags`, `view_label`.
- **Symmetric aggregates** — MAJOR: automatic fan-out protection on joins using primary keys + relationship types; `sum_distinct_on`/`custom_primary_key_sql` for pre-joined/materialized tables; `custom_primary_key_sql_for_quick_aggs` for unnested-array fan-out.

### Relationships/joins — MAJOR
- Central `relationships.yml`: `join_from_view`, `join_from_view_as`(+label), `join_to_view`(+as/as_label), `join_type` (e.g., `always_left`, inner, full outer), `on_sql`, `where_sql`, `relationship_type` (one_to_one, many_to_one, one_to_many, assumed_many_to_one...), `reversible` (allows fan-out joins to be exposed), `id`. Topic-scoped joins override/extend global ones. Auto-inference at model creation/refresh (column names and/or FK constraints). UI join builder with "infer relationship" for unknown cardinality.

### Model file settings — MAJOR (breadth)
Full model-file parameter list: `access_grants`, `ai_chat_topics`, `ai_context`, `ai_settings` (allow_ctes, allow_custom_fields, analyze/build/simple-summarize configuration, conversation_prune_length, disabled_tools, query_all_views_and_fields, validate_analysis), `auto_run`, `auto_run_dashboard`, `cache_policies`, `calcs_default_pushdown`, `compute_routing`, `constants` (reusable `@{name}` strings, resolved pre-template), `custom_formats`, `default_cache_policy`, `default_group_by`, `default_numeric_locale`, `default_row_limit`, `default_timeframes`, `default_topic_access_filters`, `default_topic_required_access_grants`, `dynamic_schemas`, `dynamic_shared_extensions`, `extends` (model inheritance / hub-and-spoke), `facet_workbook_filters`, `fiscal_month_offset`, `format_values`, `ignored_schemas`, `ignored_views`, `included_schemas`, `included_views`, `sample_queries`, `sets` (named field lists, `[set:name]` references), `skills` (packaged AI workflows), `slot_reservation`, `sql_preamble`, `template` (abstract models), `topic_group_descriptions`, `topics` (inline), `warehouse_override`, `week_start_day`.

### Filters (model YAML) — MAJOR
- LookML-like filter syntax used across topics (`default_filters`, `always_where_filters`, `always_having_filters`), query views, and measures. Operator set: `is`, `not`, `and`, `or`, `contains`, `starts_with`, `ends_with`, `sql_like`, `case_insensitive`, `less_than(_or_equal_to)`, `greater_than(_or_equal_to)`, `between`, `between_dates`, `before`, `on_or_after`, `day_of_week/month/quarter/year`, `hour_of_day`, `month_of_year`, `quarter_of_year`, `time_for_duration`, `date_offset_from_query`, `field_name_in_query` / `field_name_not_in_query` (filter-by-another-query), `cancel_query_filter`; `not_` prefix negation.
- **Templated filters** — MAJOR: Mustache parameterization of SQL (`{{# view.field.filter }} col {{/ ... }}`), default values via `{{^ }}`, filter-only fields (`filters:` block in views), dynamic-granularity timeframe switchers, parameterized WHERE clauses in SQL views, custom SQL filters wired to dashboard filters. User attributes injectable via `{{ omni_attributes.* }}`.

### Access control in the model — MAJOR
- `access_grants` (user-attribute-gated), `required_access_grants` on topics/fields/views, `default_topic_required_access_grants`, `access_filters` (row-level security), `mask_unless_access_grants` (column-level), Omni system attributes (e.g., `omni_user_groups`, `omni_is_org_admin`) usable in grants.

### Model IDE & development tooling — MAJOR
- **Model IDE**: file-tree of model/topic/view/relationship YAML files; strict validation (invalid YAML/params rejected on save); broken-reference pointers after schema changes; in-IDE **Modeling Agent** (AI chat that drafts YAML edits); "Go to definition" from workbook fields.
- **Branch Mode** — MAJOR: model + content branches; middle ground between drafts and full git; branch-aware browse modes; branches auto-rebase on merges of other branches.
- **Content Validator** — MAJOR: validates all dashboards/workbooks against the model; finds broken field/view/topic references after renames/deletions; bulk find-and-replace across content; usage/discovery search ("what references this field"); also exposed via API.
- **Model version history** (minor-major): chronological model change history with diffs and one-click restore; per-file history with author info (details >6 months old not viewable).
- **Table migration tool** (minor): swap table references model-wide when DB tables are renamed (`renamed_from` param) or soft-delete (`ignored: true`).
- **Schema refreshes** — MAJOR: hard (full, incl. deletions) vs soft (additive-only, can target specific schemas/tables with wildcards); manual (IDE/connection settings/API), scheduled (schema refresh schedules API/CLI), or branch-based (refreshes land in a branch requiring PR); orchestration-triggered via Refresh Schema API after `dbt run`.
- **Shared extension models** — MAJOR: child models inheriting a parent's joins/topics/metrics with per-child overrides; `dynamic_shared_extensions` routes users to extensions by user attribute (manual `mappings` or `map_pattern`); used for multi-tenancy and departmental models; extension branches for isolated development; "Allow exploration" toggle.
- **Local development CLI (beta)** (minor-major): `@omni-co/model-local-editor` npm CLI syncs model YAML to local filesystem in real time (edit in VS Code etc., auto-push to an Omni branch). Requires API key; works with branches.
- **Export to dbt** (minor): export a view file's dbt SQL to push virtualized fields down into dbt.

## 2. Querying & Analysis

### Workbooks — MAJOR PILLAR
- Multi-tab analysis environment; tabs can be: point-and-click query tabs, SQL tabs, spreadsheet tabs, blank data-input tables, cross-model tabs. View/edit(draft) states with autosave, versions, "Explore from Here" copies; AI-suggested titles/descriptions on save.
- **Point-and-click querying** — MAJOR: field picker with dimensions/measures per view; filters, sorts, pivots (with flatten-pivot → auto filtered measures + "Other" bucket), quick aggregates (count distinct/sum/avg/min/max/list, count true/false), quick timeframes, row limit up to 50,000 with pagination; field search with operators (`data_type:`, `is:`, `model_type:`, `schema:`, `tag:`); field verification indicators distinguishing workbook-only vs shared-model fields.
- **Custom fields** (major): ad hoc dimensions/measures in SQL with `${view.field}` substitution and chaining; bins (numeric), groups (string grouplets + remaining bucket), **Top N fields** (rank dimension by measure, keep N, group rest into "Other", dashboard-controllable N), duration fields, filtered measures (from edit, from pivot cell right-click, or flatten-pivot).
- **Filters (workbook)** — MAJOR: type-aware filter UIs; absolute + relative date grammar (`after 7 complete days ago`, `[2023][10 days]` interval-duration form, units ms→year); multi-value with comma/escape; multi-condition per field (All/Any); **multi-field OR filter groups**; **filter by another query** (`WHERE IN (SELECT ...)`, also "is not from another query"); filter suggestions (distinct-value queries capped at 2,000 rows, topic-scoped, faceted by other filters, cached ~30 days); "Filters from dashboard" quick-add.
- **Filtering/AI extras** (minor): quick calculations (% of total, running total, rank, % of previous...), period-over-period comparisons (query-structure support).
- **Cross-model tabs (beta)** (minor-major): a tab querying a *different* shared model/connection within the same workbook; dashboards can mix tiles from multiple models/connections. Point-and-click only.
- **Workbook inspector** (major): shows dialect SQL, query structure (Omni's query IR in JSON/YAML), vis config, and full AI message transcript (system prompt/context/tool calls); copy buttons produce topic `sample_queries` YAML; the query JSON is exactly what the Run Query API accepts.

### Table calculations (Excel-style) — MAJOR PILLAR
- Post-query, spreadsheet-semantics calcs with `=FORMULA` syntax, cell (`C2`), column (`users.count`), and range (`B:B`) references; created via quick calcs, AI prompt ("write formula in natural language" + suggestions), or manually.
- Function library (~120 functions, Google-Sheets-compatible where possible): Math/number (SUM, SUMIF(S), SUMPRODUCT, AVERAGE, AVERAGEIFS, COUNT(A/IF/IFS), MIN/MAX(IFS), MEDIAN, MODE, STDEV, VAR, CORREL, COVAR, SLOPE, INTERCEPT, RANK, LARGE, SMALL, ROUND(UP/DOWN), CEILING, FLOOR, INT, TRUNC, ABS, SQRT, EXP, LN, LOG, LOG10, MOD, RAND, trig...); Text (CONCAT(ENATE), LEFT/RIGHT/MID, LEN, FIND, SEARCH, SUBSTITUTE, REPLACE, TRIM, CLEAN, UPPER/LOWER/PROPER, TEXT, VALUE, EXACT, CHAR, T); Logic (IF, IFS, IFERROR, IFNA, SWITCH, AND, OR, NOT, ISBLANK, ISNUMBER, BITAND/OR/XOR/RSHIFT); Date/time (NOW, TODAY, DATE, DATEDIF, DAYS, DAY/MONTH/YEAR, HOUR/MINUTE/SECOND, EOMONTH, WEEKDAY, WEEKNUM, NETWORKDAYS); Position/lookup (**XLOOKUP**, VLOOKUP, INDEX, MATCH, ROW, PIVOT, PIVOTINDEX, PIVOTOFFSET, PIVOTROW); **AI functions** (AI_CLASSIFY, AI_COMPLETE, AI_EXTRACT, AI_SENTIMENT, AI_SUMMARIZE — run via warehouse AI functions). XLOOKUP works across query tabs (cross-query lookups).
- **Calculation pushdown** (minor-major): range-referencing calcs (`=SUM(B:B)`) can be evaluated **before** the row limit against the full dataset; per-column toggle ("Apply before/after row limit"); model default via `calcs_default_pushdown`.
- Calcs can be promoted into the workbook model / shared model.

### Spreadsheet tabs — MAJOR
- Full Excel-like spreadsheet embedded as a workbook tab, connected to live query results (protected auto-updating sheets per connected query); import XLSX preserving formatting/formulas/references; CSV import; manual entry. Limitations: spreadsheet data can't feed other queries or be promoted; no in-sheet pivot tables/charts; formulas mostly Excel-compatible.

### Data input — MAJOR (differentiator)
- **CSV/XLSX uploads (data input tables)**: upload or hand-enter tables (≤500k rows) in a workbook; optionally written back to a dedicated "table upload schema" in the warehouse, enabling joins; auto topic creation option.
- **Input columns (beta)**: editable columns added to any query result (Text/Number/Boolean), keyed on chosen dimensions, persisted via writeback to the connection's scratch schema and auto-joined back; editable on live dashboards ("Published" edit mode); access-filter fields forced into the mapping key for RLS safety. Use cases: triage, scoring, annotations, forecast overrides.

### SQL — MAJOR PILLAR
- **Omni SQL layer**: every UI query generates two SQL layers — Omni SQL (with helper functions like `OMNI_SUM`, `OMNI_DATE`, `OMNI_DAY_OF_WEEK`, `OMNI_PERCENT_OF_TOTAL`, `OMNI_RUNNING_TOTAL`, `OMNI_OFFSET`, `OMNI_RANK`, `OMNI_PIVOT`/`OMNI_PIVOT_ROW`, etc.) and dialect SQL actually executed (copy-pasteable into any IDE).
- **Bidirectional SQL↔UI** — MAJOR: the Omni SQL is editable ("Advanced Editor"); edits are parsed back into the model — unmatched expressions become **tab-only fields** (query-model layer) which can be promoted to workbook → shared model, or saved as a query view. UI state stays in sync with SQL as you click.
- **SQL tabs**: raw SQL IDE in dialect SQL; bypasses the model; full viz/dashboard/download features still available; parsed snippets surfaced as promotable fields.
- **Custom SQL filters**: templated-filter syntax inside raw SQL maps SQL tiles to dashboard filters.
- **`${view.field}` substitution operator** usable in SQL and custom fields for model-aware references.

### Performance / caching — MAJOR PILLAR
- **Query result cache**: exact-match result cache shared across users, default 6h TTL, configurable 0s–30d via `cache_policies` / `default_cache_policy` at model, topic (`cache_policy`), and dashboard level; `filter_suggestions_must_obey_policy` option (suggestions default 30d); ad hoc bypass (Run w/o Cache, Refresh Data); **cache warming** via scheduled deliveries (scheduler always bypasses and repopulates cache); **Reset cache API** for post-ETL invalidation.
- **Requeryable cache (in-browser)**: last ~30 result sets kept client-side; re-sorts, sub-filters, regrouping, and pivots re-executed in the browser when the result set was complete — enables "instant" dashboard slice-and-dice; pattern of building filter-permutation "cube" tiles for pseudo-instant dashboards.
- **Aggregate awareness** — MAJOR: register warehouse rollup tables (built in dbt or elsewhere) with `materialized_query` (`fields` mapping with timeframe qualifiers like `created_at[date]`, `base_view`); Omni transparently rewrites queries to the smallest sufficient aggregate, including across topic joins when join keys are mapped; falls back to base tables otherwise; supports **sketch-based approximate aggregates** (Snowflake HLL/APPROX_PERCENTILE/APPROX_TOP_K/MINHASH; BigQuery HLL_COUNT; Databricks HLL_SKETCH) rolled up from finer to coarser grains; SQL inspector shows the rewrite.
- **Compute routing** — MAJOR (Snowflake/Databricks/BigQuery only): `compute_routing` maps job types (workbook, dashboard, scheduled, export_download, api_run, suggestions, agentic) to warehouses or BQ slot reservations; `warehouse_override` (Snowflake/Databricks, workbook-model-only), `slot_reservation` (BigQuery), `sql_preamble` (session setup SQL with user-attribute injection) with documented resolution precedence.
- **Offloaded schemas** (minor): lazy-load metadata for large/infrequent schemas (wildcards, exclusions) — recommended for dbt virtual schemas.
- Row limits: default 1,000 (model/topic-configurable), UI max 50,000; API max 75,000 (or unlimited with `null`).

## 3. Data Connections / Databases

### Supported databases (complete list) — MAJOR
Amazon Athena; Amazon Redshift; ClickHouse; Databricks; Exasol; Google BigQuery (service account + key, or Workload Identity Federation); MariaDB; Microsoft SQL Server; MotherDuck; MySQL; PostgreSQL; Snowflake; Starburst Galaxy (Trino connector); StarRocks. (14 engines.)
- **Quick connect** (minor): paste a connection URI for most engines (Redshift, ClickHouse, Databricks, Exasol, MariaDB, MSSQL, MySQL, Postgres, Snowflake, StarRocks).

### Connection features
- **Networking**: SSH tunnels; AWS PrivateLink (cross-region); Redshift-managed VPC PrivateLink; Azure PrivateLink; Snowflake PrivateLink (AWS/Azure); Databricks PrivateLink; published Omni IP addresses.
- **Database OAuth** (minor-major): per-user OAuth to Snowflake (native, external Okta, external Entra) and Databricks — per-user credentials/RBAC passthrough (also see enforce-database-RBAC guide). Snowflake OAuth connections can use each user's `DEFAULT_WAREHOUSE` for per-user warehouse routing/cost attribution.
- **Schema restriction** (minor): limit included schemas per connection; `included_schemas`/`ignored_schemas`/`included_views`/`ignored_views` in model.
- **Table upload / scratch schema** (minor): dedicated writeback schema for CSV uploads and input columns.
- **View name generation** (minor): control catalog/schema prefixes in generated view names.
- **Timezone handling** — MAJOR: per-connection **Database timezone** (source, default UTC) and **Query timezone** (target, default "do not convert"); conversion applied in generated SQL only; **Allow user-specific timezones** (per-user profile query timezone); **per-page timezone override** picker on dashboards/workbooks; resolution priority: page override → user profile → connection query tz → UTC; Snowflake `timestamp_tz` special handling; per-field opt-out via `convert_tz: false`.
- **Dynamic connection environments** — MAJOR: register secondary connections as environments of a primary; switch environment inside a branch (dev-DB testing), or route users automatically by **user attribute** (multi-tenant DB-per-customer); schemas must be near-identical (schema model swaps, shared model constant).
- **User-selected environments** — MAJOR (new): end users pick the environment per model via File > Connection; access granted per environment to users/groups; resolution order: branch selection → user selection → user-attribute assignment → base connection; schedules can pin an environment (runs as owner).
- **Dynamic schemas** (major for embed): `dynamic_schemas` model param creates a virtual schema whose physical schema is resolved per user attribute (`schema-per-tenant` partitioning).
- **Snowflake semantic views integration** (minor-major, new): import Snowflake semantic views (dimensions + measures preserved, one folder per semantic view) and query them in Omni; governance stays in Snowflake grants; agent skill can also convert an Omni topic → Snowflake Semantic View.
- **Databricks Unity Catalog integration** (minor): listed in connect-data docs (metadata integration).
- **Archive/restore connections**, connection troubleshooting (minor).
- **Snowflake specifics**: password/key-pair/PAT/OAuth auth, warehouse selection + per-user default warehouse (OAuth), upload schema, PrivateLink, FK-based relationship inference, `timestamp_tz` handling, HLL/approx sketch rollups, warehouse_override/compute_routing.
- **BigQuery specifics**: service-account key or workload identity federation; slot `slot_reservation` + compute_routing to reservations; upload dataset; HLL_COUNT sketch rollups (warning: MERGE vs MERGE_PARTIAL).
- **Redshift specifics**: datashare-backed external schemas supported (with pre-granting caveats), Redshift-managed VPC PrivateLink.

## 4. Developer Workflow

### Git integration — MAJOR PILLAR
- Sync a shared model to a git repo (model-level). Providers: **GitHub, GitLab, Azure DevOps, Bitbucket Cloud, Bitbucket Data Center** (SSH deploy keys or HTTPS tokens; webhooks; custom web URL for tunneled repos). Multiple models can share one repo (shared deploy key/webhook). Model path configurable (`omni/<model>` default).
- Settings: base branch, **Pull request required** (all model changes via PR), **Require for system syncs** (schema refreshes/API syncs also via PR; needs branch-based schema refresh), **Always create branches** (mirror repo PRs as Omni branches), provider override, token rotation, test connection, unlink.
- Enabling git forces Branch Mode for shared-model modifications. Branches auto-rebase on merge of others.
- **Git follower mode** — MAJOR: leader/follower model replication via git — leader is where development happens; followers are read-only and updated by merging leader base branch → follower base branch. Use cases: permanent dev→prod SDLC; multi-region/multi-org deployment (followers can live in different connections or organizations).
- Deployment patterns (guides): single instance + git/dbt; single instance + dynamic connections; multi-instance prod/stage (follower); multi-instance multi-region; scaled deployments with shared model extensions; single-instance dynamic connections for embed.

### dbt integration — MAJOR PILLAR (bi-directional)
- Supports **dbt Core and dbt Cloud**; one dbt project per Omni connection; Omni compiles the dbt project itself (runs the dbt compiler, honors `generate_schema_name`/`generate_database_name` macros) to build the manifest.
- **Bottom-up (dbt → Omni)**: dbt sync pulls model metadata (descriptions, tests, tags — see metadata reference) into matching Omni views; schema refresh = structural sync + dbt sync; view upstream dbt dependencies in Omni; dbt IDE (read-only project browser) inside the model IDE.
- **dbt environments**: mirror `profiles.yml` outputs / dbt Cloud environments; production auto-created; personal (per-developer) and shared environments; managed via UI, API, or CLI; per-branch environment + git-branch selection for syncs.
- **Virtual schemas** — MAJOR: content/topics point at a *dbt environment* rather than a physical schema, so switching environments (prod ↔ personal dev build) doesn't rewrite content; enables previewing dbt changes against real dashboards in a branch.
- **Top-down (Omni → dbt)**: **Convert to dbt model** (workbook query → dbt SQL with Jinja `ref()`s), run/compile dbt SQL with Jinja in Omni, **Push to dbt repo** (branch + commit message + diff viewer + PR creation); edit existing dbt models in a workbook and push back; permission-gated.
- **dbt semantic layer (MetricFlow) import**: one-way import of dimensions, entities, measures, metrics into the Omni model (enable per connection + schema refresh). Not supported: cumulative/conversion metrics, null filling, `agg_time_dimension`, time spines (Omni uses date fill instead); ratio metrics computed via joins + symmetric aggregates.
- **Exposures**: generate dbt exposure YAML from published dashboards (name, URL, dependent models, owner) into `models/omni_exposures/`; manual push or automated via Get dbt exposures API; requires `${...}` model references for dependency mapping.
- Debugging sync issues page; recommendation: separate repos for dbt code vs Omni model code.

### APIs — MAJOR PILLAR
- REST API (`https://<instance>.omniapp.co/api`, OpenAPI spec published; interactive docs playground + in-instance API Explorer at `/api-explorer`). Versioned endpoints; rate limit 60 req/min/key (raisable to 500).
- **Auth**: Organization API keys (admin-scoped, no expiry) and Personal Access Tokens (user-scoped, inherit user permissions); OAuth-created PATs for CLI (8h auto-refresh) and MCP; `userId` impersonation on query runs (org keys only); token rotation; SCIM endpoints require org keys.

## Notes for synthesis
- Omni's positioning: "just-in-time" semantic modeling (start in workbook/SQL, promote what's worth keeping) vs. up-front modeling; UI actions always generate YAML/SQL (bidirectional), so business users and data teams share one artifact.
- The YAML dialect is LookML-like (views/dimensions/measures/`sql:`/`${}` refs/access grants/sets/extends/liquid-esque Mustache templating) but adds topics, query views, composite topics, LoD params, `materialized_query`, and AI-context parameters.
- Beta-flagged features as of Aug 2026: composite topics, cross-model tabs, input columns, model-local-editor CLI, shared extensions (support-enabled).
