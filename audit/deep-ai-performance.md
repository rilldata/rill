# AI Layer (performance & speed vs. direct Claude) — Deep-Dive Audit

**Focus:** AI response latency — why Rill AI feels slower than running the same analysis directly in Claude  |  **Scope:** `runtime/ai/*` (orchestration, agents, tools), `runtime/server/chat.go`, `runtime/drivers/{openai,gemini,claude}`, `runtime/drivers/admin/ai.go`, `admin/server/ai.go`, supporting paths (`runtime/connections.go`, `runtime/resolvers/metricsview_summary.go`, `runtime/metricsview/executor/executor_summary.go`, `cli/pkg/local/app.go`, `cli/cmd/admin/start.go`, `web-common/src/features/chat/core/*`)  |  **Health:** needs-attention

## Overview

I traced a user turn end-to-end: SSE handler (`chat.go:464` → `CompleteStreaming:325`) → `router_agent` → `analyst_agent`/`developer_agent` → `Session.Complete` tool loop (`ai.go:1279-1396`) → `drivers.AIService.Complete` (unary) → provider SDK, plus the tool implementations each iteration invokes (metrics queries, summary, file writes). Two hypotheses from the brief are **refuted**: (1) there is **no router-classification LLM call on the web hot path** — all frontends always send an explicit `agent` (`conversation.ts:116,361-365`; developer surfaces pass it via `chat-utils.ts:10`, `generateCanvas.ts:191`), and the router only invokes the LLM when `agent` is empty *and* ≥2 agents pass access checks (`router_agent.go:102-142`); (2) there is **no per-message DB persistence blocking the stream** — messages are flushed once per turn in a deferred `Flush` (`chat.go:366-371`), and the feedback agent only runs on explicit user feedback.

Where the time actually goes, in order: (a) **the entire LLM path is non-streaming** — all three provider drivers use blocking, full-generation APIs and `drivers.AIService` has no streaming method, so the user sees each LLM response (including the long final answer) only after it is fully generated; (b) **no prompt caching** — the Claude driver never sets `cache_control` (required for Anthropic caching), and the message-truncation marker rewrites the prompt prefix every iteration for long loops, defeating even the automatic caching OpenAI/Gemini provide, while ~55-60 KB of tool schemas + system prompt are re-processed on every one of up to 20 iterations; (c) **everything is serial** — multiple tool calls returned in one LLM response execute one at a time, and context seeding runs 3-6 dependent-free calls sequentially; (d) **the analyst prompt mandates a minimum of 4-6 queries plus a chart after each**, structurally multiplying LLM round-trips versus what direct Claude would choose to do; (e) **managed AI adds a unary WAN proxy hop through the admin service per LLM call** (also for local Rill Developer) and pins deployments to top-tier default models (Claude → Opus 4.5) with no tuning knobs. A typical first analyst turn is 2-4 serial OLAP seed queries + 6-13 serial LLM round-trips (each blocking, each re-processing an uncached, growing prompt) + 5-12 serial OLAP/chart tool executions — commonly 30 s to 3 min of wall clock with long dead-air windows, versus direct Claude which streams tokens immediately, caches the prefix, parallelizes tool calls, and stops when it has enough data. Verification also surfaced one outright bug on the developer path: `develop_file` executes its context-seeding tool calls but drops their results before the LLM sees them due to a wrong parent filter (finding 10).

## Findings

### deep-ai-performance-01 [HIGH] No token-level streaming anywhere in the LLM path; the final answer arrives only after full generation
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/ai.go:10-12`, `runtime/drivers/claude/claude.go:295`, `runtime/drivers/openai/openai.go:343`, `runtime/drivers/gemini/gemini.go:318`, `runtime/ai/ai.go:1302-1308`, `runtime/server/chat.go:376-407`
- **Problem:** `drivers.AIService` exposes only a unary `Complete` (`ai.go:10-12`). All three drivers call the blocking, non-streaming provider APIs: Claude `h.client.Beta.Messages.New` (claude.go:295), OpenAI `Chat.Completions.New` (openai.go:343), Gemini `Models.GenerateContent` (gemini.go:318). The client-facing "streaming" (`CompleteStreaming` → SSE) is message-granular: a message is only published via `AddMessage` after a full LLM response has returned (`ai.go:1353-1366` for intermediate text; the final answer is only published as the analyst/router *result* message after the whole loop finishes — the no-tool-call final response breaks the loop at `ai.go:1345-1348` without emitting any progress message). Anthropic's own guidance (and the SDK defaults) is to stream any request with long output/high `max_tokens`; `max_tokens` here is 8192 (claude.go:141).
- **Failure scenario / perf impact:** The final analyst answer ("3-5 key insights" with headers and citations, typically 500-1500+ tokens, worst-case 8192) is the longest generation of the turn — 10-45+ s on Opus-tier models — during which the UI shows nothing new. The same dead-air occurs during every intermediate iteration (2-8 s each). Direct Claude shows first tokens in ~1-2 s. This is the single largest *perceived* latency difference and it compounds with finding 02 (uncached prompt processing extends time-to-first-token of every generation).
- **Recommendation:** Add a streaming variant to `drivers.AIService` (e.g. `CompleteStream(ctx, opts, fn func(delta))`), implement it with the providers' SSE APIs, and forward text deltas through the session subscriber as partial-message events (the SSE plumbing in `chat.go` and the frontend `sse-*` stack already exist). For the managed path this also requires a streaming admin RPC (see finding 05). An incremental first step with most of the win: stream only the *final* (no-tool-call) generation to the client.

### deep-ai-performance-02 [HIGH] No prompt caching: Claude driver never sets `cache_control`, and truncation rewrites the prompt prefix for all providers; ~55-60 KB of prompt is re-processed every iteration
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/claude/claude.go:317-342` (no `cache_control` anywhere), `claude.go:310` (reads `CacheReadInputTokens`), `runtime/ai/ai.go:1290,1605-1661` (`maybeTruncateMessages`; marker at `:1628`, sliding keep-last window at `:1635-1636`), sizes (measured): `runtime/ai/create_chart.go:418` (24.8 KB description) + `runtime/metricsview/charts_json_schema.go` (~12.6 KB schema), `runtime/metricsview/query.go:496` (11.6 KB schema), `runtime/ai/metrics_view_query.go:40` (~6 KB description), `runtime/ai/instructions/data/development.md` (26.2 KB), `resources/canvas.md` (32.6 KB), `resources/model.md` (23.8 KB)
- **Problem:** Anthropic prompt caching is opt-in via explicit `cache_control` breakpoints (block-level or the top-level parameter); `convertMessages`/`convertTools` set neither, so `usage.cache_read_input_tokens` — which the driver dutifully reports at claude.go:310 — is always 0. Every iteration of a tool loop therefore re-processes the full prompt at full price and full time-to-first-token: for the analyst loop that is the ~8 KB system prompt + ~55 KB of tool definitions (`create_chart` alone contributes ~37 KB; `query_metrics_view` ~18 KB) + the growing history including up-to-100 KB tool results (`maxMessageSizeBytes`, `ai.go:37`), ~15-20 K tokens minimum per iteration before history. Additionally, once a loop exceeds 20 messages, `maybeTruncateMessages` rewrites the prefix on *every* subsequent iteration in two ways: the marker text embeds the changing skipped-count (`"... [%d messages omitted for brevity] ..."`, `ai.go:1628`) at position 5, and — more fundamentally — the kept tail is a *sliding* window (`messages[len-16:]`, `ai.go:1635-1636`), so everything after message 4 changes each iteration regardless of the marker. Since caching is prefix-based, this defeats even OpenAI's and Gemini's automatic caching, which otherwise benefit from the append-only message pattern below 20 messages.
- **Failure scenario / perf impact:** A 10-iteration analyst loop processes on the order of 150-400 K cumulative input tokens with 0% cache hits on Claude (and 0% past 20 messages on all providers). Cached input is roughly an order of magnitude cheaper and substantially faster to prefill; uncached prefill of 20-40 K tokens adds ~1-3 s to every iteration's TTFT on top of generation time. Direct claude.ai caches the system prompt/tools automatically across its agent loop. This is also a direct cost issue for the Rill-managed (billable) connector.
- **Recommendation:** In the Claude driver, set `cache_control` breakpoints on (a) the last tool definition, (b) the last system block, and (c) the last message of the previous turn (max 4 breakpoints; the SDK supports block-level `CacheControl`). Make `maybeTruncateMessages` cache-stable: freeze the marker text (drop the count, or bucket it) *and* truncate at stable boundaries (e.g. drop in chunks so the kept prefix only changes every N iterations) — fixing the marker alone is not sufficient because of the sliding tail window. Verify with the already-collected `cached_input_tokens` metric — it should become non-zero.

### deep-ai-performance-03 [MEDIUM] Tool calls execute strictly sequentially — both within an LLM response and in agent context seeding
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/ai/ai.go:1353-1395` (serial block loop), `runtime/ai/analyst_agent.go:111-161` (serial seeding), `runtime/metricsview/executor/executor_summary.go:91-112` (serial per-time-dimension `Timestamps` queries), `runtime/ai/develop_file.go:92-107` and `runtime/ai/developer_agent.go:60-77` (serial pre-invokes)
- **Problem:** (1) When the model returns multiple `tool_use` blocks in one response — which the Claude driver explicitly permits by using `ToolChoice: auto` without `disable_parallel_tool_use` (claude.go:276-280) — the completion loop executes them one at a time via blocking `CallToolWithOptions` (`ai.go:1367-1391`). Each `query_metrics_view` is an OLAP round-trip taking 0.1-5 s (2-minute timeout, `metrics_view_query.go:260`). (2) The analyst agent's first-turn seeding runs `get_canvas` → per-metrics-view `query_metrics_view_summary` → `get_metrics_view` strictly serially (`analyst_agent.go:111-152`); a canvas with 3 metrics views is 7 sequential calls before the first LLM token. (3) Inside each summary, `e.Timestamps` runs once per time dimension (≤2) sequentially before the combined dimension query (`executor_summary.go:91-112`) — up to 3 serial OLAP queries per summary. (4) `develop_file` and `developer_agent` pre-invoke `list_files` → `project_status` → `read_file` serially.
- **Failure scenario / perf impact:** A model that batches 3 queries (as Claude does natively when tools are independent) pays 3× OLAP latency serially instead of ~1×. Canvas seeding with 3 metrics views at ~0.5-2 s per summary adds 2-6 s of serial pre-LLM latency. Direct Claude executes independent tool calls concurrently (the documented pattern is to run parallel `tool_use` blocks concurrently and return all results in one message).
- **Recommendation:** Execute the `tool_use` blocks of a single LLM response concurrently (errgroup; append results in block order to keep the transcript deterministic — note `AddMessage` is already mutex-guarded). Parallelize the analyst seeding fan-out per metrics view, and the two `Timestamps` calls inside `Summary`. Keep dependent sequences (parser wait → status) serial.

### deep-ai-performance-04 [MEDIUM] The analyst prompt mandates a 4-6-query minimum plus a chart after every query — a structural round-trip multiplier
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/ai/analyst_agent.go:357-358` ("Execute a MINIMUM of 4-6 distinct analytical queries... Some analyses may require up to 20 queries"), `:400-414` ("After running `query_metrics_view` create a chart using `create_chart` unless...", gated on the `chat_charts` feature flag), `:198` (`MaxIterations: 20`)
- **Problem:** Each mandated query is one full LLM round-trip (blocking, uncached — findings 01/02) plus one OLAP query; the chart-per-query rule roughly doubles the tool-call count (each `create_chart` is cheap to execute but costs another LLM iteration to emit). A simple question ("what was revenue last week?") that direct Claude over the same MCP tools would answer with 1-2 queries is steered into 4-6+ queries and 4-6 charts, i.e. typically 8-13 LLM iterations. With ~3-8 s per iteration (generation + uncached prefill) and ~0.1-5 s per OLAP query, the floor for any analyst turn is tens of seconds regardless of question complexity.
- **Failure scenario / perf impact:** This is the main *structural* reason a Rill analyst turn takes minutes where claude.ai takes 15-30 s: the loop count is prompt-forced, and every extra iteration compounds the per-iteration costs from findings 01-03. It is a deliberate quality/latency trade-off, but it is currently unconditional — trivial questions pay the full research protocol.
- **Recommendation:** Make query depth adaptive: instruct the model to scale query count to question complexity (e.g. "answer directly when one query suffices; use the full OODA protocol for open-ended analysis"), or split into a fast path (single-question) and a deep-analysis path (report mode keeps the 4-6 minimum). Allow charts to be emitted in the same iteration as the query they visualize (parallel tool calls, finding 03) so the chart rule stops doubling iterations.

### deep-ai-performance-05 [MEDIUM] Managed AI routes every LLM call through a unary admin-service proxy (also from local Rill Developer) and pins deployments to top-tier default models with no tuning knobs
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/admin/ai.go:11-37`, `admin/server/ai.go:19-87`, `cli/pkg/local/app.go:281-293,324` (local AI connector = `admin`), `cli/cmd/admin/start.go:246-284` (api-key-only config), `runtime/drivers/claude/claude.go:134` (default `claude-opus-4-5-20251101`), `runtime/drivers/openai/openai.go:168` (default `gpt-5.2`)
- **Problem:** With the default (Rill-managed) AI connector — which is also what local Rill Developer uses (`app.go:281-293`: the `admin` connector pointed at Rill's cloud admin URL) — every LLM call in a 10-20-iteration loop travels runtime → admin service (WAN, unary gRPC `admin.Complete`) → provider, and back. The unary hop (a) adds a WAN round-trip plus admin-side marshalling per call (the full message history is re-serialized over the wire every iteration — tens to hundreds of KB by late iterations), and (b) makes token streaming impossible end-to-end until the admin RPC becomes a stream (blocks finding 01 for all managed deployments). Separately, the admin bootstrap passes *only* `api_key` to the driver (`start.go:250-264`), so managed deployments are pinned to driver defaults: Claude → **Opus-tier** (`claude-opus-4-5`, the slowest model class, claude.go:134), OpenAI → `gpt-5.2` with no `reasoning_effort` set, Gemini → `gemini-3-flash-preview`; no model, max-tokens, effort, or speed configuration is reachable from deployment config.
- **Failure scenario / perf impact:** 10 iterations × (1 extra WAN RTT + admin processing) adds seconds per turn even before provider time; running a 10-20-iteration *tool loop* on an Opus-tier model (vs. e.g. a Sonnet/Haiku-tier model for intermediate iterations) multiplies per-iteration generation time 2-4×. Direct claude.ai users choose their model and talk to the API with one hop.
- **Recommendation:** Add model/max-tokens/effort passthrough to the admin AI config (env + per-org override), default the agent loop to a faster model tier (optionally escalating for the final synthesis), and add a streaming `Complete` RPC to the admin proto so the proxy stops blocking finding 01. Longer term, consider issuing scoped provider credentials to runtimes so the proxy hop is only on the billing/audit path, not the data path.

### deep-ai-performance-06 [MEDIUM] `write_file` blocks on a full-project reconcile (plus a fixed 500 ms sleep) on every write
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/ai/file_write.go:117-152` (`Reconcile` at `:123`, fixed sleep at `:128-132`, `WaitUntilIdle` at `:149`)
- **Problem:** Every `write_file` in the developer/develop_file loops forces a project-parser reconcile, sleeps a hard-coded 500 ms, then calls `ctrl.WaitUntilIdle(ctx, true)` — which waits for **all** resources in the instance to finish reconciling, not just the resources declared in the written file. (The `// TODO: Only if not streaming` at `:123` shows this is known to be unrefined.) Writing a small YAML file therefore waits on any unrelated in-flight work (e.g. a big model materialization triggered earlier in the same loop or by the user), and writing a model file waits for its full materialization — potentially minutes for a large source — before the LLM gets its tool result and can proceed.
- **Failure scenario / perf impact:** A multi-file developer task ("add a source + model + metrics view + dashboard") issues 4+ writes; each pays parser reconcile + 500 ms + whole-DAG idle. If step 2 kicked off a slow ingest, steps 3-4's writes stall behind it even when they don't depend on it. This is the dominant latency term for the developer agent on real projects, ahead of LLM time.
- **Recommendation:** Wait only on the resources declared in the written file (and their upstream refs), e.g. via `ctrl.List(ctx, "", path)` + targeted waits, instead of global `WaitUntilIdle`; replace the fixed 500 ms sleep with an event-driven wait on the parser resource version; and consider returning early with "reconciliation in progress" plus letting the model poll `project_status` (which already supports `wait_until_idle`) only when it needs confirmation.

### deep-ai-performance-10 [MEDIUM] `develop_file` seeds its sub-agent with `FilterByParent(s.ID())` — a filter that can never match — so the pre-invoked discovery results are executed but silently dropped from the LLM context
- **Category:** bug  **Confidence:** high  **Novelty:** new (found during adversarial verification; root-causes part of finding 07)  **Must-fix:** no  **Location:** `runtime/ai/develop_file.go:115` (the bug), `runtime/ai/developer_agent.go:83` (the correct pattern: `FilterByParent(s.ParentID)`), supporting trace: `runtime/ai/ai.go:210-212` (root session `ParentID` is `""`), `ai.go:881` (`AddMessage` sets `ParentID: s.ParentID`), `ai.go:971` (`WithParent(callMsg.ID)` — the only `WithParent` call site, always a *message* ID)
- **Problem:** `develop_file.Handler` pre-invokes `list_files`, `project_status`, and `read_file(path)` (`develop_file.go:92-107`) and then tries to seed their results into the sub-agent's messages via `s.MessagesWithResults(FilterByParent(s.ID()))` (`:115`). `s.ID()` is the **AI session UUID** (`BaseSession.ID()`), but message `ParentID`s are only ever `""` (root) or *message* UUIDs — no code path ever sets a message's parent to the session ID (verified across all `ParentID` assignments and both `FilterByParent` producers). The filter therefore always returns an empty set, and the sub-agent's LLM receives only `[system instructions, resource instructions?, user prompt]` — no file listing, no project status, and crucially **not the current content of the file it is asked to edit**, despite the tool's own arg contract ("assuming no prior context except the path's current content and status", `develop_file.go:25`). The sibling `developer_agent.go:83` uses the correct `FilterByParent(s.ParentID)` (the current call's message ID), which is what this line was evidently meant to be.
- **Failure scenario / perf impact:** Every `develop_file` invocation (a) wastes 3 serial pre-invoked tool executions whose results reach the UI transcript but not the model, and (b) starts the sub-loop blind, so the model must spend 1-3 extra LLM round-trips (at ~3-8 s each, uncached per finding 02) re-fetching the listing/status/content it was supposed to already have — or, worse, writes an existing file without having read it, risking a blind overwrite whose damage only shows up in the returned diff. This has existed since the file was introduced (`fbe8bf575`, Jan 2026).
- **Recommendation:** Change `:115` to `FilterByParent(s.ParentID)` (matching `developer_agent.go:83`); add a mock-LLM test asserting the sub-agent's first completion request contains the `read_file` result for the target path (there is currently no test covering the seeded messages).

### deep-ai-performance-07 [LOW] `develop_file` sub-agent cold-starts per file: re-loads 26-59 KB of instructions, repeats the parent's discovery calls, and multiplies LLM iterations
- **Category:** performance  **Confidence:** high  **Novelty:** expands-existing (latency dimension of ai-11's nested-loop fan-out)  **Must-fix:** no  **Location:** `runtime/ai/develop_file.go:64-84,92-115,131`, `runtime/ai/developer_agent.go:60-77,99-102`
- **Problem:** Each `develop_file` call is an isolated sub-agent ("no prior context from the conversation", develop_file.go:36): it re-sends the 26 KB `development.md` plus up to 32.6 KB of resource-specific instructions as a fresh system prompt, and re-runs `list_files` + `project_status` + `read_file` serially (`:92-107`) even though the parent developer agent pre-invoked `list_files` + `project_status` at the start of the same turn (`developer_agent.go:60-77`). Worse, due to finding 10 those re-runs are then *discarded* before the LLM ever sees them. Each sub-loop is up to 10 more LLM iterations (min ~2), nested inside the parent's 20. A 4-file task ⇒ 4 × (fresh ~7-15 K-token system prompt with no cache reuse (finding 02) + 3 duplicate-and-dropped discovery calls + 2-10 LLM iterations + reconcile-blocked writes (finding 06)).
- **Failure scenario / perf impact:** "Build me a dashboard from this S3 bucket" routinely runs 15-40 total LLM calls across parent and sub-loops. The isolation design is defensible for context hygiene, but the duplicated discovery and uncached repeated instruction prompts are pure overhead.
- **Recommendation:** First fix finding 10 so the pre-invoked results actually reach the sub-agent; then pass the parent's fresh `list_files`/`project_status` results into the sub-agent's seed messages instead of re-invoking; with finding 02's cache breakpoints, the static instruction files become cache hits across sub-agent calls in the same session (same prefix), which removes most of the token-processing cost.

### deep-ai-performance-08 [LOW] Agent-loop progress is coupled to client drain rate via the unbuffered subscriber hand-off under the session lock
- **Category:** performance  **Confidence:** medium  **Novelty:** expands-existing (perf angle of ai-02 / MUST-FIX D "AI subscriber send under the session lock")  **Must-fix:** no  **Location:** `runtime/ai/ai.go:656-661,893-900`, `runtime/server/chat.go:385-406`
- **Problem:** `AddMessage` performs a blocking send on the unbuffered subscriber channel while holding `s.mu`. Beyond the cancellation-hang already tracked in MUST-FIX D, this serializes the *producer* (agent loop) with the *consumer*: the reader goroutine performs `messageToPB` + `stream.Send` between receives, so the next `AddMessage` blocks (under the session mutex) until the previous message has been fully serialized and flushed to a possibly slow client connection. Tool execution and LLM-response processing pause for the duration.
- **Failure scenario / perf impact:** On a slow or high-latency client link (SSE over poor networks, large tool-result messages up to 100 KB), each message hand-off adds the client's per-message serialize+write time to the agent loop's critical path — turning a network-bound consumer into an agent-loop bottleneck. Mitigating factor (why confidence stays medium on magnitude, though the mechanism is certain): kernel socket buffers absorb small frames, so real producer stalls need either large messages or a genuinely stalled client with full buffers. Impact is negligible on localhost, real on slow WANs with chatty loops (30+ messages per turn).
- **Recommendation:** The fix for MUST-FIX D (buffered per-subscriber channels with non-blocking send, or notifying outside the critical section) also removes this backpressure; prefer a small buffered channel (e.g. 64) + drop-oldest/track-lag semantics so the producer never waits on the client.

### deep-ai-performance-09 [LOW] Refutation: no router-classification LLM call and no feedback-agent call on the normal web turn
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `web-common/src/features/chat/core/conversation.ts:116,361-365`, `web-common/src/features/chat/core/conversation-manager.ts:137-141,186-190`, `runtime/ai/router_agent.go:102-142`, `runtime/ai/feedback_agent.go:68-94`
- **Problem (negative finding):** The brief hypothesized a router LLM classification before every turn and a separate feedback-agent call. Traced end-to-end: every frontend surface constructs conversations with an explicit agent (`Conversation` defaults to `analyst_agent`; editor/canvas/sample-data surfaces pass `developer_agent`), and `startStreaming` always sends `agent` in the request body — so the router takes the `args.Agent != ""` branch and performs zero LLM calls (its overhead is title derivation and two in-memory access checks). The LLM "Agent choice" call only fires for API/MCP-adjacent callers that omit `agent` while both agents are accessible (requires `EditRepo` + `developer_agent` flag). The feedback agent runs only on explicit thumbs-down (one extra structured completion at that moment), never on normal turns.
- **Failure scenario / perf impact:** None on the web hot path. Worth documenting so orchestration-overhead work targets the real contributors (findings 01-05). One residual: external API callers who omit `agent` in Rill Developer do pay one extra serial LLM round-trip (~1-3 s) per turn, and the choice call re-sends the whole root-level conversation history (`router_agent.go:118-120`).
- **Recommendation:** No action needed for the web path. For API callers, document that passing `agent` skips a model call; consider a cheap heuristic pre-route (or a fast/small model) for the choice call.
