# Connectors (performance + correctness) — Deep-Dive Audit

**Focus:** Connection pooling/reuse, conncache correctness + hit rate, download/ingest throughput, pagination + context propagation, unbounded fetches, retry/backoff cost, rduckdb read/write pool behavior, per-dialect escaping, partial-open leaks, iterator cleanup.  |  **Scope:** `runtime/drivers/{drivers,connectors,registry,olap,object_store,warehouse,information_schema,catalog,file_store}.go`, OLAP drivers (`duckdb`, `clickhouse`, `druid`, `pinot`, `starrocks`, `mysql`, `postgres`), ingestion drivers (`s3`, `gcs`, `azure`, `bigquery`, `snowflake`, `redshift`, `athena`, `databricks`, `salesforce`, `https`, `file`), `runtime/pkg/{blob,rduckdb,conncache}`.  |  **Health:** needs-attention

## Overview

This pass traced four hot paths end-to-end: (1) the DuckDB query path (`acquireOLAPConn` → `rduckdb.AcquireReadConnection` → `metaSem` + `USE` per acquisition), (2) the rduckdb write/replication path (`CreateTableAsSelect`/`MutateTable` → `pushToRemote`/`pullFromRemote` → catalog snapshots), (3) object-store listing/download (glob resolver → `ListObjectsForGlob` per page → per-call bucket/client construction; `blob.Download` → 8-way parallel, batch-bounded pipeline), and (4) warehouse ingest (Snowflake/Databricks/BigQuery Arrow→Parquet; Salesforce Bulk; Athena/Redshift UNLOAD).

The headline: **`runtime/pkg/rduckdb` — the DuckDB read/write pool and cloud-replication layer that every DuckDB project sits on — was not covered by any prior audit and contains the worst defects in this area**: a nil-pointer panic in remote deletion, a remote-corruption sequence that leaves fresh replicas unable to serve any queries (the corrupted table poisons the catalog ~5s after boot and every read and write then fails at `attachTables`), a per-model-build metrics-registration leak (a much hotter instance of the already-known drivers-olap-17), and a dirty-flag protocol that can serve stale data indefinitely while reporting success. On the performance side, the biggest wins are: stop rebuilding S3/GCS/Azure clients + credentials (+ STS AssumeRole + GetBucketRegion) on every listing page; fix the Postgres OLAP pool default of 1 connection (all dashboard queries serialize); and stop copying + re-uploading the entire table file on every incremental DuckDB refresh. Two silent-partial-data bugs (Salesforce, Druid arrayLines) and one credential-into-telemetry leak (ClickHouse object-store ingest) round out the ship-blocker set.

Where the time goes on the paths traced: object-store listing overhead is dominated by per-page client construction (up to ~0.5 s/page with `role_arn` + region detection); DuckDB read acquisition adds a serialized `USE` round trip per query plus a full `attachTables` replay (2 statements per table) on the first read after every write; incremental DuckDB refreshes are dominated by whole-file copy + whole-file upload rather than the mutation itself.

## Findings

### deep-connectors-01 [HIGH] rduckdb `deleteRemote` panics on listing errors and deletes the wrong `meta.json` key
- **Category:** bug  **Confidence:** high  **Novelty:** new  **Must-fix:** yes  **Location:** `runtime/pkg/rduckdb/remote.go:276` and `:285-298`
- **Problem:** Two defects in the same function. (a) When deleting a whole table, the code intends to delete the table's metadata first but calls `d.remote.Delete(ctx, "meta.json")` (`:276`) instead of `path.Join(table, "meta.json")` — a bucket-root key that never exists. The NotFound is swallowed, so the intended "meta first, data second" crash-safety ordering silently never happens; the prefix loop then deletes version-directory files *before* `<table>/meta.json` (numeric version dirs sort before `m`). (b) In the deletion loop (`:287-297`), when `iter.Next(ctx)` returns a non-EOF error (context cancellation, transient network error), the code only logs it and then dereferences `obj.Key` — but gocloud's `ListIterator.Next` returns `(nil, err)` on error, so this is a guaranteed nil-pointer panic. The loop also has no exit condition on persistent errors other than the panic.
- **Failure scenario:** A user saves a model file while a `DropTable`/`RenameTable` reconcile is in flight; the old reconcile's context is cancelled mid-listing; `iter.Next` returns the cancellation error; `obj.Key` panics. The controller's per-reconcile `recover()` (`runtime/controller.go:1319-1328`) catches it, so the process survives, but the reconcile fails with a spurious `panic: runtime error: invalid memory address` instead of a clean cancellation/transient error. Separately, any crash mid-delete leaves `<table>/meta.json` intact pointing at deleted data files — see -02 for why that corrupts fresh replicas.
- **Recommendation:** Delete `path.Join(table, "meta.json")` first; in the loop, `continue`/`return` on non-EOF errors before touching `obj`; add a bounded error budget so persistent listing errors terminate the loop.

### deep-connectors-02 [HIGH] rduckdb `pushToRemote` deletes the old remote version even when the `meta.json` upload failed — corrupted remote; fresh replicas cannot open the DB
- **Category:** data-loss  **Confidence:** high  **Novelty:** new  **Must-fix:** yes  **Location:** `runtime/pkg/rduckdb/remote.go:244-255`
- **Problem:** After uploading the new version's data files, `pushToRemote` uploads `<table>/meta.json`. If that upload fails (`err != nil`, `:247-249` — only logged), the code still runs the `// success -- remove old version` block: `if oldMeta != nil { _ = d.deleteRemote(ctx, table, oldMeta.Version) }` (`:252-254`) before `return err`. Remote state is now: `meta.json` → old version whose data files were just deleted; new version files present but unreferenced.
- **Failure scenario (traced end-to-end this pass):** A transient 503 on the small `meta.json` write (the `retry` helper only retries `"stream error: stream ID"`, see -18) after a successful multi-GB data upload. The writing node keeps serving from its local files, so the corruption is invisible — until a *fresh* replica (scale-out, node replacement, wiped disk) pulls from remote. `NewDB` itself succeeds: the sync downloads nothing for the referenced-but-empty version, and the boot-time table collection silently skips the table because `tableMeta` stats the missing `data.db` (`db.go:1112-1123`). But ~5 s later `localDBMonitor` (with `localDirty` still true from `NewDB`) runs `pullFromRemote(ctx, true)`, whose catalog-update loop inserts the broken table into the catalog (`remote.go:170`, see -20) and increments the snapshot. The next `AcquireReadConnection` then fails hard in `attachTables` on `ATTACH` of the missing `data.db` (`db.go:1037-1039`) — **every query on the instance fails**, and every write op fails the same way inside `acquireWriteConn` → `openDBAndAttach`, so the model rebuild that would heal the table cannot run either. Restart helps for only ~5 s until the monitor re-poisons the catalog.
- **Recommendation:** Only delete the old version when the meta upload succeeded (`if err == nil && oldMeta != nil`). Consider making `pullFromRemote` tolerate a referenced-but-empty version dir (skip the table with an error log instead of cataloging it) so one corrupted table cannot take down the whole DB.

### deep-connectors-03 [HIGH] ClickHouse object-store ingestion embeds S3/GCS credentials into SQL that is exported to OTEL traces and logs
- **Category:** data-leak  **Confidence:** high  **Novelty:** new  **Must-fix:** yes  **Location:** `runtime/drivers/clickhouse/model_executor_objectstore_self.go:126-163`; `runtime/drivers/clickhouse/clickhouse.go:933,951`; `runtime/drivers/clickhouse/dialect.go:237-240`
- **Problem:** `genSQL` builds `SELECT * FROM s3('<glob>', '<AccessKeyID>', '<SecretAccessKey>', fmt)` / `gcs(...)` via `fmt.Sprintf("'%s'", ...)` with no escaping, and the result is executed as ordinary model SQL. Traced end-to-end: (a) the ClickHouse handles are opened with `otelsql.OpenDB(clickhouse.Connector(opts))` and **no span options** — otelsql's default (`DisableQuery=false`, verified in v0.27.0 `config.go:94-95`) records the full statement as `db.statement` on every span, so **the plaintext AWS/GCS secret is exported to the tracing backend on every ClickHouse+object-store model build**; (b) with `log_queries: true` the SQL is logged, and `SanitizeQueryForLogging` (`dialect.go:237-240`) only masks dictionary `PASSWORD '...'`, not s3/gcs credentials; (c) any `'` in the path or secret breaks the statement (no escaping). Contrast rduckdb, which deliberately filters `CREATE ... SECRET` statements out of spans (`rduckdb/db.go:920-929`) — the codebase clearly intends credentials never to reach telemetry.
- **Failure scenario:** A standard Rill Cloud project with a ClickHouse OLAP and an S3 source: every model build emits a trace span containing the S3 secret key; anyone with access to the tracing/observability stack (a much wider audience than connector-secret admins) can read the credential.
- **Recommendation:** Add a `SpanFilter` on the ClickHouse handles that suppresses statements matching s3/gcs table functions (or set `DisableQuery` and log via the existing sanitized path); extend `SanitizeQueryForLogging` to mask s3/gcs credential arguments; escape interpolated values (`EscapeStringValue`). Longer term, use ClickHouse named collections or per-query headers instead of inline literals.

### deep-connectors-04 [HIGH] Salesforce batch-result fetch failures are swallowed into empty files — silent partial ingestion
- **Category:** data-loss  **Confidence:** high  **Novelty:** new  **Must-fix:** yes  **Location:** `runtime/drivers/salesforce/bulk.go:212-231` (consumed at `warehouse.go:149-155`)
- **Problem:** `fetchBatchResult` returns `bytes.NewReader(nil)` (an empty reader) in **three** failure cases: batch state `"Failed"`, and — critically — when `RetrieveBulkJobQueryResultsWithCallbackWithContext` returns an error (transient network failure). In the error branch the actual `err` is discarded entirely (the log prints the unrelated `resultInfo.batch.StateMessage`, which is empty for a network error). `retrieveJobResult` then writes the empty body to a temp CSV and returns it as a **successful** batch; `Next()` (`warehouse.go:149-155`) hands it to the model executor. Note `getBatches` already filters out batches with `NumberRecordsProcessed == 0` (`bulk.go:168`), so an empty file here always means a *non-empty* batch whose data was lost.
- **Failure scenario:** A PK-chunked export of 5M rows in 50 batches; one `RetrieveBulkJobQueryResults` call hits a transient 500. That chunk's ~100k rows are replaced by a 0-byte CSV. Depending on DuckDB's CSV sniffing the model either silently ingests partial data or fails later with a confusing schema/sniffing error that hides the root cause. Either way the driver reported success for a failed download. Related: the job-completion wait counts failed batches as done (`bulk.go:131` — `NumberBatchesCompleted+NumberBatchesFailed == NumberBatchesTotal`), so batch-level failures on chunked jobs are tolerated at the job level and then silently dropped by the `NumberRecordsProcessed > 0` filter or converted to empty files here.
- **Recommendation:** Make `fetchBatchResult` return `(io.Reader, error)` and propagate retrieve errors (with the real `err` in the message — the current log prints the unrelated, empty `StateMessage`); keep the empty-reader behavior only for the deliberate `NumberRecordsProcessed == 0` case. Fail the job when any consumed batch is in state `Failed`. Add bounded retries for the retrieve call.

### deep-connectors-05 [HIGH] rduckdb registers an un-unregisterable DB-stats metrics callback per write-handle open — leaks one per model build
- **Category:** bug  **Confidence:** high  **Novelty:** expands-existing (drivers-olap-17)  **Must-fix:** yes  **Location:** `runtime/pkg/rduckdb/db.go:956` (in `openDBAndAttach`, reached from `acquireWriteConn` at `:780`); also `runtime/pkg/rduckdb/generic.go:189`
- **Problem:** drivers-olap-17 established that `otelsql.RegisterDBStatsMetrics` (v0.27.0) discards the `metric.Registration`, making the callback permanent. That finding was scoped to ClickHouse `openHandle` (per connector open). This pass found the far hotter call site: rduckdb's `openDBAndAttach` runs `RegisterDBStatsMetrics(db.DB, ...)` on **every write-handle open**, and `acquireWriteConn` opens a fresh write handle for **every `CreateTableAsSelect` and `MutateTable`** — i.e., every model build and every incremental refresh. The handle is closed minutes later (`release()` at `db.go:862-877`), but the meter callback retains the closed `*sql.DB` forever and runs on every metrics collection cycle.
- **Failure scenario:** A cloud project with 100 models refreshing every 15 minutes leaks ~9,600 registrations/day. Memory grows unboundedly (each retains a closed `*sql.DB` graph), and every OTEL collection interval iterates an ever-growing callback list, degrading a long-running runtime over weeks.
- **Recommendation:** Do not register DB-stats metrics on ephemeral write handles at all (they live for one operation; the gauge is meaningless) — register only on the long-lived read handle in `NewDB`/`NewGeneric`. If per-write stats are wanted, vendor a variant that returns the `Registration` and unregister in `release()`.

### deep-connectors-06 [MEDIUM] Object-store listing rebuilds the cloud client, credentials (incl. STS AssumeRole) and region detection on every page
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/s3/object_store.go:61-82` → `s3.go:355-384,402-465`; `runtime/drivers/gcs/object_store.go:68-89,128-140` → `gcs.go:295-307`; `runtime/drivers/azure/object_store.go:73-95`; paginated callers: `runtime/resolvers/glob.go:277-281`, `runtime/server/connector_service.go:48-53`, `runtime/ai/list_bucket_objects.go:97-99`
- **Problem:** `ListObjects` and `ListObjectsForGlob` call `c.openBucket(...)` and `defer blobBucket.Close()` **per invocation**, and the paginated callers invoke them once per page (`pagination.CollectAll` with page size 1000 in the glob resolver; per UI/AI request elsewhere). For S3, each call runs `newCredentialsProvider` (a fresh `stscreds.NewAssumeRoleProvider` when `role_arn` is set — the STS AssumeRole HTTP round trip is repeated since the credential cache is thrown away each page; with `allow_host_access`, `config.LoadDefaultConfig` + `Credentials.Retrieve` re-hits IMDS/SSO), `config.LoadDefaultConfig` (profile/file parsing), `manager.GetBucketRegion` (an extra HTTP round trip whenever `region` is not configured, `s3.go:302-321`), and a brand-new `s3.Client`/HTTP transport (no connection/TLS reuse across pages). GCS re-runs `gcputil.Credentials` (ADC resolution) and builds a new transport per page; Azure likewise. Contrast `DownloadFiles`, which correctly opens the bucket once and paginates internally (`blob/download.go:76-83`).
- **Perf impact:** A partitioned model globbing 50k objects lists 50 pages → 50 × (credential resolution + AssumeRole (~100-300 ms) + GetBucketRegion (~50-100 ms) + TLS handshake) ≈ **5-25 s of pure overhead per reconcile**, plus the same again for `state: incremental` re-lists. Connector-UI browsing and AI bucket tools pay one client rebuild per page click/tool call. The connection cache caches the `Connection` handle, but the handle caches nothing.
- **Recommendation:** Cache the constructed client/bucket on the `Connection` keyed by bucket name (invalidate on config change — the conncache already evicts on config change), or at minimum cache the resolved `aws.Config`/credentials provider and detected region. This also fixes AssumeRole rate-limit exposure on large listings.

### deep-connectors-07 [MEDIUM] Postgres OLAP pool defaults to a single connection — dashboard queries fully serialize
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/postgres/postgres.go:211-216` (default), `:425-431` (applied)
- **Problem:** `resolveMaxOpenConns` returns **1** when `max_open_conns` is unset, and `SetMaxOpenConns(1)` is applied to the shared pool used by every OLAP query. `ConnMaxLifetime` also defaults to 1 minute, so the single connection is torn down and re-established (TLS + auth) every minute.
- **Perf impact:** An explore dashboard fires 10-30 concurrent queries; with one connection they execute strictly sequentially: total load time = Σ(query times) instead of ≈ max. A 20-tile dashboard at 200 ms/query renders in ~4 s instead of ~0.4 s, and one slow query (or a `Head`/profiling query) head-of-line-blocks everything, including schema lookups. Contrast: StarRocks defaults to 20, ClickHouse to 20, DuckDB to `pool_size` 2-5.
- **Recommendation:** Raise the default (e.g. 5-10, matching the other drivers' philosophy), or at minimum document `max_open_conns: 1` prominently as a dashboard-latency cliff. Reconsider the 1-minute `ConnMaxLifetime` default.

### deep-connectors-08 [MEDIUM] MySQL and Snowflake OLAP pools are unbounded — no `MaxOpenConns` cap
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/mysql/mysql.go:384-390`; `runtime/drivers/snowflake/snowflake.go:381-386` (OLAP via `AsOLAP` at `:319-321`, `olap.go:50-62`)
- **Problem:** Both drivers' `getDB` open the pool with only `SetConnMaxIdleTime(time.Minute)`; there is no `SetMaxOpenConns` (unlimited) and no `max_open_conns` config option, unlike postgres/starrocks/clickhouse (StarRocks sets 20/5/30m at `starrocks.go:342-345`; ClickHouse defaults `max_open_conns` to 20 at `clickhouse.go:233`). Every concurrent query opens a new connection on demand. Both drivers implement `OLAPStore`, so dashboard fan-out hits this pool directly.
- **Failure scenario:** A dashboard burst (or several users) against a MySQL-backed metrics view opens dozens-to-hundreds of connections; MySQL's default `max_connections` is 151, so Rill can exhaust the server's connection budget, failing its own queries and starving other applications sharing the database. After the burst, all but 2 idle conns (the `database/sql` default `MaxIdleConns`) are torn down, so the next burst re-handshakes from scratch. Snowflake tolerates more concurrency but each new conn re-authenticates (JWT/password exchange) after every burst.
- **Recommendation:** Cap the pools (e.g. 20, mirroring StarRocks) and set `SetMaxIdleConns` to match; expose `max_open_conns` in config like the postgres driver.

### deep-connectors-09 [MEDIUM] Druid `context.AfterFunc` cancel hook is never stopped — a spurious cancel DELETE fires for every query, including successful ones
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/druid/druidsqldriver/druid_api_sql_driver.go:116-129`
- **Problem:** Each query attempt registers `context.AfterFunc(ctx, ...DELETE /druid/v2/sql/{sqlQueryId}...)` and **discards the returned `stop` function**. `AfterFunc` fires whenever the context ends — which for gRPC/HTTP request contexts is *always*, at RPC completion. So after a query completes successfully and its rows are consumed, the hook still fires when the request context ends, spawning a goroutine that sends a cancel DELETE for an already-finished query ID (Druid answers 404). With retries, each of up to 6 attempts registers its own hook (distinct query IDs), all of which eventually fire. Until the context ends, every registration (closure + request body copy) is retained. The prior audit (drivers-olap-11) held this code up as the *good* cancellation example; the mechanism is right but the missing `stop()` gives it a per-query cost.
- **Perf impact:** +1 HTTP round trip and +1 short-lived goroutine to the Druid broker **per query attempt** — on a busy Druid-backed deployment this roughly doubles broker HTTP request count (dashboards routinely issue tens of queries per view). Registrations on long-lived contexts (e.g. reconciler-scoped) are retained for the context's lifetime.
- **Recommendation:** Capture `stop := context.AfterFunc(...)` and call `stop()` when the query completes — e.g. wrap the returned `driver.Rows` so `Close()` calls `stop()`, and call it on all error returns after registration.

### deep-connectors-10 [MEDIUM] Druid `arrayLines` responses have no truncation detection — mid-stream disconnects yield silent partial results
- **Category:** correctness  **Confidence:** high (code) / medium (trigger)  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/druid/druidsqldriver/druid_api_sql_driver.go:319-335` (also `:164-211`)
- **Problem:** The driver requests `resultFormat: "arrayLines"` (`:496`) and `druidRows.Next` iterates `dec.Decode(&dr.currentValues)` until `io.EOF`. Druid's SQL API documents that the `*Lines` formats emit **a trailing empty line as a success marker precisely so clients can detect truncated responses**; an empty line is whitespace to `encoding/json`, so a stream that ends cleanly at a row boundary produces exactly the same `io.EOF` as legitimate completion. `database/sql` treats the `io.EOF` as end-of-rows and the query "succeeds" with a subset of rows.
- **Failure scenario:** A long-running export or high-cardinality dashboard query streams through an intermediary that terminates the response early but cleanly; the user gets a numerically plausible but wrong result (or a truncated export) with no error anywhere. Trigger caveat (why confidence is medium): an *abrupt* connection cut mid-chunked-response surfaces as `io.ErrUnexpectedEOF` from Go's HTTP transport and does fail the query; the silent case requires a proxy/LB that forges proper stream termination (or close-delimited responses), which some do on upstream timeout. The marker check is still the documented, cheap defense.
- **Recommendation:** Track whether the trailing blank line was observed before EOF (read the raw stream, or switch to `objectLines` and apply the same check) and return an error from `Next` when the success marker is missing.

### deep-connectors-11 [MEDIUM] BigQuery detects partial writes ("not all rows written") but returns success anyway
- **Category:** data-loss  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/bigquery/warehouse.go:308-310` (parquet path) and `:354-356` (JSON path)
- **Problem:** After draining the Arrow reader / row iterator, `Next`/`downloadAsJSONFile` compare rows written against `f.bqIter.TotalRows` and, on a shortfall, emit `logger.Error("not all rows written to parquet file", ...)` — then **return the file as a successful result**. The condition exists precisely because the storage-read stream can end early without surfacing an error, i.e. the code detects data loss and proceeds.
- **Failure scenario:** A storage-read stream ends prematurely; the model ingests, say, 8.7M of 10M rows; the reconciler records success; dashboards silently under-report. Only someone reading runtime error logs would notice.
- **Recommendation:** Return an error when `rows < TotalRows` (both paths). If there are known benign cases (e.g. `TotalRows` being an estimate for certain query shapes), gate the check on the exact-count cases and document it.

### deep-connectors-12 [MEDIUM] rduckdb generic `acquireConn` leaks the pooled connection when `USE` fails (MotherDuck/external DuckDB)
- **Category:** bug  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/pkg/rduckdb/generic.go:538-556`
- **Problem:** `acquireConn` gets `conn` from the pool via `m.db.Connx(ctx)`, then runs `USE <db>` / `USE <schema>`. If either `ExecContext` fails, it returns `nil, err` **without `conn.Close()`** — the `sql.Conn` is never returned to the pool. The pool has no `MaxOpenConns` limit, so each failure creates a new connection on the next call while the leaked ones accumulate.
- **Failure scenario:** A MotherDuck outage or detached database makes `USE mydb` fail; every read (`AcquireReadConnection`), `Schema`, `DDL`, and every write op leaks one connection per attempt for the duration of the incident; dashboards polling against the connector accumulate hundreds of dangling conns (each holding driver-side state) that are never reclaimed.
- **Recommendation:** `defer`-close on error: on any failure after `Connx` succeeds, `_ = conn.Close()` before returning.

### deep-connectors-13 [MEDIUM] rduckdb dirty-flag protocol: failed background pulls are marked clean, and meta-write failures return success without updating the catalog — stale reads served indefinitely
- **Category:** correctness  **Confidence:** high (code) / medium (trigger)  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/pkg/rduckdb/db.go:746-751` (monitor), `:470-474` (`CreateTableAsSelect`), `:562-566` (`MutateTable`), `:715-719` (`RenameTable`)
- **Problem:** Two interacting defects. (a) `localDBMonitor` runs `pullFromRemote` and then sets `d.localDirty = false` **unconditionally, even when the pull failed** (`:746-751`); since `pullFromRemote` short-circuits on `!d.localDirty` (`remote.go:25`), a single failed pull permanently disables re-sync — subsequent write ops *also* skip their initial pull. (b) In `CreateTableAsSelect`/`MutateTable`, if `writeTableMeta` fails after a successful remote push, the function **returns success** without calling `catalog.addTableVersion` (`:470-474`, `:562-566`) — the "background goroutine will eventually sync" comment relies on the monitor, which (a) can permanently disarm; and with `remote == nil` (every local Rill Developer project) there is nothing to sync from at all, so the new data is never served.
- **Failure scenario:** Local dev: disk-full/transient FS error on the tiny `meta.json` write after a large successful ingest → the model shows "succeeded" but dashboards keep serving the previous version until the next write or restart (with `remote == nil` the "background sync" comment is vacuous — nothing ever retries). Cloud: a transient pull failure in the monitor permanently clears the dirty flag, so the same stale state persists until a write to that specific table. Note (a) is also load-bearing for -02: after the monitor's failed pull poisons the catalog and clears `localDirty`, nothing ever re-pulls to reconcile.
- **Recommendation:** In the monitor, only clear `localDirty` when the pull succeeded. In the write ops, treat `writeTableMeta` failure as an error (the remote is already consistent; returning the error lets the reconciler retry and heal), or at minimum still call `addTableVersion` (the meta is in memory) and leave `localDirty = true`.

### deep-connectors-14 [MEDIUM] Incremental DuckDB refreshes copy the entire table file and re-upload it whole
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/pkg/rduckdb/db.go:512-518` (`MutateTable` → `copyDir`), `runtime/pkg/rduckdb/io.go:44-65` (`copyFile` = plain `io.Copy`), `runtime/pkg/rduckdb/remote.go:204-234` (`pushToRemote` uploads every file in the version dir)
- **Problem:** `MutateTable` (the path for incremental model refreshes) creates the new version by byte-copying the previous version's entire `data.db` (`copyDir` → `io.Copy` — no reflink/clonefile even on filesystems that support CoW), applies the mutation, and then `pushToRemote` uploads the **entire** new file to object storage. Write amplification is therefore O(table size) per refresh regardless of delta size.
- **Perf impact:** A 50 GB table with a 1-minute incremental append pays 50 GB of local disk I/O (copy) + 50 GB of network upload per refresh — the mutation itself is a rounding error. Refresh latency and infra cost scale with total table size, not increment size; the `writeSem` is held throughout, blocking all other writes.
- **Recommendation:** Short-term: use `clonefile`/`FICLONE` (reflink) when available for the local copy — it is near-instant on APFS/XFS/Btrfs. Medium-term: skip the pre-copy by mutating a hard-linked WAL-isolated copy, and/or make replication incremental (upload only changed blocks or use DuckDB `EXPORT`/attach-diff). At minimum document the cost so users size `Last`/partitions accordingly.

### deep-connectors-15 [MEDIUM] ClickHouse file ingestion buffers the whole file in memory — twice
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/clickhouse/model_executor_filestore_self.go:151-162`
- **Problem:** For each local/HTTPS file, the executor does `contents, _ := os.ReadFile(path)` and then builds `query := "INSERT INTO ... FORMAT ...\n" + string(contents)` — the full file is held in memory once as `[]byte` and again as part of the concatenated query string, then sent as a single statement.
- **Perf impact:** A 2 GB CSV → ~4 GB transient allocations per file (plus driver-side buffering); multiple concurrent file ingests (`Concurrency` returns `_defaultConcurrentInserts`) multiply this. Large files can OOM the runtime pod outright.
- **Recommendation:** Stream the file: use clickhouse-go's block-append API, or POST the file body via the HTTP interface with `io.Reader`, or chunk the INSERT into bounded batches.

### deep-connectors-16 [MEDIUM] HTTPS `FilePaths` temp file is never deleted by its consumers — one full-size orphan per refresh
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/drivers/https/https.go:277`; `runtime/pkg/fileutil/fileutil.go:38-40`; consumer `runtime/drivers/clickhouse/model_executor_filestore_self.go:104`
- **Problem:** `FilePaths` downloads the URL to a temp file via `fileutil.CopyToTempFile(resp.Body, "", extension)` — whose doc comment says "**The caller must delete**" — and passes `""` as the directory, so the file lands in the OS temp dir, *not* the instance-scoped temp dir that gets wiped. The consumer (`clickhouse` fileStore executor) never removes `localPaths` (it cannot blindly do so, because for the `file` driver the same interface returns the user's own files). Result: every refresh of an HTTPS-sourced ClickHouse model leaks one full-size file in `/tmp` until reboot. (The DuckDB driver avoids this path by reading HTTPS directly via httpfs.)
- **Recommendation:** Extend the `FileStore` contract to signal ownership (e.g. `FilePaths` returns an `ownsFiles bool` or a cleanup func); have `https` place files under `storage.TempDir()` so instance GC reclaims them; delete after ingest when owned.

### deep-connectors-17 [LOW] rduckdb generic `RenameTable` interpolates unescaped identifiers
- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/pkg/rduckdb/generic.go:416`
- **Problem:** `fmt.Sprintf("ALTER %s %s RENAME TO %s", typ, oldName, newName)` uses raw names, while the sibling `dropTableUnsafe` (`:326`) and the rduckdb main implementation consistently use `safeSQLName`. Model names derive from file names and may be reserved words (`order`, `table`) or contain characters requiring quoting (`my-model`).
- **Failure scenario:** On MotherDuck/external DuckDB, renaming a model file `order.sql` → `orders.sql` fails with a parser error ("syntax error at or near order"), leaving the old table in place; names with quotes could inject SQL (self-inflicted — the author already runs arbitrary SQL).
- **Recommendation:** Wrap both names in `safeSQLName` like every other statement in the package.

### deep-connectors-18 [LOW] blob and rduckdb retry helpers only retry GCS HTTP/2 stream errors — all other transient failures abort multi-GB work
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/pkg/blob/download.go:323-340`; `runtime/pkg/rduckdb/remote.go:302-320`
- **Problem:** Both `retry` helpers retry only when `err.Error()` contains `"stream error: stream ID"` (a GCS HTTP/2 quirk). S3/Azure 5xx, connection resets, TLS hiccups, and DNS blips fail immediately. The retry delay is a flat 10 s (no jitter/backoff). In `blob.Download`, one failed object download cancels the whole errgroup, so the entire glob ingest restarts from zero on the next reconcile attempt (all previously downloaded files discarded); in rduckdb, `pushToRemote`'s un-retried meta upload failure is what arms finding -02.
- **Perf impact:** For a 100 GB glob ingest, a single transient S3 500 at file 900/1000 discards ~90 GB of completed downloads and repeats them on the reconciler's retry.
- **Recommendation:** Retry on standard transient classes (HTTP 5xx/429, `net.Error` timeouts, connection reset) with jittered exponential backoff; gocloud surfaces `gcerrors.Code` for this. Consider per-file retry independence so one file's failure doesn't cancel completed work.

### deep-connectors-19 [LOW] rduckdb read acquisition serializes on `metaSem` + a `USE` round trip per query; first read after every write replays full `attachTables` while holding it
- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/pkg/rduckdb/db.go:329-349` (`AcquireReadConnection`), `:1235-1263` (`prepareSnapshot`), `:1167-1179`/`:1265-1274` (background DETACH/DROP SCHEMA also under `metaSem`); caller `runtime/drivers/duckdb/duckdb.go:694-711`
- **Problem:** Every DuckDB query (`acquireOLAPConn`/`acquireMetaConn` → `rduckdb.AcquireReadConnection`) acquires the weight-1 `metaSem` and executes `USE main_<snapshot>` before the actual query — an extra serialized statement per query. Worse, every write increments the snapshot, and the *first* read of a new snapshot runs `CREATE SCHEMA` + `USE` + `attachTables` (1 `ATTACH` + 1 `CREATE VIEW` per table, ~2N statements) while holding `metaSem`, blocking **all** concurrent read acquisitions. Background `removeTableVersion` (DETACH) and `removeSnapshot` (DROP SCHEMA CASCADE) also take `metaSem`, inserting stalls between queries. The read pool itself (`dbHandle`) has default `MaxIdleConns=2` with `pool_size` up to 5, so bursts churn connections (each new conn re-runs `ConnInitQueries`).
- **Perf impact:** With ~100 tables, the post-write stall is ~200 serialized statements (tens to hundreds of ms) applied to the unlucky first dashboard query after every model build/refresh, plus queueing for all concurrent queries. Steady-state overhead is one `USE` round trip + one semaphore handoff per query (sub-ms each, but on every query).
- **Recommendation:** Pre-warm the new snapshot's schema at write-completion time (build it under `metaSem` *before* flipping `currentSnapshotID`) so readers never pay `attachTables`; skip the `USE` when the pooled conn already sits on the right schema (track last-used snapshot per conn); set `SetMaxIdleConns(pool size)` on `dbHandle`.

### deep-connectors-20 [MEDIUM] rduckdb `pullFromRemote` returns `errNotFound` after successfully cataloging a newly-discovered table — aborts the pull and fails the calling write op
- **Category:** bug  **Confidence:** high  **Novelty:** new  **Must-fix:** no  **Location:** `runtime/pkg/rduckdb/remote.go:165-172`
- **Problem:** In the catalog-update loop, when `d.catalog.tableMeta(table)` returns `errNotFound` for a table discovered in remote, the code correctly calls `d.catalog.addTableVersion(table, remoteMeta, true)` — and then falls through to `return err`, returning `errNotFound` from `pullFromRemote` instead of `continue`-ing. The pull aborts (remaining remote tables never reach the catalog), and the calling write op (`CreateTableAsSelect`/`MutateTable`/`DropTable`/`RenameTable` all run `pullFromRemote(ctx, true)` first) fails with a cryptic `rduckdb: not found`. Each retry advances past exactly one new table (it was added before the return), so N new tables need N failed attempts to converge. The `addTableVersion` also performs no local-file validation, which is the exact insertion point that poisons the catalog in the -02 corruption scenario.
- **Failure scenario:** Any catalog-updating pull that discovers a table absent from the in-memory catalog: a replica syncing tables written by another node, or recovery flows after -02/-13. The first write op after such a discovery errors spuriously; with a corrupted remote (-02) this same line converts "one table missing" into "whole instance unqueryable".
- **Recommendation:** `continue` after the `errNotFound` branch and only `return err` for other errors; before cataloging a pulled table, verify its data files exist locally (reuse `d.tableMeta`'s stat) and skip+log otherwise.

## Performance Notes

Ranked latency/throughput contributors found on the traced hot paths (with rough cost):

1. **Per-page cloud-client rebuild in object-store listing** (-06): up to ~0.5 s of pure overhead per 1000-object page (AssumeRole + GetBucketRegion + TLS) on partition discovery, connector browsing, and AI bucket tools; the single biggest connector-side latency win.
2. **Postgres `MaxOpenConns=1` default** (-07): dashboard load time degrades from ≈max(query) to Σ(queries) — 5-10× on typical explore pages.
3. **Incremental DuckDB refresh = full copy + full upload** (-14): O(table size) disk + network per refresh; dominates refresh latency for large tables; holds the write semaphore throughout.
4. **rduckdb post-write `attachTables` replay + per-query `USE` under `metaSem`** (-19): tens-hundreds of ms first-query stall after every write; per-query serialized round trip in steady state.
5. **Druid spurious cancel DELETE per query** (-09): +1 broker round trip and goroutine per query attempt (~2× broker HTTP request volume).
6. **ClickHouse file ingest double-buffering** (-15): 2× file size in transient memory per file; OOM risk over ~1-2 GB files.
7. **Narrow retry conditions** (-18): a single transient failure discards a whole glob download (up to the full dataset) and repeats it on reconciler retry.
8. **MySQL/Snowflake unbounded pools + 2-idle default** (-08): connection storms under burst, then full re-handshake next burst.
9. **Per-model-build metrics-callback accumulation** (-05): metrics collection cost grows linearly with total historical builds on a long-lived runtime.
10. Minor: `blob.Download`'s up-front `CollectAll` listing (covered by drivers-object-store-11); Athena double `GetWorkGroup` (drivers-object-store-13); Pinot buffers whole broker responses in memory (inherent to the client; bounded by broker limits).
