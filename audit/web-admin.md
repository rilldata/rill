# Web Admin (Cloud Frontend) — Code Review

**Scope:** `web-admin/src` — features (billing, embeds, public-urls, view-as-user, edit-session, projects, organizations, authentication, bookmarks, scheduled-reports, dashboards) and the `/-/embed`, `/[organization]`, and billing routes. Also traced into the directly-consumed `web-common` embed RPC (`lib/rpc.ts`), embed store, feature-flags singleton, date-picker, and runtime-client v2 where the web-admin flows depend on them.  |  **Health:** fair

## Overview
The cloud frontend is a SvelteKit SPA (`ssr = false`), so the module-level singletons (`EmbedStore`, `viewAsUserStore`, `featureFlags`, RPC method registry) are per-tab and do not leak across users — the most dangerous class of bug for this code is therefore avoided. Code quality is generally good: project polling uses well-considered smart-backoff intervals that stop when reconciliation ends, and the project layout thoughtfully juggles three auth modes (cookie / bearer-token / mock). The most significant issue is an open redirect in the billing upgrade callback (attacker-controllable `redirect` param navigated with no allowlist). The "View As" impersonation feature has two correctness gaps — one narrower than first assessed — that can undermine its security-testing purpose. The embed surface has a discarded-cleanup leak and a dead conditional, both low-impact in the standalone-iframe deployment. Most other items are minor UX or simplification issues.

## Findings

### web-admin-01 [HIGH] Open redirect through unvalidated `redirect` query param
- **Category:** security  **Confidence:** high  **Location:** `web-admin/src/routes/[organization]/-/upgrade-callback/+page.svelte:34,97-100`, `web-admin/src/features/billing/plans/upgrade-to-plan.ts:54-58`, `web-admin/src/routes/-/auth/device/+page.svelte:17,30-31`
- **Problem:** The billing upgrade callback reads `redirect = $page.url.searchParams.get("redirect")` and, after the upgrade attempt, executes `window.open(redirect, "_self")` with no allowlist or same-origin check (the comment documents that the value "could be on a different domain like the rill developer instance"). The same unvalidated value flows through `ChoosePlanDialog` → `upgradeToPlan(...)` → `window.open(redirect, "_self")`. The device-auth page does the same with `window.location.href = decodeURIComponent(redirectURL)`. Verified that `getBillingUpgradeUrl` (`selectors.ts:79-90`) only ever builds a same-origin `/<org>/-/upgrade-callback` URL and never sets `redirect`, so nothing internal legitimately populates `redirect` — the value arrives only from external deep links and is fully caller-controllable.
- **Failure scenario:** An attacker sends an authenticated Rill user `https://ui.rilldata.com/<org>/-/upgrade-callback?redirect=https://evil.example&plan=<self-serve-plan>`. `upgrade()` runs on mount; when the org has no payment issues and the plan resolves, the subscription mutation is attempted inside a `try/catch` that swallows errors, and `window.open(redirect, "_self")` then fires **unconditionally** (even if the mutation threw) — bouncing the user from the trusted origin to a phishing clone. The device-auth sink is lower-risk because it only fires after a successful `code_confirmed=true` POST, which requires a valid pending `user_code`.
- **Recommendation:** Validate `redirect` against an allowlist of trusted hosts (the app origin plus known Rill Developer/localhost origins) or require same-origin before navigating; reject `javascript:`/`data:` schemes defensively. Centralize this in one `safeExternalRedirect(url)` helper used at all three sinks. Also skip the redirect when the mutation failed. (Note: `window.open("javascript:…","_self")` / `location.href = "javascript:…"` execution is browser-dependent and blocked by most modern browsers, so treat scheme-blocking as defense-in-depth rather than the primary risk; the same-origin phishing bounce is the concrete issue.)

**Verification:** CONFIRMED — `+page.svelte:34` reads `redirect` from the query string; the `try/catch` at lines 72-96 swallows mutation errors and line 97-100 executes `window.open(redirect, "_self")` unconditionally with no origin/allowlist check. Same sink in `upgrade-to-plan.ts:54-58`, and `device/+page.svelte:17,30-31` does `window.location.href = decodeURIComponent(redirectURL)`. `getBillingUpgradeUrl` never populates `redirect`, so the value is fully attacker-controllable.

**Manual Reproduction Steps (for QA):**
1. Log in to Rill Cloud as an admin of an org that is on (or eligible for) a self-serve plan.
2. In the browser address bar, navigate to `https://ui.rilldata.com/<your-org>/-/upgrade-callback?redirect=https://example.org&plan=<any-plan-name>` (any value for `plan` works; an invalid plan short-circuits to the billing page, so use a real self-serve plan name to exercise the full path).
3. Observe the "Upgrading to ... plan..." spinner briefly, then the browser navigates to `https://example.org` — an arbitrary external domain — even though no legitimate flow ever set that parameter, and even if the subscription mutation failed.
4. Expected (secure) behavior: the app should refuse to navigate to a non-allowlisted external host and instead land on `/{org}` or the billing settings page.
5. (Device-auth variant) Start `rill login` from the CLI, and when the browser opens `/-/auth/device?user_code=...`, append `&redirect=https%3A%2F%2Fexample.org` to the URL before clicking "Confirm code". After confirmation the page navigates to `example.org`.

### web-admin-02 [MEDIUM] "View As" can serve the previous user's cached data when switching to a recently-viewed impersonated user
- **Category:** correctness  **Confidence:** medium  **Location:** `web-admin/src/routes/[organization]/[project]/+layout.svelte:196-207,281-290`, `web-common/src/runtime-client/v2/runtime-client.ts:78-89`, `web-common/src/runtime-client/v2/RuntimeProvider.svelte:29-34`, `web-common/src/runtime-client/invalidation.ts:9-24`
- **Problem:** Runtime-query invalidation on impersonation change is driven only by a change in `authContext`. `RuntimeClient.updateJwt` returns `authContextChanged` only when the context string differs, and `RuntimeProvider` invalidates solely when that is true. Runtime query keys are `[ServiceName, methodName, instanceId, request]` (verified in `invalidation.ts:14-15`) — the JWT is injected by the transport interceptor and is **not** part of the cache key — so two mocked users on the same deployment (same host + instanceId) share cache entries. Switching directly from viewing-as A to viewing-as B keeps `authContext === "mock"`, so `updateJwt` reports no change and nothing is invalidated. Note the mitigating path the original review missed: the deployment-credentials query has **no** `keepPreviousData`/`placeholderData`, so a switch to an *uncached* user transiently makes `mockedUserDeploymentCredentials` `undefined` → `mockUser` `undefined` → `authContext` drops to `"user"` for one render, which *does* trigger invalidation. The stale-data window therefore only materializes when B's deployment credentials are already cached (e.g. toggling A→B→A within the ~5-minute gcTime, or re-selecting a recently-viewed user), where `data` resolves synchronously and `authContext` never leaves `"mock"`.
- **Failure scenario:** Admin views the project as user A, switches to user B, then back to A (or re-selects a user whose credentials are still cached). The target user's JWT is installed on the transport, but already-resolved dashboard queries continue to display the other user's row-filtered results until each naturally refetches — so the admin sees one user's session displaying another user's restricted data, weakening the security-policy test the feature exists for.
- **Recommendation:** Include the impersonated user id (or JWT) in the `{#key}` expression in the project layout so `RuntimeProvider` remounts on any user switch, or make `updateJwt` report a change (and invalidate) whenever the JWT itself changes while `authContext === "mock"`. Either fix covers both the cached and uncached cases.

**Verification:** PLAUSIBLE — code mechanics confirmed: the `{#key}` at `+layout.svelte:284` keys only on `host::instanceId` (identical for two mocked users of one deployment); `RuntimeProvider.svelte:30-34` invalidates only when `updateJwt` returns true; `runtime-client.ts:78-89` returns true only when the `authContext` *string* changes ("mock"→"mock" is false, even with a different JWT); and `invalidation.ts:14-15` confirms query keys are `[Service, method, instanceId, request]` with no JWT. The stale-data window is conditional on the target user's `GetDeploymentCredentials` result still being in the TanStack cache (so `authContext` never transits through `"user"`), hence PLAUSIBLE rather than unconditionally CONFIRMED.

**Manual Reproduction Steps (for QA):**
1. As an org/project admin, open a project that has a metrics view with row-level security policies and at least two members (A and B) who see different filtered rows.
2. Open an explore dashboard, click the avatar menu → "View as", and select user A. Note the rows/values shown.
3. Via "View as", switch to user B. Note B's (different) rows.
4. Within ~5 minutes, switch back to user A (or repeat A→B→A quickly).
5. Actual (bug): immediately after the switch, the dashboard still shows the *previous* user's filtered data until individual queries refetch on their own. Expected: all data repaints to the newly selected user's view at once.
6. To make it observable, open devtools → Network and confirm no burst of runtime `QueryService` refetches fires on the second (cached) switch, unlike the first switch.

### web-admin-03 [MEDIUM] "View As" falls back to the real admin's permissions while the mocked permissions are unavailable
- **Category:** correctness  **Confidence:** high  **Location:** `web-admin/src/features/projects/project-runtime.ts:38-39`, `web-admin/src/routes/[organization]/[project]/+layout.svelte:196-203`
- **Problem:** `resolveRuntimeConnection` returns `projectPermissions: mockUser.permissions ?? projectData?.projectPermissions`. In the layout, `mockUser` is constructed as soon as `mockedUserId && mockedUserDeploymentCredentials` are truthy, but its `permissions` field is `$mockedUserProjectQuery.data?.projectPermissions` — a *separate* `GetProject` call authenticated with the mocked user's bearer token that resolves strictly after the credentials query. During that loading window (present on every switch), and permanently if that query errors, `mockUser.permissions` is `undefined`, so the effective permissions fall back to the real admin's. `runtime.projectPermissions` feeds `ProjectHeader`, `ProjectTabs`, and `BranchDeploymentStopped`'s `canManage`, so admin-level affordances render.
- **Failure scenario:** Admin views-as a low-privilege user. Permission-gated affordances (Edit, Share, manage controls) render using the admin's full permissions instead of the restricted user's — the opposite of what the feature demonstrates. If the mocked `GetProject` errors (unverified server-side: whether the admin `GetProject` endpoint accepts a runtime-issued deployment JWT as a bearer token), this state is sticky rather than transient.
- **Recommendation:** When `mockUser` is active, do not fall back to the admin's permissions. Treat missing mocked permissions as empty/loading (render no elevated affordances) until the mocked `GetProject` resolves, and surface an explicit error state if it fails.

**Verification:** CONFIRMED — `project-runtime.ts:38-39` returns `projectPermissions: mockUser.permissions ?? projectData?.projectPermissions` (admin's own permissions). In `+layout.svelte:196-203`, `mockUser` becomes truthy as soon as the credentials query resolves, while `permissions` comes from the separate `mockedUserProjectQuery` (lines 173-183) that is only *enabled* after the credentials arrive — so on every switch there is a window where `mockUser.permissions` is `undefined` and the admin's permissions flow into `ProjectHeader`/`ProjectTabs` (lines 292-305).

**Manual Reproduction Steps (for QA):**
1. As an org admin, open a project that has a viewer-level member (no manage/edit rights).
2. Open devtools → Network and throttle to "Slow 3G" (to widen the loading window).
3. Use "View as" to impersonate the viewer-level user.
4. Actual (bug): during the seconds while the impersonated `GetProject` call is in flight, the header/tabs still render admin-only affordances (e.g. Settings tab, Share/Edit controls) — the admin's permissions, not the viewer's. Expected: no elevated affordances at any point while viewing as a restricted user.
5. (Sticky variant) In devtools → Network, right-click the second `GetProject` request (the one with the mocked bearer token) and block it, then re-select the user: the admin-permission UI persists indefinitely.

### web-admin-04 [LOW] Embed iframe RPC message listener cleanup is discarded
- **Category:** correctness  **Confidence:** high  **Location:** `web-admin/src/routes/-/embed/+layout.svelte:108-113`
- **Problem:** `onMount` calls `createIframeRPCHandler()` — which returns an unsubscribe that removes the global `window` `message` listener — but the return value is discarded. The cleanup actually returned from `onMount` is `initEmbedPublicAPI()`'s, which only unsubscribes the page/eventBus/AI-pane stores; it never removes the RPC message listener.
- **Failure scenario:** In practice the impact is negligible: the embed layout is the root of a standalone iframe document, its `onMount` runs once, and child-route navigations do not remount the layout — so the listener never accumulates and is torn down with the document. The defect only bites if the embed layout is ever mounted/unmounted repeatedly within one long-lived document (embed → non-embed → embed in the shared SPA), where each mount would stack another `message` listener and a single inbound RPC would be answered N times. The discarded cleanup is a latent correctness defect and the clear intent (dispose both) is unmet.
- **Recommendation:** Capture and compose both cleanups, e.g. `const disposeRpc = createIframeRPCHandler(); const disposeApi = initEmbedPublicAPI(); return () => { disposeApi(); disposeRpc(); };`.

**Verification:** PLAUSIBLE — `+layout.svelte:108-113` calls `createIframeRPCHandler()` and discards its return value; `rpc.ts:79-91` shows that return value is the only way to remove the `window` `message` listener; `onMount` returns only `initEmbedPublicAPI()`. The defect is real in the code but latent: the embed layout is the root of a standalone iframe document, so the listener is torn down with the document and never accumulates in practice.

**Manual Reproduction Steps (for QA):**
Not user-reproducible in the current deployment (the embed layout mounts once per iframe document and is never unmounted within a live document). Confirm in code: `web-admin/src/routes/-/embed/+layout.svelte:108-113` — `createIframeRPCHandler()`'s returned unsubscribe function is not captured or returned from `onMount`; compare with `web-common/src/lib/rpc.ts:86-90` where the cleanup removes the global `message` listener.

### web-admin-05 [LOW] `onProjectPage` is always `false` in the embed layout (dead conditional)
- **Category:** correctness  **Confidence:** high  **Location:** `web-admin/src/routes/-/embed/+layout.svelte:43-53,117-122,142`
- **Problem:** `activeResource` is derived with a `?? { kind: ResourceKind.Canvas, name: $page.params.name }` fallback, so it is *always* truthy. `onProjectPage = !activeResource` is therefore always `false`. **Verification:** CONFIRMED — `+layout.svelte:43-49` derives `activeResource` with the `?? { kind: ResourceKind.Canvas, name: $page.params.name }` fallback, making it always truthy; line 51 `onProjectPage = !activeResource` is therefore always `false`; line 53 `showDashboardChat = $dashboardChat && !onProjectPage` reduces to `$dashboardChat`; line 142 `class:border-b={!onProjectPage}` is always applied; and the `{#if activeResource}` title branch (line 117-118) renders `{activeResource.name} - Rill` with `name === undefined` on the listing route.

### web-admin-06 [LOW] Embed RPC handler does not validate `event.origin` and replies with `targetOrigin: "*"`
- **Category:** security  **Confidence:** medium  **Location:** `web-common/src/lib/rpc.ts:64-77,79-91,100-104`
- **Problem:** `createIframeRPCHandler`'s handler accepts any `message` event with a `source` and `data`; there is no `event.origin` check before dispatching to RPC methods. Verified the registered methods (`init-embed-public-api.ts`): `setState` calls `goto(...)` (drives navigation), plus `setThemeMode`/`setTheme`/`setAiPane`; `getState`/`stateChange` emit the dashboard's URL/filter state. All outbound `postMessage` calls (`sendResponse`, `sendError`, `emitNotification`) use `targetOrigin: "*"`. Exploitability is limited because the embed requires an `access_token` in the URL and the parent is the intended controller, so this is primarily a defense-in-depth gap.
- **Failure scenario:** Any frame able to `postMessage` to the embed window can invoke RPC methods; the wildcard target origin means state (filters, theme) is emitted without asserting the recipient origin. Combined with a compromised or multi-origin embedding page this can leak dashboard state or drive navigation.
- **Recommendation:** Accept an expected parent origin (e.g. via an embed param) and validate `event.origin` on inbound messages; use that specific origin as `targetOrigin` on outbound `postMessage` instead of `"*"`.

**Verification:** CONFIRMED — `rpc.ts:80-84` accepts any message with a truthy `source` and `data`, with no `event.origin` check; `sendResponse`/`sendError`/`emitNotification` (lines 66, 75, 102) all post with `targetOrigin: "*"`. Registered methods in `web-admin/src/features/embeds/init-embed-public-api.ts` include `setState` (line 45, drives `goto` at line 51), `getState` (line 40), `setThemeMode`/`setTheme`/`setAiPane` — so any frame that can post to the embed window can read and drive dashboard state.

### web-admin-07 [LOW] Embed layout disables the global `adminServer` feature flag with no restore

- **Recommendation:** Restore the previous flag value in the layout's `onMount` cleanup, or scope the read-only/adminServer state to the embed subtree rather than mutating the global singleton.

**Verification:** PLAUSIBLE — the code facts are confirmed: `-/embed/+layout.svelte:39` runs `featureFlags.set(false, "adminServer")` in the script body with no cleanup, and the root layout sets it `true` only once at init (`routes/+layout.svelte:80`, `featureFlags.set(true, "adminServer", "readOnly")`). ## Product Improvements

## New Feature Ideas
- **Trusted-redirect allowlist utility (S):** A single `safeExternalRedirect()` helper plus a configured allowlist, used by every `window.open`/`location.href` sink. Removes the whole open-redirect class and makes future sinks safe by default. High security value, low effort.
- **View-As banner with "unable to load permissions" state (S):** When impersonating, show whether the mocked permissions/data have fully loaded, and warn if the mocked `GetProject` failed — so admins never mistake a fallback view for the real restricted experience. Directly reinforces the security-testing purpose (findings 02/03).
- **Embed RPC handshake with origin pinning (M):** Add an `allowed_origin` embed param and a `connect` handshake so the iframe validates the parent and scopes all `postMessage` targets. Hardens the embed surface for enterprise customers and enables per-embed telemetry.
- **Public URL management surface improvements (M):** Show expiry countdown, one-click revoke, and "created by / last used" columns in `PublicURLsTable`. Public/magic tokens are a sharing-and-security feature that currently offers little visibility once issued.
- **Billing upgrade idempotency + explicit result (M):** The upgrade-callback mutates on mount and swallows errors; give it an explicit success/failure screen with retry, and make the subscription update idempotent against double-loads/refreshes. Improves trust in a money-moving flow.
