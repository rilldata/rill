# Shared Frontend Features — Code Review
**Scope:** `web-common/src/features/{entity-management, file-explorer, sources, add-data, connectors, exports, alerts, scheduled-reports, themes, visual-metrics-editing, models}` (plus the tightly-coupled `env-management` helpers the add-data flow depends on)  |  **Health:** fair

## Overview
This area covers the file CRUD / rename / delete surface, the add-data import wizard (connector + secret creation, model/metrics/dashboard generation), source detection and upload, the connector explorer, exports, alert/report mutation dialogs, theme injection, and the visual metrics editor. The code is generally well-structured, with thoughtful separation (e.g. `EnvEditSession` for secret allocation, `protected-files` predicates for pinned/managed paths) and several places show real care about async ordering (the AI connector dialog explicitly avoids auto-closing before its save resolves). The biggest risks cluster around **error propagation and async completion**: `renameFileArtifact`/`deleteFileArtifact` swallow failures internally, which defeats the `try/catch` success/failure branching in every caller and produces navigation to non-existent paths. Secondary risks are a **string-compared version gate** that can hang the connector-validation poll loop at digit boundaries, and **`.env` secrets left committed after a failed/abandoned connector attempt** because cleanup only runs on the explicit "Back" path. None of these are catastrophic, but the error-handling one is user-visible on any rename/delete failure. (The theme CSS sanitizer flagged in the initial pass turned out to guard dead code and is not a reachable injection — see fs-shared-03 and the Verification Notes.)

## Findings

### fs-shared-01 [high] `renameFileArtifact` and `deleteFileArtifact` swallow errors, so every caller's `try/catch` treats a failure as success
- **Category:** correctness  **Confidence:** high  **Location:** `web-common/src/features/entity-management/actions/actions.ts:206-232` (rename), `:258-276` (delete)
- **Problem:** Both functions wrap the runtime call in an internal `try/catch` that emits a notification and then returns normally — they never re-throw. But their callers are written as if the functions throw on failure. `RenameAssetModal.onUpdate` (`actions/RenameAssetModal.svelte:105-121`) does `await renameFileArtifact(...); await navigateToFile(newPath); closeModal();` inside a `try/catch`; `handleEntityRename` (`actions/ui-actions.ts:60-66`) does `await renameFileArtifact(...); return getFileHref(newPath)`; `FileExplorer.handleDropSuccess` (`file-explorer/FileExplorer.svelte:151-155`) navigates to `newFilePath` after the await. Because no error propagates, the success path always runs.
- **Failure scenario:** A user renames `foo.yaml` to a name the backend rejects (e.g. a server-side validation/permission error, or a transient controller error). `renameFileArtifact` shows a "Failed to rename" toast but returns normally; `RenameAssetModal` then `navigateToFile("/foo_new.yaml")` — a path that does not exist — and closes the modal. The user lands on a broken/empty editor route while their original file still sits at the old path. The same happens on drag-drop moves and on `deleteFileArtifact` (it navigates `navigateToHome()` after a delete that actually failed).
- **Recommendation:** Have `renameFileArtifact`/`deleteFileArtifact` re-throw after emitting the notification (or return a discriminated result), and let callers gate navigation/`closeModal()` on success. At minimum, only navigate when the operation resolved without error.

**Verification:** CONFIRMED — `renameFileArtifact` catches the error and only emits a notification, never re-throwing (`web-common/src/features/entity-management/actions/actions.ts:227-231`); `deleteFileArtifact` does the same (`actions.ts:271-275`). Callers assume throw-on-failure: `RenameAssetModal.svelte:105-118` navigates and closes the modal after the await, `ui-actions.ts:60-63` returns the new href, and `FileExplorer.svelte:151-154` navigates to `newFilePath` after a drag-drop move. `FileExplorer.svelte:114-117` similarly calls `navigateToHome()` after an un-failable `deleteFileArtifact`.

**Manual Reproduction Steps (for QA):**
1. Start Rill Developer (`rill start`) on a project and open it in two browser windows (A and B).
2. In window A, right-click a file (e.g. `my_model.sql`) in the left file tree and choose Rename; leave the rename dialog open with a new name typed (e.g. `my_model_renamed.sql`).
3. In window B, delete that same file from the file tree.
4. In window A, click Save/confirm in the rename dialog.
5. Expected: the rename fails, the dialog stays open (or shows an error), and you stay where you are. Actual: a "Failed to rename" toast appears, but the dialog still closes and the app navigates to `/files/my_model_renamed.sql`, which does not exist, leaving you on a broken/empty editor route.

### fs-shared-02 [medium] `waitForResourceReconciliation` compares `stateVersion` strings with `>`, hanging the poll at digit boundaries
- **Category:** correctness  **Confidence:** high  **Location:** `web-common/src/features/entity-management/actions/actions.ts:95-111`
- **Problem:** `stateVersion` is an int64 serialized as a `string` (`V1ResourceMeta.stateVersion?: string`, `runtime-client/gen/index.schemas.ts:2392`). The gate `newStateVersion > prevStateVersion` is a lexicographic string comparison, so `"10" > "9"` is `false`. When `prevStateVersion` is supplied and the version crosses a digit-count boundary (9→10, 99→100, …), `newVersionArrived` stays `false`, so the `RECONCILE_STATUS_IDLE && newVersionArrived` success branch never fires and the `while (true)` loop keeps polling every 2s with no attempt cap on that branch. The same gate also suppresses the `reconcileError` branch (line 102), so a genuine reconcile error is not surfaced.
- **Failure scenario:** Only `createConnector` passes `prevStateVersion` (`add-data/manager/steps/connector.ts:98-104,128-134`), and only for an already-existing connector resource. A user re-tests/edits a connector whose `stateVersion` ticks from `"9"` to `"10"`; the validation poll never returns, so the "Test and connect" spinner hangs indefinitely (or a real error is hidden). New connectors are safe because `prevStateVersion` is `undefined`.
- **Recommendation:** Compare as numbers: `BigInt(newStateVersion) > BigInt(prevStateVersion)` (or `Number(...)`). Also consider an overall attempt cap on the still-reconciling branch so the loop can never poll forever.

**Verification:** CONFIRMED — `actions.ts:96-98` does `newStateVersion > prevStateVersion` where both are the string-typed `V1ResourceMeta.stateVersion` (`web-common/src/runtime-client/gen/index.schemas.ts:2392`), so the comparison is lexicographic and `"10" > "9"` is `false`. The success branch (`actions.ts:110`) and error branch (`actions.ts:102`) are both gated on `newVersionArrived`, and the `while (true)` loop (`actions.ts:84`) has no attempt cap on the still-reconciling branch. `prevStateVersion` is passed only from `createConnector` (`add-data/manager/steps/connector.ts:98-104` cached `stateVersion`, passed at `:133`), i.e. only when the connector resource already exists in the query cache.

**Manual Reproduction Steps (for QA):**
Not reliably user-reproducible — hitting it requires an existing connector resource whose cached `stateVersion` is exactly at a digit boundary (e.g. `"9"`) when "Test and connect" is re-run, which QA cannot observe or control from the UI. Best effort: repeatedly re-run the Add Data connector wizard for the same connector name (each reconcile bumps the version) and on roughly the 9th/10th attempt watch for the "Test and connect" spinner never resolving. How to confirm in code: `web-common/src/features/entity-management/actions/actions.ts:96-98` — string `>` on `stateVersion`; unit-test with `prevStateVersion="9"`, `newStateVersion="10"` and assert the success branch fires.

### fs-shared-03 [REMOVED — refuted] Theme CSS sanitizer `}` rule-breakout is not a reachable injection
- **Category:** security → simplification (dead code)  **Confidence:** medium → **refuted as a live vulnerability**  **Location:** `web-common/src/features/themes/css-sanitizer.ts:87-136`; `themes/theme-manager.ts:232-256,348-353`
- **Original claim:** `isSafeVariableValue` does not reject `{`/`}`/`;`, so a theme variable value string-concatenated into a `<style>` (`injectCurrentModeThemeVariables` → `createAndInjectStyle` via `textContent`) could close the rule and inject arbitrary page-wide CSS.
- **Why it is refuted:** The cited injection path is **dead code, and doubly gated even if it were live**:
  1. **Dead code.** The only concatenation-into-`textContent` path is `themeManager.injectCurrentModeThemeVariables` → `createAndInjectStyle`, reachable only from `themeManager.applyTheme`. A whole-repo grep finds **no caller of `applyTheme`** (`web-common/src/features/themes/theme-manager.ts:195` is the sole occurrence); `clearTheme`, `handleCurrentModePrimarySecondary`, and `createAndInjectStyle` are likewise uncalled. `sanitizeThemeVariables` (and thus `isSafeVariableValue`) has no live caller either — its only reference is inside the dead `injectCurrentModeThemeVariables` (`theme-manager.ts:239`). This is folded into fs-shared-12.
  2. **Live path canonicalizes values.** Dashboards apply themes through `ThemeProvider.svelte` (used by `dashboards/workspace/Dashboard.svelte`, `canvas/CanvasDashboardWrapper.svelte`, the embed layout, and chart wrappers), which sets `styleEl.textContent = theme.css`. `theme.css` comes from `Theme.generateCSS()` (`themes/theme.ts:87-106`), which runs every value through chroma-js (`getChroma`) and emits only `--name: <hsl(...)>;` — a raw breakout string never reaches the output.
  3. **Backend validation.** `runtime/parser/parse_theme.go:253-278` (`ThemeColors.validate`) rejects any variable name not in a fixed allowlist and runs every value through `csscolorparser.Parse`. A value like `red; } body { … }` is not a valid CSS color, so the theme fails to reconcile before its spec ever reaches the frontend.
- **Disposition:** Removed as a security finding. The sanitizer's `{`/`}`/`;` gap is real *in isolation* but guards an unused path; the residual value is dead-code cleanup, captured in fs-shared-12. If `applyTheme`/`sanitizeThemeVariables` are ever revived, add the `{`/`}`/`;` guard at that time.

### fs-shared-04 [medium] `.env` secrets are committed before the connector/model operation is confirmed, and cleanup only runs on one specific exit path
- **Category:** security  **Confidence:** medium  **Location:** `web-common/src/features/add-data/manager/steps/connector.ts:112-166`; `connectors/ai/saveAiConnector.ts:87-100`; `add-data/manager/steps/import.ts:218-251`
- **Problem:** `createConnector` calls `envEditSession.commit()` (writes secrets to `.env`) and `runtimeServicePutFile` (writes `<connector>.yaml`) *before* validation; when validation throws (`connector.ts:143`) the `catch` re-throws but performs no rollback. `saveAiConnector` commits secrets at `:87` then writes the YAML and updates `rill.yaml` at `:90-98` with no rollback if a later step fails. Rollback (`maybeDeleteConnector` → delete file + `envEditSession.rollback()`) is wired only to the explicit "Back" button (`ConnectorForm.svelte:100-110`). Dismissing the surrounding dialog (`AddDataModal.svelte:17-27` just flips `open`/`showForm`) or cancelling after a failed save leaves the committed secret and the broken YAML in the project. `connectorFormCache` is never cleared (only per-id `delete`, `connector.ts:349-356`), so the in-memory `EnvEditSession` (holding the plaintext secret) is retained for the page lifetime.
- **Failure scenario:** A user enters a real API key, clicks "Test and connect", the test fails, and instead of "Back" they close the modal. The key stays in `.env` and a non-reconciling `<connector>.yaml` stays in the project, with no UI indication either exists. On Cloud these are pushed with the project.
- **Recommendation:** On any terminal failure/abandon (dialog close, unmount, cancel-after-failed-save), run the same cleanup as "Back" (`maybeDeleteConnector` + `envEditSession.rollback()`), e.g. from an `onDestroy`/effect-teardown guarded on "not successfully saved". Clear `connectorFormCache` when the add-data flow closes.

**Verification:** CONFIRMED, with one correction. Note that committing secrets *before* validation is by design — the runtime reads `.env` to actually test the connection — so the real defect is the **cleanup gap**, not the commit ordering. `createConnector` runs `envEditSession.commit()` then `runtimeServicePutFile` before validation (`add-data/manager/steps/connector.ts:112-119`), and its `catch` (`connector.ts:156-166`) only re-wraps and re-throws with no rollback. `ConnectorForm.onUpdate` (`ConnectorForm.svelte:45-66`) catches that error and only shows it — no cleanup. `maybeDeleteConnector` (+ `envEditSession.rollback()`, `connector.ts:169-190`) is invoked only from `cleanupAndBack`, wired to the "Back" button (`ConnectorForm.svelte:100-110,122`). Dismissing the dialog just flips `open`/`showForm` (`AddDataModal.svelte:17-20`, `handleDialogClose`) with no cleanup. `saveAiConnector` commits at `connectors/ai/saveAiConnector.ts:87` then writes the YAML and `rill.yaml` at `:90-98`; `AddAiConnectorDialog.handleSave` (`:137-175`) `catch` shows an error but never rolls back, so a partial write leaks. `connectorFormCache.clear()` is called only in a spec file (`AddDataStateManager.svelte.spec.ts:181`); product code uses only per-id `delete`.

**Correction to the initial pass:** `import.ts` is *not* entirely without rollback. `cleanupImportStep` (`import.ts:117-137`) deletes the generated files and calls `config.envEditSession.rollback()`, and `GenerateDashboardStatus.svelte:117-121` wires it to the error-state "Back" button (`cleanupAndBack`). The gap there is narrower: "Skip and view project" (`GenerateDashboardStatus.svelte:123-127`) and dialog dismissal bypass cleanup, and the sibling `ImportDataStatus.svelte` (which also calls `runImportSteps` → `runCreateModelStep` → `envEditSession.commit()`) has **no** cleanup wiring at all. So the leak on non-"Back" exits still holds, but the connector flow (createConnector/saveAiConnector) is the primary, common trigger.

**Manual Reproduction Steps (for QA):**
1. In Rill Developer, open Add Data and pick a credentialed connector (e.g. ClickHouse or Postgres).
2. Fill in the form with a recognizable fake secret (e.g. password `LEAKED_TEST_SECRET_123`) and an unreachable host, then click "Test and connect".
3. Wait for the connection test to fail and show an error.
4. Do NOT click "Back"; instead dismiss the dialog (press Escape or click outside it).
5. Open the project's `.env` file and the `connectors/` folder in the file tree.
6. Expected: no trace of the failed attempt. Actual: `.env` contains a new entry with `LEAKED_TEST_SECRET_123`, and a non-reconciling `connectors/<name>.yaml` remains in the project with no UI indication; both would be pushed on deploy.

### fs-shared-05 [low] `uploadFile` interpolates the raw file name into the upload URL without encoding
- **Category:** correctness  **Confidence:** high  **Location:** `web-common/src/features/sources/modal/file-upload.ts:18-27`
- **Severity note (verifier):** Downgraded medium → low. The URL parser inside `fetch` percent-encodes spaces and most punctuation, so the practically-breaking characters are `#` (starts a fragment), `?` (starts a query), and stray `%`; these are uncommon in data filenames and the operation fails loudly (upload error or a reconcile error from the mismatched name) rather than corrupting existing data. Reachable — `SourceForm.svelte:126-129` and `refreshSource.ts:39` pass the raw `File` with an unmodified `file.name`.
- **Problem:** `const filePath = \`data/${file.name}\`` is inlined into `\`${host}/v1/instances/${id}/files/upload/-/${filePath}\`` with no `encodeURIComponent`. File names containing URL-significant characters (`#`, `?`, `%`, spaces) corrupt the path.
- **Failure scenario:** A user uploads `report #1.csv`. The `#1.csv` becomes a URL fragment, so the server receives path `data/report ` — the upload lands at the wrong path or fails, and the generated source YAML (`compileLocalFileSourceYAML(filePath)`) then references a name that does not match what was stored. (Browsers strip directory components from `file.name`, so this is a robustness/correctness bug, not a traversal.)
- **Recommendation:** Encode each path segment (`encodeURIComponent(file.name)`) when building the URL, and keep the un-encoded name only for display / YAML where appropriate.

**Verification:** CONFIRMED — `web-common/src/features/sources/modal/file-upload.ts:18` builds `const filePath = \`data/${file.name}\`` and line 21 interpolates it directly into the fetch URL with no `encodeURIComponent`; a `#` in the name becomes a URL fragment and `?`/`%` corrupt the path.

**Manual Reproduction Steps (for QA):**
1. On your machine, create a small valid CSV named `report #1.csv`.
2. In Rill Developer, open Add Data and choose the local file option, then select `report #1.csv`.
3. Expected: the file is uploaded to `data/report #1.csv` and the generated source/model reconciles. Actual: everything after `#` is treated as a URL fragment, so the server receives a truncated path (`data/report ` or similar); the upload lands at the wrong path or fails, and the generated YAML references a file name that does not match what was stored, producing a reconcile error.
4. Repeat with a file named `sales%20q1.csv` to observe the `%`-decoding variant.

### fs-shared-11 [low] `maybeUnsetOlapConnectorInYaml` builds a `RegExp` from an un-escaped connector name; `replace*InYAML` use un-escaped replacement strings
- **Category:** correctness  **Confidence:** low  **Location:** `web-common/src/features/connectors/code-utils.ts:355-365` (regex), `:342-353,386-397` (replacement)
- **Problem:** `new RegExp(\`^\\s*olap_connector:\\s+${connectorName}\\s*$\`, "m")` interpolates the name into a pattern; regex metacharacters would be interpreted. `blob.replace(regex, \`olap_connector: ${newConnector}\`)` uses a string replacement, so `$`-sequences in the name (`$&`, `$1`) would be interpreted specially. ## New Feature Ideas
- **Trash / undo for file delete & rename (S–M):** soft-delete files to a recoverable `.trash` area (or an in-session undo toast). Directly mitigates the blast radius of fs-shared-01 and the force-delete flow; high user value given deletes are one-click from the nav tree.
- **Multi-select file operations (M):** the file explorer supports one-at-a-time rename/duplicate/delete only. Shift/ctrl multi-select with bulk move/delete (and a single confirmation) is a common expectation for a file tree.

- **Connector "test connection" with explicit cleanup (M):** run validation against a temp/in-memory connector spec before committing secrets and files, so a failed test never leaves artifacts behind — turning fs-shared-04 into a non-issue by construction.
- **Theme live-preview + validation in the editor (M):** surface skipped/unsafe CSS variable values (currently only a `console.warn`) as inline editor warnings, and preview the applied palette, so authors see exactly what was rejected and why.
- **`.env` secret manager view (S–M):** a project settings panel listing which `.env` keys are referenced by which connectors, flagging orphaned secrets (like those left by fs-shared-04) with a one-click remove.
