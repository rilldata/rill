# Admin Billing, Provisioners & Jobs — Code Review

**Scope:** `admin/billing/**`, `admin/provisioner/**`, `admin/jobs/**`, `admin/metrics.go`, `admin/billing.go`, `admin/used_flusher.go` (plus call sites in `admin/provision.go`, `admin/server/provision.go`, `admin/deployments.go`, `admin/jobs/org_jobs.go`, and the `static_runtime_assignments` DB layer for tracing)  |  **Health:** needs-attention

## Overview
This area covers the Orb-backed billing lifecycle (trials, subscriptions, credit grants, invoices, webhooks), the runtime/ClickHouse provisioners (static slots, `clickhouse-static` multi-tenant DBs, Kubernetes), and the River background-job fleet that drives trial/grace-period/hibernation state machines and usage reporting. The code is generally careful: webhook signatures are verified, most jobs are idempotent via River unique keys, and trial/credit flows have explicit "already done" guards. The biggest risks are concentrated in two places: (1) the `clickhouse-static` provisioner truncates the only unique component of a database name, which can collide when org/project names are long and cause data loss on deprovision (and, in narrower cases, cross-tenant access); and (2) static runtime slot allocation performs an unserialized read-then-write, allowing slot overcommit. Secondary risks are a handful of job workers whose retry/partial-failure paths are not fully idempotent (hibernation abandoned after a committed state transition; emails emitted inside an open DB transaction) and unbounded "first 100 projects" loops in org teardown/hibernation. Concurrency in `used_flusher` shutdown is fragile but low-impact.

## Findings

### abp-01 [HIGH] `clickhouse-static` truncates the unique resource ID out of the database name, causing collisions

**Status (2026-07-25):** ✅ Fixed and merged in [#9683](https://github.com/rilldata/rill/pull/9683).

- **Category:** security  **Confidence:** high  **Location:** `admin/provisioner/clickhousestatic/provisioner.go:335-350` (used at `:146` create, `:182` grant, `:275` drop)
- **Problem:** `generateDatabaseName` builds `rill_<org>_<project>_<resourceID>` and then blindly truncates to 63 bytes with `name[:63]`. Because the resource ID (the only globally-unique component) is appended **last**, it is exactly what gets cut off when the org/project prefix is long. The repo's own test documents this: input id `very_long_resource_id_..._12345678` yields `rill_verylongorganizationname_verylongprojectname_verylongresou` — the ID is gone. The per-resource `user` is built as `rill_<full sanitized resourceID>` (`:136`) and is **not** truncated, so it stays unique. Provisioning does `CREATE DATABASE IF NOT EXISTS <name>` and then `GRANT ... ON <name>.* TO <user>`, so two resources whose names truncate identically get **distinct users granted on the same shared database**.
- **Reachability:** Requires the sanitized `org + project` prefix to be long enough to truncate the 32-char resource ID. There is no server-side length cap on org/project names (`CreateOrganizationRequest.name`/project name are `min_len = 1` only in `proto/rill/admin/v1/api.proto`, and the `orgs`/`projects` name columns are bare `TEXT` in `migrations/0001.sql`), so long names are possible. The most reachable harm is **same-tenant**: the ClickHouse resource is keyed per-deployment (`admin/server/provision.go:52,72` → new `uuid.New()` per deployment in `admin/provision.go:75`), so a redeploy of a project with a long `org+project` prefix produces a new resource ID that truncates to the *same* database name as the previous deployment. Deprovisioning the old deployment then runs `DROP DATABASE IF EXISTS <shared name>` (`:275`), destroying the live deployment's data. Cross-project (same org) and cross-org collisions are also possible but require the org/project prefix (or a shared org prefix) to survive truncation identically, which is less likely.
- **Recommendation:** Never truncate away the uniqueness. Reserve a fixed suffix for a deterministic hash of `r.ID` (e.g. truncate the human-readable org/project prefix, then always append `_<first 12 hex of sha256(r.ID)>`), or key on the full sanitized `r.ID`. Add a collision test with long org/project names asserting distinct names for distinct IDs.

**Verification:** CONFIRMED — `generateDatabaseName` (`admin/provisioner/clickhousestatic/provisioner.go:335-350`) appends the resource ID last and then truncates with `name[:63]`, so long org/project prefixes cut off the only unique component; the untruncated per-resource user is built at `:136`, provisioning uses the name at `:146`/`:182`, and deprovision runs `DROP DATABASE IF EXISTS` on it at `:275`. The existing test (`provisioner_test.go`) shows the ID fully truncated away for long inputs.

**Manual Reproduction Steps (for QA):**
1. On a staging Rill Cloud environment configured with a `clickhouse-static` provisioner, create an organization and project whose combined sanitized names exceed ~58 characters (e.g. org `verylongorganizationnameforcollisiontesting`, project `verylongprojectnameforcollisiontesting`), and deploy the project so a ClickHouse database is provisioned.
2. Connect to the ClickHouse cluster as an admin and run `SHOW DATABASES LIKE 'rill_%'`; note the database name is exactly 63 characters and does not end with the deployment's resource ID.
3. Redeploy the project (e.g. hibernate and wake it, or trigger a redeploy that creates a new deployment) so a second ClickHouse resource with a new resource ID is provisioned.
4. Run `SHOW DATABASES LIKE 'rill_%'` again: only one database exists for both deployments (the names truncated identically), and `SHOW USERS` shows two distinct `rill_<id>` users.
5. Deprovision/tear down the old deployment (e.g. delete it or let cleanup run), then query the new deployment's dashboard: its data is gone because `DROP DATABASE` removed the shared database.

### abp-02 [HIGH] Static runtime slot allocation is a TOCTOU race (not serialized) → slot overcommit
- **Category:** concurrency  **Confidence:** high  **Location:** `admin/provisioner/static/static.go:93-122`
- **Problem:** `Provision` calls `ResolveStaticRuntimeSlotsUsed` (a plain `SELECT host, SUM(slots) ... GROUP BY host`, `admin/database/postgres/postgres.go:821-828`), filters hosts with free capacity in memory, then writes `UpsertStaticRuntimeAssignment` (a plain `INSERT ... ON CONFLICT`, `:794-810`). There is no transaction, `SELECT ... FOR UPDATE`, or advisory lock spanning the read and the write, and the call site (`admin/provision.go:106`, reached from `admin/deployments.go:743-758`) invokes this without any external lock. Provisioning runs concurrently (River `MaxWorkers: 10`, and `ProvisionerMaxConcurrency` up to 30), so concurrent provisions can observe the same "slots used" snapshot.
- **Failure scenario:** A host has 8 free slots. Two deployments provision 6 slots each at the same time. Both read `used` showing 8 free, both select that host, both upsert → 12 slots committed onto an 8-slot host. The runtime is silently overcommitted (memory/CPU limits exceeded → OOM/contention), and the capacity `Check` only warns after the fact.
- **Recommendation:** Serialize allocation: wrap the resolve+upsert in a single transaction with `SELECT ... FOR UPDATE` on the affected host rows, take a Postgres advisory lock keyed on the provisioner, or push the capacity check into the `INSERT ... WHERE (SELECT SUM(slots) ...) + $slots <= capacity` statement so the DB enforces the invariant atomically.

**Verification:** CONFIRMED — `Provision` (`admin/provisioner/static/static.go:93-122`) reads `ResolveStaticRuntimeSlotsUsed` (plain `SELECT ... SUM(slots) ... GROUP BY host`, `admin/database/postgres/postgres.go:821-828`), filters in memory, then calls `UpsertStaticRuntimeAssignment` (plain `INSERT ... ON CONFLICT`, `postgres.go:794-810`) with no transaction or lock spanning the two; concurrency is real (`MaxWorkers: 10` in `admin/jobs/river/river.go:182`, `ProvisionerMaxConcurrency` default 30 in `cli/cmd/admin/start.go:60`).

**Manual Reproduction Steps (for QA):**
1. On a staging environment using the `static` runtime provisioner, configure a single runtime host with a small capacity (e.g. 8 slots) in the provisioner spec.
2. Simultaneously deploy two projects that each request more than half the capacity (e.g. 6 slots each) — for example, run two `rill project deploy`/redeploy operations for two different projects at the same moment (a script firing both API calls in parallel is the most reliable way).
3. After both deployments succeed, query the admin Postgres database: `SELECT host, SUM(slots) FROM static_runtime_assignments GROUP BY host;`.
4. Observe the summed slots exceed the host's configured capacity (e.g. 12 > 8), confirming overcommit. Note: timing-dependent; repeat step 2 several times if both provisions do not overlap on the first try.

### abp-03 [MEDIUM] `CreditBalanceDepletedWorker` abandons project hibernation on retry after committing the issue swap
- **Category:** correctness  **Confidence:** medium  **Location:** `admin/jobs/river/credit_balance_event_handlers.go:110-201`
- **Problem:** The worker (a) confirms the org is `OnCreditTrial` (`:110-117`), (b) cancels the subscription (`:136`), (c) in a transaction deletes the `OnCreditTrial` issue and raises `TrialCreditsDepleted`, commits (`:141-166`), then (d) loops hibernating every project with keyset pagination (`:168-184`). If hibernation fails partway (step d), or the subsequent email send fails (`:188-198`), `Work` returns an error and River retries — but the retry re-runs the guard at `:114`, finds no `OnCreditTrial` issue (it was deleted and committed in step c), logs "org is not on the credit trial", and returns `nil`. - **Failure scenario:** Org with 10 projects depletes credits; hibernation of project #3 fails (transient runtime error). On retry the worker no-ops, leaving projects #3–#10 running compute indefinitely on a depleted trial. Unlike the trial-grace worker (`trial_checks.go:263-289`), this path also never zeroes org quotas, so nothing else forces the projects down.
- **Recommendation:** Make hibernation idempotent and independent of the trial-issue state: drive it off `TrialCreditsDepleted` (the state the retry can still observe) or hibernate before/inside the committed transition, and treat "already depleted" as a resumable state rather than an early return.

**Verification:** CONFIRMED — `admin/jobs/river/credit_balance_event_handlers.go`: the `OnCreditTrial` guard returns `nil` when the issue is absent (`:114-117`), the issue swap is committed at `:164-166`, and both the hibernation loop (`:168-184`) and the email send (`:188-198`) after the commit return errors that trigger a River retry, which then hits the guard and no-ops, leaving remaining projects running.

Watch the admin logs: the first job run cancels the subscription, hibernates all projects, then fails on the email and is retried; the retry logs "credit_balance_depleted webhook ignored: org is not on the credit trial" and completes without sending the email. ### abp-04 [MEDIUM] Org teardown and inactive-org hibernation only process the first 100 projects
- **Category:** correctness  **Confidence:** medium  **Location:** `admin/jobs/river/org_jobs.go:207-221` (DeleteOrg), `:250-267` (HibernateInactiveOrgs)
- **Problem:** Both workers call `FindProjectsForOrganization(ctx, orgID, "", 100)` once, with no keyset loop (contrast `credit_balance_event_handlers.go:168-184`, `trial_checks.go:291-310`, and `biller_event_handlers.go:215-234`, which all loop with `afterProjectName`). The query is `... WHERE org_id=$1 AND lower(name) > lower($2) ORDER BY lower(name) LIMIT $3` (`postgres.go:340-351`).
  - `HibernateInactiveOrgsWorker` (`:250-267`) has **no retry and no pagination**: it always fetches the same first 100 projects by name and hibernates those with a live deployment. Projects beyond the first 100 (alphabetically) are never hibernated — the query does not filter on deployment state, so already-hibernated projects keep occupying the first-100 window on every weekly run.
  - `DeleteOrgWorker` (`:207-227`) tears down ≤100 projects (`TeardownProject` deletes the project row, `projects.go:138-...`) then calls `DeleteOrganization`; the `projects.org_id` FK is `ON DELETE RESTRICT` (`migrations/0001.sql:15`), so with >100 projects the delete fails and relies on River retries (`MaxAttempts: 3`, `river.go:188`) to drain ~100 per attempt (≈300 max). It self-heals under ~300 projects but stalls above that. Separately, `TeardownProject` polls up to 5 minutes per project, so ~100 sequential teardowns can exceed the 1-hour `JobTimeout` (`river.go:187`).
- **Failure scenario:** An inactive org with 150 projects leaves 50 projects running compute forever (no retry, no pagination). An enterprise org with 350 projects is deleted: three attempts clear ~300, the 4th never runs, and the org plus ~50 projects stay half-deleted.
- **Recommendation:** Loop with keyset pagination until exhausted (as the other workers do), and consider fanning teardown out per-project rather than serially polling within one job.

**Verification:** CONFIRMED — `admin/jobs/river/org_jobs.go`: `DeleteOrgWorker` calls `FindProjectsForOrganization(ctx, job.Args.OrgID, "", 100)` once at `:207` with no pagination loop, and `HibernateInactiveOrgsWorker` does the same at `:251`; contrast the keyset loop in `credit_balance_event_handlers.go:168-184`. `MaxAttempts: 3` and `JobTimeout: time.Hour` confirmed at `admin/jobs/river/river.go:187-188`.

**Manual Reproduction Steps (for QA):**
1. On a staging Rill Cloud environment, create an organization and deploy (or script-create via the admin API) more than 100 projects in it — e.g. 120 projects named `p001`…`p120`.
2. For the hibernation case: make the org "inactive" per the inactivity criteria (or adjust the staging threshold), then trigger the weekly `hibernate_inactive_orgs` job (enqueue it via the jobs trigger endpoint or wait for the schedule).
3. After the job completes, list the projects: the first 100 alphabetically are hibernated but projects 101-120 still show live deployments. Re-running the job does not fix them (the same first 100 are re-fetched every run).
4. For the deletion case: delete the organization (CLI `rill org delete` or admin API) on an org with >300 projects; observe the `delete_org` job fail after tearing down ~100 projects per attempt, exhaust its 3 attempts, and leave the org and remaining projects half-deleted (org still present in the DB, projects still listed).

### abp-05 [LOW] `TrialEndCheckWorker` performs the DB state transition and sends email inside one transaction
- **Category:** correctness  **Confidence:** medium  **Location:** `admin/jobs/river/trial_checks.go:147-203`
- **Problem:** The worker opens a transaction, upserts `TrialEnded`, deletes `OnTrial`, then calls `SendTrialEnded` (a network call to the email provider) **before** `tx.Commit()`. Two consequences: (1) the DB transaction (holding the upserted/deleted `billing_issues` rows) stays open across an external API round-trip, for every ending trial in the batch, so an email-provider slowdown pins connections/locks; (2) the durability ordering is inverted — if the email succeeds but `Commit` fails (`:200-203`) the customer received a "trial ended" email while the DB rolled back, so the next daily run sends it again. Because email failure returns an error that rolls the transaction back (`:191-198`), an email-provider outage also stalls *all* trial-end transitions until it recovers.
- **Failure scenario:** Email provider is slow/commit races a connection drop → a duplicate trial-ended email and a transaction pinned open across email latency; or an email outage blocks every org's trial-end processing.
- **Recommendation:** Perform the DB state transition and commit first, then send the (best-effort, logged-not-returned) email outside the transaction, matching the pattern already used in `PaymentSuccessWorker` (`biller_event_handlers.go:165-175`).

**Verification:** CONFIRMED — `admin/jobs/river/trial_checks.go:147-203`: the transaction opens at `:147`, `SendTrialEnded` is called at `:184-190` before `tx.Commit()` at `:200`, and an email error rolls the transaction back (`:191-198`), so email I/O sits inside the open transaction and an email outage blocks the trial-end transition.

**Manual Reproduction Steps (for QA):**
1. On a staging environment with billing enabled, create an org whose trial end date has passed (or shorten the trial in staging config) so the daily `trial_end_check` job will process it.
2. Break the email provider configuration (e.g. invalid API key) so `SendTrialEnded` fails.
3. Trigger or wait for the trial-end check job; observe in logs it errors with "failed to send trial period ended email" and that the org's billing issue remains `on-trial` (no `trial-ended` issue appears in the DB `billing_issues` table) — the whole transition rolled back because of the email failure.
4. Restore email; the next run transitions the org and sends the email. The duplicate-email variant (email sent, commit fails) is timing-dependent and not reliably reproducible manually; confirm in code at `trial_checks.go:184-203` that the email precedes the commit.

### abp-06 [LOW] `usedFlusher.Close` does not join the background goroutine; `flushWg` is incremented inside the function it waits on
- **Category:** concurrency  **Confidence:** medium  **Location:** `admin/used_flusher.go:113-134` (Close call site `admin/admin.go:162`, shutdown path)
- **Problem:** `runBackground` calls `flush()` on a 30s ticker; `flush()` itself does `flushWg.Add(1)`/`defer Done()`. `Close()` calls `cancel()`, then its own `flush()`, then `flushWg.Wait()`, but never joins the background goroutine. After `cancel()`, if the ticker and `ctx.Done()` are both ready, the `select` may still pick the tick and run one more `flush()` concurrently with `Close`'s `flush()`/`Wait()`. Because `Add` happens inside the waited-on function rather than being registered before `Wait` for a fixed set, this is the shape Go's `WaitGroup` contract warns about (`Add` racing `Wait` from a zero counter), and the background goroutine can still be writing to the DB after `Close` returns.
- **Failure scenario:** On shutdown, a background tick fires concurrently with `Close`; in a narrow window it can trip `sync: WaitGroup misuse: Add called concurrently with Wait`, or a background flush runs after the pool is torn down (logged error). Shutdown-only, low frequency.
- **Recommendation:** Give the background goroutine its own done channel / `WaitGroup` and `Wait` on *that* in `Close` (join the loop), then do one final synchronous flush. Don't `Add` to the wait group inside the function being awaited.

**Verification:** CONFIRMED — `admin/used_flusher.go`: `Close()` (`:113-117`) calls `cancel()`, `flush()`, `flushWg.Wait()` but never joins the goroutine started in `newUsedFlusher` (`:52`); `runBackground`'s `select` (`:119-130`) can pick a ready tick over `ctx.Done()`, and `flush()` does `flushWg.Add(1)` inside itself (`:133`), the exact `Add`-racing-`Wait`-from-zero shape the `WaitGroup` contract forbids.

**Manual Reproduction Steps (for QA):**
Not user-reproducible — this is a narrow shutdown-only race with no user-facing surface. Confirm in code: `admin/used_flusher.go:113-134` (Close does not join the `runBackground` goroutine; `flushWg.Add` is inside `flush`, the function being awaited) and the Close call site on the admin service shutdown path in `admin/admin.go`. A Go engineer can also demonstrate it with a `-race` unit test that spins tickers fast and calls `Close` concurrently, but no QA-visible symptom exists beyond a rare `sync: WaitGroup misuse` panic in admin-service shutdown logs.

### abp-13 [LOW] Two owners of the "trial started" email can double-send when an init-failed org is repaired
- **Category:** product-improvement  **Confidence:** low  **Location:** `admin/billing.go:209` (`RepairOrganizationBilling` sends `SendCreditTrialStarted`), `admin/jobs/river/org_jobs.go:114` and `:155` (start-trial workers send it)

The real duplicate path is cross-owner: if `InitOrganizationBilling` failed leaving `billing_customer_id` empty and a superuser runs `SudoTriggerBillingRepair` (which selects exactly those orgs, `admin/server/billing.go:945-951` → `FindOrganizationIDsWithoutBilling`), `RepairOrganizationBilling` starts the credit trial and sends email #1, while a still-retrying `StartCreditTrialWorker` later succeeds and sends email #2. This is a narrow operational window, not a routine flow.
- **Failure scenario:** An org whose billing init partially failed is repaired by an operator while its start-trial job is retrying → the customer receives two "your trial has started" emails.
- **Recommendation:** Record an "email sent" marker on the trial billing issue (or only email on an absent→present issue transition) and pick a single owner for the trial-started notification.

**Verification:** PLAUSIBLE — both senders exist as described: `RepairOrganizationBilling(initSub=true)` sends `SendCreditTrialStarted` at `admin/billing.go:209-215` and `StartCreditTrialWorker` sends it at `admin/jobs/river/org_jobs.go:155-161` (email failures swallowed at `:162-164`, so single-worker retries do not re-send); the repair path is reachable via `SudoTriggerBillingRepair` (`admin/server/billing.go:939`). The double-send requires the narrow interleaving of an operator-triggered repair racing a still-retrying start-trial job, which could not be confirmed to occur in practice.

**Manual Reproduction Steps (for QA):**
1. On staging, arrange for an org's initial billing setup to fail partway (e.g. temporarily break the Orb API credentials while creating a new org, so `billing_customer_id` stays empty and the `start_credit_trial` job keeps retrying).

## Product Improvements
- **abp-13** (duplicate trial-started emails) is the clearest user-visible polish item — trial onboarding emails should fire exactly once, owned by one code path.
- **Trial re-grant guard is balance-based, not history-based (defensive hardening, low):** `StartCreditTrial`'s idempotency guard is `if balance <= 0 { GrantCustomerCredits(...) }` (`admin/billing.go:285-291`), which cannot distinguish "never granted" from "granted and fully depleted". No current caller re-invokes `StartCreditTrial` on a depleted org (see Verification Notes, abp-08), so this is not an active bug — but if a future path ever does, a depleted org would silently receive a fresh 250-credit trial. Basing the guard on granted-history (issue/ledger presence) rather than current balance would make this robust by construction.
- **Seat billing gap (observed, low):** `BillingReporterWorker.reportOrgUsageMetrics` (`billing_reporter.go:198-255`) reports the `seats` gauge only for orgs that emitted *runtime* usage this hour (`reportedOrgs`). An org whose projects are all hibernated but that still has active members reports zero seats. If seats are billable independent of compute, confirm this is intended; otherwise report seats for all billing-enabled orgs.
- **Provisioner health is opaque (observed, low):** `clickhouse-static` and `kubernetes` `Check` are no-ops, and static `Check` only logs (`static.go:170-206`). There is no capacity metric/alert surfaced to operators; slot exhaustion is discovered by provisioning failures (`static.go:110`).

## New Feature Ideas
- **Collision-proof, human-readable resource naming helper (S):** a shared util that composes `<readable-prefix-truncated>_<hash(id)>` guaranteeing uniqueness under length limits, reused by `clickhouse-static` and the Kubernetes name builder. Directly retires abp-01 and prevents the class of bug.
- **Provisioner capacity metrics + alerting (M):** emit slot-used/slot-total gauges per host (static) and cluster health (ClickHouse/k8s) to OpenTelemetry, with an alert at the existing 80%/70% thresholds instead of log-only. Gives operators lead time before overcommit/exhaustion.
- **Orphaned-resource reconciler (M):** a periodic job that lists `provisioner_resources` (and static assignments) with no live deployment and deprovisions/reclaims them — closes leaks from abp-04 and interrupted teardowns.
- **Billing-issue admin console (M):** an internal view to list/inspect/resolve per-org billing issues (trial, payment-failed invoices, credit state) and manually re-run repair, since today the state lives only in DB rows and daily jobs.
- **Idempotent "reconcile org billing" (L):** treat Orb as the source of truth and reconcile subscription/plan/quotas/issues in one convergent operation (replacing the several overlapping Init/Repair/Start paths), eliminating duplicate-email and re-grant edge cases.
- **Safeguarded autoscaler re-enable (L):** finish and re-enable the disabled autoscaler behind the real `AutoscalerCron` flag with per-project min/max policies, dry-run logging, and the nil-guards from abp-07 — turning abp-12's dead code into a shipped capability.
