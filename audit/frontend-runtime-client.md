# Frontend Runtime Client, SSE & Chat — Code Review
**Scope:** `web-common/src/runtime-client` (`index`, `application-store`, `constants`, `query-matcher`, `invalidation`, `invalidation/*`, `local-service`, `sse/*`, `v2/*`) + `web-common/src/features/chat/**` (plus the SSE/queue consumers `file-and-resource-watcher.ts`, `ProjectLogsPage.svelte`, `web-local/src/features/tables/selectors.ts`)  |  **Health:** fair

## Overview
This area is the JWT-gated ConnectRPC request layer (`RuntimeClient` + priority `RequestQueue`), a well-layered SSE stack (`sse-protocol` → `sse-fetch-client` → `sse-connection` → `sse-subscriber`/`lifecycle`), the TanStack-Query invalidation logic driven by the file/resource watch stream, and the chat streaming feature. The SSE layering is genuinely good: single-flight reconnect with an abort controller, run-id gating against stale events, and careful guards so intentional stops are not surfaced as errors. The invalidation and queue code is where most risk lives.

The one serious issue is in chat: because `startStreaming` resolves on the connection `close` event rather than rejecting on error, the documented optimistic-message rollback is unreachable, so a failed send silently loses the user's draft and leaves an orphan message. Everything else is medium-or-lower: the status-page Tables list is never invalidated on reconcile (stale until the tab is re-focused), `removeByName`/`clear` leave a stale abort listener that throws when it later fires, and the request-priority map has misnamed keys. Test coverage is good for the happy paths but misses every one of the failure modes below.

This report is the post-verification version; each finding below was independently re-traced in code. Several severities/confidences were adjusted and one inaccurate claim (server-side priority impact in finding 04) was corrected — see **Verification Notes** at the end.

## Findings

### frontend-runtime-client-01 [HIGH] Failed chat send loses the user's draft and never rolls back the optimistic message
- **Category:** correctness  **Confidence:** high  **Location:** `web-common/src/features/chat/core/conversation.ts:378` (and `249`, `705`)
- **Problem:** `startStreaming` awaits a promise that only ever *resolves*, on the SSE `close` event (`onceConnection("close", … resolve())`, lines 378-383). It has no reject path. Transport failures are reported through the separate `stream.onConnection("error")` handler (which only calls `streamError.set(...)`, line 450) and then the connection's `close` fires and resolves the await. Consequently `await this.startStreaming(...)` in `sendMessage` never throws, so the entire `catch` block (lines 249-266) and `handleTransportError(..., wasStreaming=false)` rollback (lines 705-723) are dead code for real transport errors. `sendMessage` clears the draft up-front (`this.draftMessage.set("")`, line 212) and adds the optimistic user message (line 235), but on failure neither is undone. (The fork-failure early-return at 225-232 has the same draft-loss gap.)
- **Failure scenario:** User types a message and hits send while the JWT is expired (401) or the network is down. The optimistic user message is written to the conversation cache; the request fails; `streamError` shows an error, but (a) the typed text is gone (draft was cleared, never restored) and (b) the un-persisted user message remains in the UI. On a `NEW_CONVERSATION_ID` send this leaves an orphan message under a disabled query; on a retry the user must retype, and stale messages accumulate. `stream-complete` is even emitted for the failed/cancelled stream because `close` resolves the await, triggering a spurious `invalidateConversationsList` (line 248). The existing test `surfaces transport errors (SSEHttpError) through streamError` (conversation-streaming.spec.ts:203) confirms the resolve-on-close behavior — it calls `sendMessage(...).catch(() => {})`, fires `error` then `close`, and asserts only that `streamError` is set — but never asserts rollback.
- **Recommendation:** Make `startStreaming` reject (or return a discriminated result) when the stream ends in an error state — e.g. capture the last transport/server error in the `onConnection("error")`/`on("error")` handlers and have the `close` handler `reject(err)` when one is pending, else `resolve()`. Then `sendMessage`'s existing `catch` will correctly roll back pre-stream failures and keep mid-stream ones. Alternatively, track a `didError` flag and perform the rollback/draft-restore explicitly. Add a test asserting the optimistic message is removed and the draft restored on a pre-stream 401.

**Verification:** CONFIRMED — `startStreaming` awaits a promise whose only settlement is `resolve()` inside `onceConnection("close", ...)` (conversation.ts:378-383); transport errors go to `onConnection("error")` which only calls `this.streamError.set(...)` (conversation.ts:441-451). In `SSEConnection.handleError` with no retry configured (chat sets none, conversation.ts:397-400), the error path calls `this.close()` which emits `close` (sse-connection.ts:227-234, 133-148), resolving the await. So `sendMessage`'s `catch` (conversation.ts:249-263) and `handleTransportError`'s rollback (conversation.ts:705-723) never run for transport failures, while the draft was already cleared at conversation.ts:212 and the optimistic message added at :235. `stream-complete` + `invalidateConversationsList` fire at :245-248 despite the failure. The fork-failure return at :225-232 also does not restore the draft.

**Manual Reproduction Steps (for QA):**
1. Open a Rill project with the AI chat sidebar enabled and start a conversation (or a new one).
2. Open browser devtools, go to the Network tab, and set throttling to "Offline" (or use request blocking on `*/ai/complete/stream`).
3. Type a message in the chat input and press send.
4. Expected: an error is shown, the message bubble is removed (it never reached the server), and your typed text is restored in the input so you can retry.
5. Actual: an error is shown, but the input is empty (draft lost) and the unsent user message bubble remains in the conversation; on reload of a persisted conversation the orphan bubble disappears, confirming it was never saved.

  2. The status-page Tables list (`useInfiniteTablesList`, selectors.ts:29-53, used by web-local `LocalProjectTables`/`TablesSection` and web-admin `ProjectTables`/`TablesSection`) is served under a **hand-written key** `["/v1/olap/tables-infinite", {instanceId, connector, searchPattern}]`. Also fix the misleading comment at invalidation.ts:226 that says `"QueryService"` where the code checks `"ConnectorService"`.

### frontend-runtime-client-03 [MEDIUM] `removeByName`/`clear` leave a live abort listener that throws when it later fires
- **Category:** concurrency  **Confidence:** high  **Location:** `web-common/src/runtime-client/v2/request-queue.ts:129` (abort guard), `:147`/`:158` (`removeByName`/`clear`), `heap.ts:34` (`pop` does not clear `index`)
- **Problem:** The abort listener registered in `enqueue` guards re-entry only with `if (!entry.fn) return;` (line 129). `fireEntry` clears `entry.fn` when a request fires (line 198), so *fired* entries are protected. But `removeByName` (150-154) and `clear` (159-165) reject and `pop()` entries **without clearing `entry.fn`**, and `Heap.pop` never resets the popped entry's `index` (it leaves it at `0`, its root position). So after `removeByName` empties a resource's `queryHeap`, each removed entry still has `fn` set and `index === 0`. If that request's `AbortSignal` fires afterward (the `{ once: true }` listener is still attached), the guard passes and the handler calls `nameEntry.queryHeap.delete(entry)`; inside `Heap.delete`, `idx` resolves to the stale `0`, `value = this.array[0]` is `undefined` on the now-empty heap, and `delete value.index` throws `TypeError: Cannot read properties of undefined (reading 'index')` from inside the abort event handler.
- **Failure scenario:** A metrics view / table is renamed or deleted while it still has queued (not-yet-fired) profiling/aggregation requests. `renameFileArtifact`/`deleteFileArtifact` call `client.requestQueue.removeByName(...)` (actions.ts:212, 270), rejecting those entries but leaving `fn`/`index` intact. When the corresponding TanStack queries unmount and abort, the guard fails to short-circuit and the delete throws an uncaught `TypeError` per aborted request. The promise itself is already settled (rejected by `removeByName`), so the primary observable is uncaught console errors on a common flow rather than silent data loss; genuine heap corruption would require the stale index to land on a *different* live entry, which is unlikely because the orphaned `NameEntry` is removed from `nameHeap` and re-enqueues create a fresh one.
- **Recommendation:** In `removeByName` and `clear`, set `entry.fn = undefined` for each removed entry so the abort guard short-circuits. Additionally have `Heap.pop`/`Heap.delete` clear the removed entry's `index`, and harden `Heap.delete` to bail when `this.array[idx]` is not the expected entry (verify `this.array[idx] === value` or `keyGetter(this.array[idx]) === key`).

**Verification:** CONFIRMED — the abort listener's only re-entry guard is `if (!entry.fn) return;` (request-queue.ts:129); `fn` is cleared only in `fireEntry` (:198). `removeByName` (:147-155) and `clear` (:158-166) `pop()` and reject entries without clearing `fn`. `Heap.pop` (heap.ts:34-47) deletes the key from `valueToIdxMap` but never deletes the popped item's `index`, so a popped root entry keeps `index === 0`. When the abort later fires, `queryHeap.delete(entry)` resolves `idx = value?.index ?? ...` to the stale `0` (heap.ts:51), reads `value = this.array[0]` which is `undefined` on the emptied heap (heap.ts:54), and `delete value.index` (heap.ts:56) throws `TypeError`. Call sites `client.requestQueue.removeByName(...)` confirmed at web-common/src/features/entity-management/actions/actions.ts:212 (rename) and :270 (delete).

**Manual Reproduction Steps (for QA):**
1. In Rill Developer (localhost, so `maxConcurrent` is 5), open a wide source/model table so many column-profiling requests queue up (open the profile panels for a table with 20+ columns).
2. While the profile queries are still loading, rename or delete that source/model file from the file tree (this calls `requestQueue.removeByName`).
3. Immediately navigate to a different page so the still-mounted profile components unmount and TanStack aborts their queries.
4. Expected: no console errors; aborted requests are cleaned up silently.
5. Actual (timing-sensitive): the devtools console shows one uncaught `TypeError: Cannot read properties of undefined (reading 'index')` per queued request whose abort fired after the rename/delete. If the timing is hard to hit through the UI, confirm in code: request-queue.ts:129 vs :150-154 (fn not cleared) and heap.ts:34-47/49-56 (stale index), or write a unit test that enqueues, calls `removeByName`, then fires the abort signal.

### frontend-runtime-client-04 [LOW] Request-priority map keys don't match the actual RPC method names
- **Category:** performance  **Confidence:** high  **Location:** `web-common/src/runtime-client/v2/request-priorities.ts:9`
- **Problem:** `getPriorityForMethod` looks up `req.method.name` (the ConnectRPC method name, PascalCase — confirmed by request-queue.spec.ts, which passes `"MetricsViewTimeRanges"` and expects 100) in `MethodPriorities`, but three keys use non-existent names: `NumericHistogram` (actual RPC: `ColumnNumericHistogram`, queries_connect.ts:333), `RugHistogram` (`ColumnRugHistogram`, :344), `DescriptiveStatistics` (`ColumnDescriptiveStatistics`, :311); and `ColumnProfile` (:8) has no corresponding RPC at all. All four fall through to `DEFAULT_PRIORITY = 10`. The value `getPriorityForMethod` returns is used as the **client-side heap weight** passed to `queue.enqueue` (request-queue.ts:250, 261) and — only when the caller has not already set `msg.priority` — is injected into the proto message (`msg.priority`, line 257).
- **Failure scenario:** On the client heap, `ColumnNumericHistogram`/`ColumnRugHistogram`/`ColumnDescriptiveStatistics` (plus `ColumnTopK`/`ColumnTimeSeries`, which are simply absent from the map) are weighted at `DEFAULT_PRIORITY` (10) instead of their intended values, so under contention (localhost's 5-slot ceiling) numeric histograms lose their edge over other default-weight work within a resource. Server-side impact is limited: the column-profile callers (`column-profile/queries.ts`, `NumericProfile.svelte`) independently set `msg.priority` via `getPriorityForColumn(...)`, and the interceptor's `if (!msg.priority)` guard preserves that, so the *server* still receives the intended priority for those queries — the earlier claim that they are "server-scheduled at 10" was incorrect and has been removed. `ColumnProfile` is simply dead. Note also that the queue weight is derived *solely* from the method name and ignores the `msg.priority`/`getPriorityForColumn` active-column offset entirely, so client-side column prioritization is largely flat regardless of these keys.
- **Recommendation:** Rename the keys to the real method names (`ColumnNumericHistogram`, `ColumnRugHistogram`, `ColumnDescriptiveStatistics`), add `ColumnTopK`/`ColumnTimeSeries` if they should be prioritized, and drop `ColumnProfile`. Add a table-driven test asserting each configured key resolves to its intended priority (guards against future proto renames). Consider whether the queue weight should honor `msg.priority`/`getPriorityForColumn` so the active-column offset actually orders the client heap.

**Verification:** CONFIRMED — `MethodPriorities` contains `NumericHistogram` (request-priorities.ts:25), `RugHistogram` (:31), `DescriptiveStatistics` (:32), and `ColumnProfile` (:16), while the actual RPC method names in queries_connect.ts are `ColumnNumericHistogram` (:333), `ColumnRugHistogram` (:344), `ColumnDescriptiveStatistics` (:311); there is no `ColumnProfile` RPC. The lookup uses `req.method.name` (request-queue.ts:250) so all four keys are dead and those methods fall through to `DEFAULT_PRIORITY = 10` (request-priorities.ts:35, :41). The interceptor's `if (!msg.priority)` guard (request-queue.ts:257) preserves caller-set server-side priority, and the queue weight passed to `enqueue` (:261-262) is derived solely from the method name, ignoring `msg.priority`.

**Manual Reproduction Steps (for QA):**
Not user-reproducible through the UI — the client heap weight has no direct visible effect and the server still receives the caller-set priority. Confirm in code: compare the key names at `web-common/src/runtime-client/v2/request-priorities.ts:16,25,31,32` with the generated method names at `web-common/src/proto/gen/rill/runtime/v1/queries_connect.ts:311,333,344`, and note `getPriorityForMethod(req.method.name)` at `web-common/src/runtime-client/v2/request-queue.ts:250`. Optionally, in devtools you can inspect a `ColumnNumericHistogram` request body: its `priority` field comes from `getPriorityForColumn` (caller-set), proving the map entry is never used for it.

### frontend-runtime-client-05 [MEDIUM] JWT-wait loop ignores the request's abort signal; aborted requests stall and consume concurrency during auth degradation
- **Category:** correctness  **Confidence:** medium  **Location:** `web-common/src/runtime-client/v2/runtime-client.ts:119`
- **Problem:** `waitForFreshJwt` polls every 50 ms (`CHECK_RUNTIME_STORE_FOR_JWT_INTERVAL`) for up to 60 s and only breaks out on `this.disposed` (line 126) or the 60 s deadline (line 129). It does not observe the in-flight request's `AbortSignal`. The JWT interceptor (lines 63-69) is dispatched by the queue's `fireEntry`, which increments `activeCount` before awaiting (request-queue.ts:182-183), so a request parked in `waitForFreshJwt` holds one of the `maxConcurrent` slots. The queue only handles aborts *before* a request fires (`if (!entry.fn) return;`); once it enters `waitForFreshJwt` there is no cancellation path, and `req.signal` is available but unused.
- **Failure scenario:** The loop only runs when the JWT is within `JWT_EXPIRY_WARNING_WINDOW` (1 s) of the assumed 30-min TTL, i.e. when proactive refresh has stopped (admin outage, tab asleep past TTL). In that degraded state every request enters the wait loop and holds a slot. A user navigating away aborts those queries, but each keeps polling for up to 60 s, so the app's `maxConcurrent` slots (5 on localhost) stay pinned by already-cancelled requests and new critical requests queue behind them for up to a minute; cancellation appears not to work.
- **Recommendation:** Thread `req.signal` into `waitForFreshJwt` and reject with the signal's reason when it fires (mirroring the `disposed` check) via a one-shot `abort` listener that rejects the wait promise.

**Verification:** CONFIRMED — `waitForFreshJwt` (runtime-client.ts:119-138) polls on a 50 ms timer with only two exits: `this.disposed` (:126) and the 60 s deadline (:129); `req.signal` is never consulted (the JWT interceptor at :63-69 does not pass it). The queue interceptor is outermost (:59-61), so the queue's `fireEntry` has already incremented `activeCount` (request-queue.ts:182-183) before the JWT interceptor runs, and the queue's abort handling only applies to entries that have not fired (`if (!entry.fn) return;`, request-queue.ts:129). Constants confirmed: TTL 30 min, warning window 1 s, poll 50 ms (constants.ts:2,7,10). The stall only occurs when the JWT is within 1 s of expiry, i.e. during auth-refresh degradation.

**Manual Reproduction Steps (for QA):**
Reproducible only in a degraded-auth state, which is hard to stage through the UI (requires the runtime JWT to reach within 1 s of its assumed 30-minute TTL without a refresh). Best-effort repro:
1. Open a Rill Cloud project dashboard and, in devtools, use Network request blocking to block the admin credentials/JWT-refresh endpoint so `updateJwt` stops receiving fresh tokens.
2. Leave the tab open (or asleep) past the 30-minute token TTL, then interact with the dashboard so new runtime queries fire.
3. Navigate away from the dashboard (which aborts those queries via TanStack).
4. Expected: aborted requests release immediately and new pages load normally.
5. Actual: requests sit in the JWT wait loop for up to 60 s while holding concurrency slots; new queries queue behind them and the app appears frozen despite cancellation.
If staging this is impractical, confirm in code: `web-common/src/runtime-client/v2/runtime-client.ts:119-138` (no `req.signal` parameter or abort listener) and `web-common/src/runtime-client/v2/request-queue.ts:182-183` (slot held across the await).

### frontend-runtime-client-06 [LOW] SSE resume-from-pause is routed through the retry budget; with `maxRetryAttempts` 0/unset it closes the stream on resume
- **Category:** bug  **Confidence:** medium  **Location:** `web-common/src/runtime-client/sse/sse-connection.ts:104` (`resumeIfPaused`) → `:162` (`reconnect`) → `:178`
- **Problem:** `resumeIfPaused` calls the same `reconnect()` loop used for error retries. `reconnect` reads `currentAttempts` and, when `currentAttempts >= (this.params?.maxRetryAttempts ?? 0)`, calls `this.close()` (lines 178-181). `pause()` resets `retryAttemptCount` to 0 (line 123), so on resume `currentAttempts` is 0; if a consumer attaches a lifecycle but creates the connection with `maxRetryAttempts` unset or 0, `0 >= 0` is true and the connection is **closed instead of resumed**. Resume is a user/visibility-driven action, not a failure, so conflating it with the retry budget is a latent footgun in a reusable primitive.
- **Failure scenario:** Latent — no current consumer triggers it. The only lifecycle-attached consumer (`file-and-resource-watcher.ts`) sets `maxRetryAttempts: MAX_RETRIES` (3), and the other retrying consumer (`ProjectLogsPage`, `maxRetryAttempts: 5`) attaches no lifecycle, while chat attaches neither. A future `createSSEStream` consumer that attaches a `lifecycle` but omits `connection.maxRetryAttempts` — a combination the README's building blocks explicitly allow — would terminate the stream the first time the tab is re-focused after an idle pause.
- **Recommendation:** Treat resume as distinct from retry: in `resumeIfPaused`, open directly (or pass a flag so the `attempts >= max` short-circuit is skipped for the first resume attempt). At minimum, guard against `maxRetryAttempts` being unset when a lifecycle is attached.

**Verification:** PLAUSIBLE — the logic is exactly as described: `resumeIfPaused` calls `reconnect()` (sse-connection.ts:104-108); `pause()` resets `retryAttemptCount` to 0 (:123); `reconnect` closes the stream when `currentAttempts >= (this.params?.maxRetryAttempts ?? 0)` (:177-181), so `0 >= 0` closes instead of resuming when `maxRetryAttempts` is unset or 0. However, no in-repo consumer triggers it: `file-and-resource-watcher.ts:101` sets `maxRetryAttempts: MAX_RETRIES` (3), `ProjectLogsPage.svelte:71` sets 5 (and per the lifecycle preset wiring, chat attaches no lifecycle at all, conversation.ts:397-400). Latent footgun in a reusable primitive, not a live bug.

**Manual Reproduction Steps (for QA):**
Not user-reproducible — no shipped surface creates a lifecycle-attached SSE stream with `maxRetryAttempts` unset/0. Confirm in code: `web-common/src/runtime-client/sse/sse-connection.ts:104-108` (resume routes through `reconnect`), :123 (pause resets attempts to 0), :177-181 (`0 >= (maxRetryAttempts ?? 0)` → `close()`). A unit test that constructs `SSEConnection` with no `maxRetryAttempts`, opens, pauses, then calls `resumeIfPaused()` will observe status CLOSED instead of CONNECTING.

### frontend-runtime-client-07 [LOW] Cross-resource request priority is not honored; the name-heap weight is fixed to active/inactive
- **Category:** performance  **Confidence:** medium  **Location:** `web-common/src/runtime-client/v2/request-queue.ts:210` (`getNameEntry`), `:31` (`createNameHeap`), `:176` (`drain`)
- **Problem:** Per-query priority (100 for `MetricsViewTimeRange`, etc.) orders the *inner* `queryHeap` within a resource, but the *outer* `nameHeap` orders resources solely by `NameEntry.weight`, which is hard-set to `ACTIVE_PRIORITY` (10) on creation and only changed to `INACTIVE_PRIORITY` (5) by `inactiveByName`. Equal weights make the name-heap comparison return 0, and `push` never reorders equal-weight entries, so among active resources `drain` empties whichever resource sits at the root before serving others, regardless of the priority of queries waiting in a sibling resource.
- **Failure scenario:** On localhost (`maxConcurrent` 5), opening a dashboard while another active resource has many queued profiling queries can delay that dashboard's critical `MetricsViewTimeRange` behind the other resource's low-priority work. Impact is limited on cloud where `maxConcurrent` is 200 and where the injected `msg.priority` still lets the server reorder.
- **Recommendation:** If cross-resource priority matters, set/update each `NameEntry`'s weight from the max priority of its queued queries (bump on `enqueue`, recompute on pop), so the name-heap reflects the most-urgent pending work.

**Verification:** CONFIRMED — `getNameEntry` creates every `NameEntry` with `weight: ACTIVE_PRIORITY` (request-queue.ts:213-219); the only mutation is `inactiveByName` setting `INACTIVE_PRIORITY` (:169-174). The name-heap comparator is `a.weight - b.weight` (:33), so all active resources compare equal (0), and `Heap.moveUp`/`moveDown` only swap on `> 0` (heap.ts:81, :108), so equal-weight entries are never reordered. `drain` (:176-194) pops queries from `nameHeap.peek()` until that resource's `queryHeap` is empty before any sibling resource is served, regardless of per-query weights in siblings.

4. In devtools Network, watch the request waterfall.
5. Expected: the dashboard's `MetricsViewTimeRange`/`MetricsViewTimeRanges` (priority 100) fire ahead of the remaining column-profile requests.
6. Actual: the queued profiling requests for the previous resource continue to drain first — the previous resource's `NameEntry` stays at the heap root with equal weight. (Note: `inactiveByName` has no production callers outside specs, so navigation never deprioritizes the old resource.) If not observable, confirm in code at `web-common/src/runtime-client/v2/request-queue.ts:31-36,176-194,210-222`.

### frontend-runtime-client-08 [LOW] `Bearer undefined` if the JWT is cleared while a request waits for a fresh token
- **Category:** correctness  **Confidence:** low  **Location:** `web-common/src/runtime-client/v2/runtime-client.ts:63`
- **Problem:** The JWT interceptor checks `if (this.currentJwt)` (line 64), then `await this.waitForFreshJwt()`, then sets `Bearer ${this.currentJwt}` (line 66). If `updateJwt(undefined, …)` runs during the await (e.g. logout / "View As" clear), `currentJwt` becomes `undefined` and the header is literally `"Bearer undefined"`. The await always yields at least a microtask even when the JWT is fresh, so the window is not limited to the 60 s poll.

## Product Improvements

- **Resend / retry affordance for failed chat messages** (ties to finding 01): even after the rollback bug is fixed, a failed send should offer a one-click "Retry" that re-submits the same prompt and preserves the draft. Today a transient 401 forces the user to retype.
- **Visible reconnect state for long-lived streams:** the watcher/logs streams expose `status`, but chat is one-shot with no reconnect; a dropped mid-response stream just stops. A subtle "connection lost — retry" inline control (reusing `SSEConnection`'s status) would make failures recoverable.
- **Degraded-auth banner:** when JWT refresh fails and requests start stalling in `waitForFreshJwt`, surface a "session expired, reconnecting" state instead of silently freezing the UI for up to 60 s.

## New Feature Ideas

- **Queue diagnostics overlay** (S): a dev-only panel bound to `appQueryStatusStore` + `RequestQueue` internals showing active/queued counts and per-resource priority, to debug prioritization and the localhost 5-connection ceiling.
- **Stop/regenerate for AI responses** (M): `cancelStream` exists but is only wired to lifecycle limits; expose an explicit "Stop generating" and "Regenerate" in the chat UI, and make cancel not emit `stream-complete`.
- **Offline-aware request queue** (M): pause `drain` on `navigator.onLine === false` and resume on reconnect, instead of firing requests that immediately fail; pairs well with the SSE lifecycle signals already implemented.
- **Typed SSE error taxonomy** (S): `V1WatchErrorPayload`/`ChatServerError` are decoded best-effort; a shared, typed error-code enum with user-facing copy would unify chat, watcher, and logs error handling.
