# Cloud Editing & Deployment (races + first-reconcile latency) — Deep-Dive Audit

**Focus:** (1) Race conditions across concurrent edits/deploys/redeploys, provisioning, deployment-reconcile jobs, github webhooks, config reload, controller lifecycle. (2) First-reconciliation latency: deploy → create-instance → controller start → project-parser reconcile → per-resource reconcile → dashboards ready.
**Scope:** `admin/{projects,deployments,provision,github,used_flusher}.go`, `admin/server/{projects,deployment,provision,github,repos}.go`, `admin/jobs/river/*` (reconcile_deployment, validate_deployments, hibernate_expired_deployments, deployments_health_check, river), `cli/pkg/local/{app,server,project,git,admin,slots}.go`, `runtime/{controller,registry,runtime,config_reloader}.go`, `runtime/reconcilers/{project_parser,migration,source,model,connector,util}.go`, `runtime/drivers/admin/{repo,repo_archive}.go`, `runtime/parser/parser.go` (traced as needed).
**Health:** needs-attention

## Overview

I traced the full deploy hot path end-to-end:

1. **Admin:** `CreateProject` (admin/server/projects.go:449) → `admin.CreateProject` (admin/projects.go:24) → `CreateDeployment` inserts a Pending deployment and enqueues a `reconcile_deployment` River job (admin/deployments.go:37-63, admin/jobs/river/river.go:337-359).
2. **Job:** `ReconcileDeploymentWorker` (admin/jobs/river/reconcile_deployment.go) → `StartDeploymentInner` (admin/deployments.go:179-335): provision runtime (static = slot upsert, no wait; k8s = `AwaitReady` poll 1s until pod Available + ping with retries — kubernetes.go:397), then `CreateInstance` RPC on the runtime.
3. **Runtime:** `registryCache.create` (runtime/registry.go:328-345) stores the instance, spawns the controller goroutine (`ensureRepoReady` pull → `updateProjectConfig` full parse → `NewController` catalog init → ready → `ctrl.Run`), then — cloud only — synchronously calls `ReloadConfig` → `configReloader.reloadConfig` (runtime/config_reloader.go:48-186), which forces a second repo pull, blocks on controller readiness, and for archive-based projects **restarts the controller it just started**.
4. **Controller:** `Run` enqueues everything (runtime/controller.go:176-182); the project parser pulls again and does the authoritative full parse (runtime/reconcilers/project_parser.go:112-165), creates resources; the DAG then runs connector test → model ingest (semaphore, default `rill.models.concurrent_execution_limit=5`) → metrics-view validation (OLAP queries) → explore; dashboards are ready when explores/MVs go idle.

**Headline (latency):** excluding data ingestion (inherent) and k8s pod spin-up (dominant when used), the avoidable fixed overhead of a first deploy is concentrated in the runtime's instance-creation choreography: a git deploy performs **3 sequential network pull rounds and 2+ full project parses**; an archive ("zip-and-ship") deploy performs **2 full archive downloads, 3 full parses, and 2 complete controller startups**, because `reloadConfig` force-refreshes a signed URL that changes on every call (so `archiveRepo.sync` re-downloads) and sets `restartController=true` whenever `cfg.UsesArchive`. On multi-tenant (static-provisioner) hosts, all of this serializes through **one global config-reload mutex** held across network I/O, so concurrent deploys and the hourly/boot reload sweep queue behind each other.

**Headline (races):** deployment desired-state management has three unserialized read-modify-write layers that can drop or revert transitions — the `reconcile_deployment` unique-job dedup vs. the worker's completion recheck, `UpdateDeployment`'s stale `DesiredStatus` write, and project-level redeploy/hibernate flows with no per-project serialization. All are bounded by janitor jobs (3h orphan sweep, 15-min TTL cron, hourly config reload), so the failure modes are zombie/duplicate deployments and delayed state convergence rather than permanent data loss.

Prior findings re-confirmed unchanged (not re-filed): admin-projects-deploy-01 (delete discards checkpoint on push failure; deployments.go:412-421), admin-projects-deploy-05 (`GetRepoMeta` nil `depl.Branch` at admin/server/repos.go:92), admin-projects-deploy-07 (synchronous webhook), abp-02 (static slot TOCTOU), abp-06 (`used_flusher.Close` un-joined goroutine; used_flusher.go:113-134), runtime-core-02 (`DeleteInstance` nil-channel hang; registry.go:114-120), runtime-core-06 (`markPending` clears ancestor error, controller.go:1166), cli-01 (`DeployProject` pushes `.env` to unsuffixed name; cli/pkg/local/server.go:454-457).

## Findings

### deep-cloud-deploy-01 [HIGH] First-deploy critical path repeats repo pulls and parses; archive deploys restart the controller and re-download the archive

- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `runtime/registry.go:339-343` (create → `ReloadConfig`), `runtime/registry.go:436-478` (`ensureRepoReady` + `updateProjectConfig` per controller start), `runtime/config_reloader.go:132-163` (forced pull, `ctrl.Reconcile`, `restartController = ... || cfg.UsesArchive`), `runtime/drivers/admin/repo.go:771-802` (singleflight keyed on pull options), `runtime/drivers/admin/repo_archive.go:26-49` (sync keyed on signed URL), `admin/server/assets.go:252-270` (signed URL expires in 15 min → differs per call), `admin/server/deployment.go:790-791` (`UsesArchive = proj.ArchiveAssetID != nil`).
- **Problem:** On cloud (`AllowHostAccess=false`, `EnableConfigReloader=true` — cli/cmd/runtime/start.go:94,254), `CreateInstance` triggers this sequence:
  1. Controller goroutine: `ensureRepoReady` → pull #1 (clone / archive download #1), `updateProjectConfig` → **full parse #1**, `NewController`, ready, `Run`.
  2. Same RPC: `reloadConfig` — `updatedOn[instanceID]` is always missing at create, so it does pull #2 with `ForceHandshake: true`. The pull singleflight key includes the options (`repo.go:775`), so it does **not** dedupe against pull #1; it serializes behind it on the repo write lock. For **git**, this round is handshake-only (an admin `GetRepoMeta` RPC; `pullInner` gates the actual `git pull` on `UserTriggered` — repo.go:829). For **archives**, the forced handshake mints a **new** signed URL (V4 signature embeds a 15-minute expiry → different string every call; admin/server/repos.go:41 mints one per `GetRepoMeta`), and `archiveRepo.sync` compares `syncedDownloadURL != archiveDownloadURL` — not `archiveID` — so it **re-downloads the full archive** even though the content is identical.
  3. Git path: `ctrl.Reconcile(GlobalProjectParserName)` (config_reloader.go:156) blocks until the controller is ready, then enqueues the parser. If the parser's first invocation already started (usual case — `Run` starts it immediately after ready), `markPending` **cancels the in-flight first parse and restarts it** (controller.go:1117-1121), adding one more pull + full re-parse.
  4. Archive path: `restartController = true` → `EditInstance(inst, true)` → the just-started controller is torn down and **started again from scratch** (pull #3, full parse #2, catalog re-init, re-enqueue), followed by the parser reconcile (pull #4, full parse #3).
- **Perf impact:** For a git deploy: 3 sequential network pull rounds (clone + forced-handshake round + parser `git pull`), 2-3 full parses, ~1 extra `GetRepoMeta` + `GetConfig` admin round-trips. For an archive deploy: 2 full archive downloads (100 MB archive on a 100 Mbps pod ≈ +8-10 s wasted), 2 complete controller startups, 3 full parses. All of this sits between "deployment shows Running" and "parser starts creating resources", i.e. directly on the deploy → dashboard path.
- **Recommendation:** (a) Key `archiveRepo.sync` on `archiveID` instead of the signed URL (one-line fix, kills the duplicate download). (b) Skip the create-time `ctrl.Reconcile(parser)` and forced pull when the instance was created in this call (the controller will parse anyway) — e.g. have `create()` prime `configReloader.updatedOn[instanceID]` from the `CreateInstance` request, or pass a `justCreated` flag. (c) Remove the `UsesArchive` restart at creation: the fresh controller already has the current archive; the restart exists to re-open the repo connection for archive-ID changes, which cannot have happened yet. (d) Longer-term: let the parser reconciler reuse the parse result from `updateProjectConfig` (both run `parser.Parse` on the same commit within milliseconds).

### deep-cloud-deploy-02 [HIGH] One global config-reloader mutex serializes instance creation and config reloads across all instances on a host

- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `runtime/config_reloader.go:27-33` (single `ctxsync.RWMutex` + `updatedOn` map), `:48-53` (`reloadConfig` takes `r.mu.Lock` for its whole duration), `:60-68` (`admin.GetConfig` network call under lock), `:135-160` (repo pull + `getController` ready-wait under lock), `:188-217` (`periodicallyReloadConfigs`: serial sweep of every instance at boot and hourly).
- **Problem:** `reloadConfig` holds the process-wide mutex across: an admin `GetConfig` RPC, a forced repo pull (which on first call serializes behind a full clone/archive download), a blocking `Runtime.Controller()` wait for controller readiness (config_reloader.go:152 — bounded only by the caller's context), `EditInstance`, and `.env` writes. Every cloud `CreateInstance` calls `ReloadConfig` synchronously (registry.go:339-343), as does every admin-triggered `UpdateDeploymentInner`/variable push (`rt.ReloadConfig`, admin/deployments.go:546), plus the hourly sweep over all instances. On a multi-tenant static-provisioner host with N instances, one slow instance (big clone, unresponsive admin, controller stuck initializing) stalls **every other instance's** deploy completion and env-var propagation. At **runtime boot**, `reloadAllInstances` runs immediately with an empty `updatedOn` map, so every instance takes a forced-handshake pull — serially, behind the same lock — while all N controllers are simultaneously cold-starting; for archive-based instances it additionally forces a controller restart mid-startup (see finding 01).
- **Perf impact:** Sequential vs parallel: cost is `sum(per-instance reload)` instead of `max(...)`. With 100 instances × (GetConfig ~50 ms + occasional pull seconds), the boot sweep alone runs minutes; a single wedged `GetConfig` (e.g. 30 s timeout) inserts a 30 s bubble into every concurrent deploy on the host. This directly inflates p95 deploy-to-ready on shared runtimes.
- **Recommendation:** Hold the lock only around the `updatedOn` map (or shard a mutex per instance ID). Move `ctrl.Reconcile`/ready-wait outside any lock. Consider bounded parallelism (e.g. 8-way) for `reloadAllInstances`, and skip the boot sweep for instances whose deployment `UpdatedOn` matches a persisted value.

### deep-cloud-deploy-03 [MEDIUM] `reconcile_deployment` job dedup can drop a desired-state change that lands as the previous job completes

- **Category:** concurrency  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `admin/jobs/river/river.go:342-350` (unique `ByArgs` with `ByState` including `Running`), `admin/jobs/river/reconcile_deployment.go:50-51` (capture), `:86-89` (already-stopped early return **without** recheck), `:130-146` (final recheck before Work returns), `admin/deployments.go:729-741` (`triggerDeploymentReconcileJob` ignores the `Duplicate` flag).
- **Problem:** All deployment mutations follow: write `desired_status` → insert a `ReconcileDeployment` job. The insert is deduplicated against jobs in `Running` state, and the worker compensates with a final `DesiredStatusUpdatedOn` recheck. But the recheck reads the row *inside* `Work` (via `UpdateDeploymentStatus ... RETURNING *` at reconcile_deployment.go:130), while the job only leaves `Running` after `Work` returns and River's completer commits. A desired-status change + insert landing in the window between the recheck read and job completion is (a) skipped as a duplicate and (b) invisible to the recheck — the trigger is silently dropped and `triggerDeploymentReconcileJob` reports success. Two branches skip the recheck entirely: the "already stopped" early return (`:86-89`) — so a Start issued while a redundant stop-job is finishing can be lost for its entire duration — and the delete branch (`:122`, benign since the row is deleted).
- **Failure scenario:** User hibernates a project moments after pushing env vars: the update job is mid-completion; the stop's job insert is deduped; the recheck ran before the stop committed → deployment stays Running with `desired_status=stopped`. Nothing reconverges it: `validate_deployments` only tears down *non-primary* prod deployments after 3 h (validate_deployments.go:113), `hibernate_expired_deployments` re-enqueues stops only when the TTL is actually expired (postgres.go:647-661). A dropped **teardown** during `TeardownProject` makes the 5-minute poll (admin/projects.go:152-169) time out and the project delete fail until retried.
- **Recommendation:** Make the trigger level-based and race-free: either exclude `Running` from the unique `ByState` set (an extra queued job is a cheap no-op for this state-machine worker), or perform the final status update + recheck + completion in one transaction using River's transactional completion. Also propagate/log the `Duplicate` result in `triggerDeploymentReconcileJob`, and add the recheck to the already-stopped branch.

### deep-cloud-deploy-04 [MEDIUM] `UpdateDeployment` writes a stale `DesiredStatus` snapshot, letting project-wide updates resurrect stopping/deleting deployments

- **Category:** concurrency  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `admin/deployments.go:97-119` (`UpdateDeployment` writes `depl.DesiredStatus` via `UpdateDeploymentSafe`/`UpdateDeploymentDesiredStatus`), `admin/deployments.go:139-175` (`UpdateDeploymentsForProject` fetches deployments once, then fans out with limit 100), `admin/database/postgres/postgres.go:749-786` (unconditional `UPDATE ... SET desired_status=$1`).
- **Problem:** `UpdateDeployment` re-writes the deployment's `desired_status` using the caller's in-memory snapshot in order to bump `desired_status_updated_on` and re-trigger the reconcile job. Callers (`UpdateProjectVariables`, `UpdateProject`, `UpdateOrgDeploymentAnnotations`) read the deployment list first, then write later. A concurrent `StopDeployment`/`TeardownDeployment` (user action, TTL cron, redeploy teardown) that commits between the read and the write is clobbered back to `Running`, and the subsequent reconcile job restarts the deployment.
- **Failure scenario:** The 15-minute TTL cron stops an idle prod deployment while a user pushes env vars (`UpdateProjectVariables` → `UpdateDeploymentsForProject`). The stale write flips `desired_status` back to Running → the deployment is resurrected and billed. Worse: `RedeployProject` tears down the old deployment (desired=Deleted) while an org-rename annotation fan-out is in flight → the old deployment is revived as a *second running prod deployment*; it burns slots until `validate_deployments` reaps it as an orphan after 3 h (prod only; a revived dev/editable deployment lives until its TTL re-expires).
- **Recommendation:** Add a re-trigger primitive that does not overwrite `desired_status` (e.g. `UPDATE deployments SET desired_status_updated_on=now() WHERE id=$1` + job insert), or make the write conditional (`WHERE desired_status=$expected`) and skip on mismatch. `UpdateDeploymentSafe` should treat branch and desired-status as separate concerns.

### deep-cloud-deploy-05 [MEDIUM] Concurrent redeploy/hibernate flows have no per-project serialization: duplicate prod deployments and lost primary-pointer updates

- **Category:** concurrency  **Confidence:** high  **Novelty:** expands-existing (concurrency dimension of admin-projects-deploy-08's "not fault tolerant" TODO at admin/projects.go:21)  **Must-fix:** no
- **Location:** `admin/projects.go:336-406` (`RedeployProject`: create new depl → update `PrimaryDeploymentID` → teardown old), `admin/server/projects.go:2024-2069`/`2097-2158` (handlers, no idempotency/locking), `admin/projects.go:409-449` (`HibernateProject`), `admin/jobs/river/validate_deployments.go:108-122` (3-hour orphan sweep as the only safety net), `admin/jobs/river/hibernate_expired_deployments.go:61-96`.
- **Problem:** `RedeployProject` and `HibernateProject` are multi-step, non-transactional, and unguarded. Two concurrent `RedeployProject` calls (double-click, CLI + UI, wake-on-visit racing a manual redeploy) both read the same `PrimaryDeploymentID`, both provision a fresh deployment (2× slots), and race their `UpdateProject` writes — the loser's deployment keeps running but is unreferenced. `HibernateProject` racing `RedeployProject` can commit `PrimaryDeploymentID=nil` over the redeploy's new pointer, leaving a running prod deployment invisible to the UI. All `UpdateProject` writes are full-row (all fields from each caller's snapshot) with no optimistic concurrency, so *any* concurrent pair of project mutations loses one side's fields.
- **Failure scenario:** Org admin clicks "Redeploy" twice: two deployments provision on the static provisioner (compounding abp-02's overcommit risk), one becomes primary, the other consumes slots for up to 3 h before `validate_deployments` tears it down; meanwhile `CountProjectsQuotaUsage`-based quota checks over-count, blocking other creates in the org.
- **Recommendation:** Serialize project-level deployment mutations — a Postgres advisory lock keyed on project ID around `RedeployProject`/`HibernateProject`/`CreateProject(deploy=true)`, or route them through a per-project unique River job (the same pattern already used per-deployment). Add `updated_on`-based optimistic concurrency to `UpdateProject`.

### deep-cloud-deploy-06 [MEDIUM] A controller that exits with a fatal error is never restarted; one hung reconciler permanently downs the instance

- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `runtime/controller.go:26-27` + `:272-285` (`hangingTicker`: a reconcile hung >10 min after cancellation stops the whole controller with a fatal loop error), `runtime/registry.go:500-513` (on `!reopen`: `controllerErr` set, `running=false`, **no retry/backoff loop**), `runtime/registry.go:296-303` (`getController` then returns the stored error to every caller), `admin/jobs/river/deployments_health_check.go:210-236` (health check only logs `controller_error`; no remediation).
- **Problem:** The registry restarts a controller only on `EditInstance(restart=true)` or process restart. If `NewController` fails (catalog hiccup), `Run` exits with a loop error (catalog flush failure), or the hanging-reconcile tripwire fires (one model stuck in an uncancellable driver call — e.g. a wedged DuckDB/ClickHouse client), the instance is left permanently serving `controllerErr` for all queries and reconciles. The deployment still reports Running in the admin DB; `deployments_health_check` (every 10 min) detects `ControllerError` but only writes a log line. Recovery requires a human: env-var push (forces `EditInstance(restart=true)`), redeploy, or pod restart.
- **Failure scenario:** During first reconcile, one model's connector hangs past cancellation (10 min): the controller dies mid-hydration, dashboards never become ready, and the project stays broken indefinitely while showing a Running deployment.
- **Recommendation:** Auto-restart failed controllers with exponential backoff in `registryCache` (crash-loop style), and/or have `deployments_health_check` trigger `UpdateDeployment`/`ReloadConfig(restart)` when it sees a persistent `ControllerError`. At minimum surface the state in `DeploymentStatus` rather than logs only.

### deep-cloud-deploy-07 [MEDIUM] A transient connector test failure at first reconcile leaves the project stuck behind dependency errors (no automatic retry; refs gate all downstream resources)

- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `runtime/reconcilers/connector.go:83-87` (test on every reconcile; error returned with **no `Retrigger`**), `:95-103` (spec-change path: `SpecHash` persisted even when the test fails, so nothing marks it dirty), `runtime/reconcilers/util.go:18-60` (`checkRefs` converts an errored ref into a dependency error), `runtime/parser/parse_model.go:118,157` + `parse_metrics_view.go:857` (models/MVs raw-ref their connectors), `runtime/parser/parser.go:785-796` (connector refs are kept **only when the connector is explicitly defined as a resource**), `runtime/controller.go:1492-1500` (retrigger only honored when a reconciler asks for it).
- **Problem:** When a project defines connectors explicitly (a `connectors/*.yaml` file or `rill.yaml` connector entry — the standard pattern for ClickHouse/external-OLAP projects), the connector resource is a DAG parent of every model that uses it (`inferAmbiguousRefs` drops the ref otherwise, so implicit-DuckDB-only projects are unaffected). `testConnector` pings the connector on every reconcile; a transient failure (ClickHouse cluster waking, brief network blip during pod start — precisely the conditions during a fresh deploy) records an error on the connector and dependency errors on every downstream model. The controller has no error-retry policy, the connector reconciler sets no `Retrigger`, and a re-parse only re-enqueues resources whose specs changed — so the failure is sticky. The UI's per-model "refresh" won't help (the model re-fails `checkRefs` because the connector is still errored). Manual recovery does exist — `rill project refresh --all` (the `All` flag includes `ResourceKindConnector`; runtime/server/controller.go:444-453) or a trigger naming the connector re-runs its reconcile directly (refresh_trigger.go:76-94) — but nothing automatic, and the obvious remediations (model refresh, re-parse) don't work; otherwise it takes a controller restart (redeploy / env push) or a spec edit.
- **Failure scenario:** First deploy against a scale-to-zero ClickHouse: the ping races the cluster wake-up and fails once; every model and dashboard in the project shows a dependency error until someone intervenes with the right command, even though the infrastructure recovered seconds later.
- **Recommendation:** Return `Retrigger` with backoff from the connector reconciler on ping failure (e.g. 10 s → 1 m → 5 m), or add a general controller-level retry policy for errored resources. Consider treating a failed ping as a warning when the spec is unchanged (the comment at connector.go:84 already acknowledges transience).

### deep-cloud-deploy-08 [MEDIUM] Controller restarts re-enqueue and re-validate everything; runtime boot cold-starts all instances with unbounded concurrency

- **Category:** performance  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `runtime/controller.go:174-182` (`Run` enqueues every catalog resource on every start), `runtime/reconcilers/metrics_view.go:135-137` (explicit "no spec-hash skip" note) + `:142-182` (`ValidateAndNormalizeMetricsView` OLAP queries + unconditional state bump), `runtime/registry.go:200-217` (`init` starts all controllers concurrently, no limit), `runtime/config_reloader.go:203-204` (boot sweep on top).
- **Problem:** Every controller (re)start replays reconciliation of the entire project. Models no-op via spec hash, but each metrics view runs live validation queries against the OLAP and bumps its state version (invalidating downstream caches), each connector re-pings, and the parser re-pulls and re-parses. Because of finding 01, a single archive deploy performs this twice; on a runtime **version upgrade or pod restart** of a multi-tenant host, N instances × (repo pull + full parse + catalog load + M metrics-view validation queries + connector pings) start simultaneously with no cross-instance startup concurrency limit, hammering the admin service (`GetRepoMeta`/`GetConfig` per instance), the git/asset backends, and the shared OLAPs — inflating time-to-ready for every project on the host.
- **Perf impact:** For a 50-instance host averaging 10 metrics views each: ~500 OLAP validation queries + 50 pulls + 50 parses within the first minute of boot, plus the serialized config sweep (finding 02). Restart storms are the main reason "redeploys feel slow" beyond ingestion.
- **Recommendation:** Skip metrics-view revalidation when spec hash, model state version, and connector are unchanged (persist a validation hash in state); rate-limit concurrent controller cold-starts (small semaphore in `registryCache.init`); stagger the boot config sweep. Consider only enqueueing resources whose `StateUpdatedOn` predates the last successful reconcile rather than everything.

### deep-cloud-deploy-09 [LOW] Instance record is read-modify-written by four uncoordinated writers with no optimistic locking

- **Category:** concurrency  **Confidence:** medium  **Novelty:** new  **Must-fix:** no
- **Location:** Writers: `runtime/config_reloader.go:73-100,163` (`reloadConfig`), `runtime/runtime.go:140-207` (`UpdateInstanceWithRillYAML`, called from both `registryCache.updateProjectConfig` at registry.go:615-642 and the parser reconciler at project_parser.go:376-378), `runtime/runtime.go:211-255` (`UpdateInstanceConnector`, called per connector resource from connector.go:70,90). Store: `runtime/drivers/sqlite/registry.go:283+` (full-row UPDATE, no version guard); `registryCache.edit` (registry.go:375-396) serializes only the write, not the read-modify.
- **Problem:** Each writer does `Instance()` → shallow clone → mutate its own field family → `EditInstance` (full-row persist). Two overlapping writers commit the later one's stale snapshot of the other's fields. At instance creation, `reloadConfig` (admin-side vars/annotations/connector config) races the controller's `updateProjectConfig` and the parser's `reconcileProjectConfig` (rill.yaml connectors/vars) and per-connector `UpdateInstanceConnector` calls, all within a few hundred milliseconds.
- **Failure scenario:** An env-var push (`reloadConfig` writes `Variables`) lands inside the parser's `UpdateInstanceWithRillYAML` read-modify-write window → the new variables are reverted to their old values until the hourly reload or next parse. Conversely a `reloadConfig` commit inside the parser's window can wipe `ProjectConnectors` until the next parse — on a prod deployment (no file watcher) that can persist up to an hour, failing model reconciles with unknown-connector errors. Destructive interleavings are millisecond-wide, hence low severity, but the pattern guarantees eventual weirdness under load.
- **Recommendation:** Add a version/updated-on CAS to `EditInstance` and retry on conflict, or funnel all instance mutations through a single per-instance mutex (the registry already has the natural owner). Field-level merge (only persist the fields the writer owns) would also eliminate the cross-family clobbering.

### deep-cloud-deploy-10 [LOW] Migration template `lookup` of a non-model resource panics (recovered into a confusing error)

- **Category:** bug  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `runtime/reconcilers/migration.go:139-152` — `Lookup` callback does `res.Resource.(*runtimev1.Resource_Model)` (twice) with a single-value type assertion; the template function `lookup` passes any user-specified kind (runtime/parser/template.go:246-270, args parsed as `(kind, name)` at template.go:479-502).
- **Problem:** A migration whose SQL contains `{{ lookup "metrics_view" "my_mv" }}` (or any non-model kind whose resource exists — a not-found lookup returns a clean error first) hits an interface-conversion panic inside `ResolveTemplate`. The controller's invoke recover (controller.go:1317-1328) converts it to `panic: interface conversion: ...` on the migration resource — a misleading error, plus a scary stack trace in logs.
- **Failure scenario:** Any user migration that looks up an existing metrics view/explore/etc. errors with an internal panic message instead of a clean "lookup only supports models" error.
- **Recommendation:** Use the comma-ok assertion and return a helpful error (or support the other kinds by switching on the resource type). Sibling context: reconcilers-06/07 already cover this file's version-skipping bugs.

### deep-cloud-deploy-11 [LOW] Quota and branch-uniqueness checks in project/deployment creation are check-then-act

- **Category:** concurrency  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `admin/server/projects.go:501-520` (project/slot/deployment quotas read via `CountProjectsQuotaUsage`, then insert), `admin/server/deployment.go:309-318` (one-deployment-per-branch check), `:325-338` (quota checks), no corresponding DB constraints.
- **Problem:** Concurrent `CreateProject`/`CreateDeployment` calls both pass the quota reads and both insert, exceeding org quotas by the concurrency degree; two concurrent `CreateDeployment` calls for the same branch both pass the uniqueness check and create two deployments (two editable deployments pushing the same `rill/xxxx`-style branch corrupt each other's checkpoints). Low severity because the windows are small and the surfaces require deliberate racing, but the editable-deployment flow is user-facing (browser "edit" button).
- **Recommendation:** Enforce with the database: partial unique index on `(project_id, branch)` for live deployments, and quota checks inside the insert transaction (`SELECT ... FOR UPDATE` on the org row), mirroring the fix direction for abp-02.

### deep-cloud-deploy-12 [LOW] GitHub push arriving while the deployment is Pending is dropped; picked up only by the hourly config sweep

- **Category:** concurrency  **Confidence:** high  **Novelty:** expands-existing (admin-projects-deploy-07 covered the synchronous handler; this is a distinct lost-event window)  **Must-fix:** no
- **Location:** `admin/github.go:396-401` (webhook skips deployments whose status is not Running/Updating), `admin/jobs/river/reconcile_deployment.go:83,130` (status flips to Running only after `StartDeploymentInner` returns), `runtime/config_reloader.go:133-160` (hourly catch-up pull only when `cfg.UpdatedOn` advanced).
- **Problem:** During a first deploy, the runtime's parser performs its pull at controller start; the deployment stays Pending until the job finishes (`CreateInstance` return + status write). A commit pushed after the parser's pull but before the Running transition is skipped by the webhook ("deployment is not ready") and there is no periodic git poll — the commit deploys only when the hourly config reload notices `depl.UpdatedOn` advanced, or on the next push. The one-shot catch-up is guaranteed: the Running status write bumps `updated_on` (postgres.go:740-747) after the create-time reload primed `updatedOn[instanceID]`, and `GetConfig` returns `depl.UpdatedOn` (admin/server/deployment.go:790), so the next sweep force-pulls and re-triggers the parser exactly once.
- **Failure scenario:** User pushes a fix seconds after `rill deploy`/connect completes on the admin side; the dashboard serves the previous commit for up to ~1 h with no indication.
- **Recommendation:** Have the webhook fall through to `TriggerParser` for Pending deployments too (the parser trigger is idempotent and cheap — worst case the parser is already pulling the latest), or enqueue a delayed retrigger when a push is skipped due to status.

### deep-cloud-deploy-13 [MEDIUM] Redeploying an editable deployment deletes the git branch its replacement runs on, silently losing the edit session's work

- **Category:** data-loss  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `admin/projects.go:340-343,348-368` (`RedeployProject` creates the new deployment with `branch = prevDepl.Branch`, `editable = prevDepl.Editable`, then tears down the old one), `admin/deployments.go:461-473` (`DeleteDeploymentInner` deletes the branch of any editable deployment whose branch != primary), `runtime/drivers/admin/repo_git.go:125-155` (in editable mode a missing remote branch is silently **recreated from the primary branch** and pushed), `admin/jobs/river/reset_all_deployments.go:53-66` (iterates ALL deployments — including editable dev ones — through `RedeployProject`; enqueued via `EnqueueByKind("reset_all_deployments")`, cli/cmd/admin/start.go:444-455), `admin/server/projects.go:2097-2158` (deprecated `TriggerRedeploy` accepts arbitrary deployment IDs, including dev/editable).
- **Problem:** `RedeployProject` reuses the previous deployment's branch for the new deployment, then tears the old one down. For editable deployments, `DeleteDeploymentInner` assumes the branch is disposable: it checkpoints (GitPush) and then **deletes the branch** — the same branch the just-created replacement deployment is configured to clone. The create job and the teardown job are independent River jobs with no ordering. If the branch delete lands before the new instance's clone, the new runtime finds the branch missing and recreates it from the **primary** branch (repo_git.go:132-155), discarding every commit of the edit session (including the checkpoint just pushed). If the clone lands first, the remote branch is deleted afterwards and the next checkpoint push recreates it from the new clone — which is missing the old session's final checkpoint unless the checkpoint push happened to complete before the clone. Most interleavings lose un-merged browser edits with zero signal.
- **Failure scenario:** Ops runs `reset_all_deployments` (routine fleet maintenance, e.g. after a runtime upgrade): every project with an open editable edit session gets its session branch deleted/recreated-from-primary, and all users' unpublished edits vanish silently.
- **Recommendation:** In `RedeployProject`, skip the branch delete when the successor uses the same branch — e.g. pass a "preserve branch" flag through `TeardownDeployment`, or sequence teardown before create for editable deployments (checkpoint → delete old → create new on a fresh branch seeded from the checkpoint). At minimum, exclude editable deployments from `reset_all_deployments`. Related but distinct: the Tier-2 must-fix item about checkpoint-push *failure* during deletion (deployments.go:413-421) — this finding loses data even when the checkpoint push *succeeds*.

### deep-cloud-deploy-14 [LOW] A discarded or panicking reconcile_deployment job strands the deployment in a transitional status with no error surfaced

- **Category:** correctness  **Confidence:** high  **Novelty:** new  **Must-fix:** no
- **Location:** `admin/jobs/river/river.go:874-880` (`HandleError` on max attempts: log only), `:883-889` (`HandlePanic`: log + `SetCancelled: true` — job abandoned on the **first** panic), `admin/jobs/river/reconcile_deployment.go:59,71,91,110` (status set to Updating/Pending/Stopping/Deleting with a progress message before the `Inner` call), `admin/deployments.go:736` (the **only** writer of `DeploymentStatusErrored`: the job-insert failure path).
- **Problem:** The worker writes a transitional status ("Provisioning...", "Updating...", "Stopping...", "Deleting...") before doing the work; the terminal status is written only on success. If the job exhausts its 25 attempts (attempt^4 backoff — hours between late attempts, ~3 weeks total) or panics once (immediately cancelled by `HandlePanic`), nothing ever updates the deployment row: it shows "Provisioning..." (or another transitional state) indefinitely while `desired_status` stays unreconciled. No sweep repairs it: `validate_deployments` only reaps non-primary prod orphans, and the health check only logs. A later user action (hibernate/redeploy) does insert a fresh job (Cancelled/Discarded are not in the unique `ByState` set), so manual recovery works — but the UI gives no indication that anything failed.
- **Failure scenario:** A provisioner bug makes `StartDeploymentInner` panic (or fail persistently): the project page shows a healthy-looking "Provisioning..." spinner forever; support has to find the discarded River job in logs to explain it.
- **Recommendation:** On final failure (discard or `SetCancelled`), write `DeploymentStatusErrored` with the error message — either from `HandleError`/`HandlePanic` (both receive the job args, so the deployment ID is available) or via a small janitor that marks deployments stuck in transitional statuses with no live reconcile job. Also reconsider `MaxAttempts: 25` for this job (see Performance Notes item 6).

## Performance Notes

Ranked contributors on the deploy → first-dashboard-ready path, with rough costs and fixes:

1. **Model ingestion** — data-bound, 5-way parallel by default (`rill.models.concurrent_execution_limit=5`, drivers/registry.go:209). Inherent; expose/tune the limit per instance size. DuckDB writes further serialize inside the driver.
2. **Kubernetes provisioning** (when used) — `AwaitReady` polls the Deployment at 1 s and then pings with 2-10 s retry waits (kubernetes.go:397-432): pod schedule + image pull ≈ 30 s-3 min cold. Static provisioner ≈ 0 (slot upsert only). Fix: image pre-pull/warm pools.
3. **Duplicate pulls/parses/controller starts at create** (finding 01) — git: 3 pull rounds + 2-3 parses; archive: 2 full downloads + 2 controller starts + 3 parses. Fix list in finding 01; the `archiveID` sync check and skipping the create-time restart are the two cheapest wins.
4. **Global config-reload mutex** (finding 02) — cross-instance serialization of `CreateInstance` completion and env propagation; worst at boot/hourly sweep on multi-tenant hosts. Fix: per-instance locking + parallel sweep.
5. **Restart replay** (finding 08) — every restart replays parser pull/parse + per-MV OLAP validation queries + connector pings; boot storms multiply by instance count with no concurrency cap.
6. **River job overheads** — enqueue→pickup ~10-100 ms (fine), but retry backoff is `attempt^4` seconds with `MaxAttempts: 25` (river.go:341, 188): a single transient provisioning error adds 16 s (attempt 2) or 81 s (attempt 3) before the deploy resumes. Consider a gentler early-retry curve (e.g. 2 s, 5 s, 15 s) for `reconcile_deployment`.
7. **Connector test pings** (connector.go:151-160) — one cold connection open + ping per connector, DAG-ordered before all models. Small (~100-500 ms) but on the critical path; could overlap with model scheduling for already-tested specs.
8. **Metrics-view validation** — 1-3 OLAP queries per MV after models complete (metrics_view.go:142-152); on scale-to-zero ClickHouse the first query pays the wake-up. Cache validation results by (spec hash, model state) per finding 08.
9. **Per-model post-build stats** — `COUNT(*)` + size probe after each model build (model.go:771-813, noted in reconcilers.md); cheap on DuckDB, potentially a scan on external OLAPs.
10. **`TriggerParserAndAwaitResource` polling** (admin/projects.go:507-539) — 1 s poll, 1 min cap; only affects virtual-file (personal canvas) flows.
11. **`ParseDotenv` full project parse** (cli/pkg/local/project.go:11-25) — the local deploy flow parses the whole project just to read `.env`; negligible but easy to trim.

Not on the hot path but worth knowing: deployment status flips to Running only after `CreateInstance` returns, and `CreateInstance` blocks on controller readiness (clone + parse) via `reloadConfig`'s `ctrl.Reconcile` — so "Provisioning..." in the UI actually covers clone+parse time, and the frontend can reach the runtime immediately once Running.
