# PLG & First-User Experience — Code Review
**Scope:** `web-common/src/features/{welcome,onboarding,sample-data,add-data,sources,help,templates,project}`, `web-local/src/routes` (welcome / home / deploy), `cli/cmd/start`, `cli/pkg/local`, `runtime/server/examples.go`, `runtime/server/generate_metrics_view.go`, `runtime/server/generate_canvas_dashboard.go`, plus the reconciliation/polling helpers the add-data flow depends on.  |  **Health:** fair

## Overview
This area owns the `rill start` → splash → (pick example | add data | generate sample data) → import → auto-generate model/metrics/dashboard → deploy funnel. The happy path is well-built: the add-data flow is a clean state machine (`AddDataStateManager`), the AI generators degrade to deterministic "simple" generators, and routing between welcome/developer/preview modes is thoughtfully guarded. The biggest risks are in the *unhappy* paths that first-run users hit constantly: several flows can spin forever or dead-end silently when AI is unavailable, a connector is misconfigured, or a backend call errors. The most consequential is the splash "Generate sample data" CTA, which is not gated by the same flags as its home-screen twin and can silently do nothing. There is also real duplication in the add-data generators (a model plus metrics view plus two dashboards per source) and a dead `/deploy?org=` deep link that 404s. Overall the code quality is good; the gaps are robustness and funnel-completeness rather than structural.

## Findings

### plg-first-run-01 [HIGH] Splash "Generate sample data" is ungated and can silently dead-end when the developer agent can't stream
- **Category:** product-improvement  **Confidence:** medium  **Location:** `web-common/src/features/add-data/OnboardingGenerateSampleData.svelte:32` + `web-local/src/routes/(misc)/welcome/+page.svelte:41`; `web-common/src/features/sample-data/generate-sample-data.ts:59-64`; `web-common/src/features/chat/layouts/sidebar/sidebar-store.ts:66-71`; `web-common/src/features/chat/DeveloperChat.svelte:13`
- **Problem:** The splash card `OnboardingGenerateSampleData` is rendered unconditionally on the welcome screen (`welcome/+page.svelte:41`), but its handler `generateSampleData()` drives generation entirely through the developer chat agent: `developerChatActions.startChat(prompt)` → `waitUntil(() => get(chatMounted))` → `eventBus.emit("start-chat", …)`. The chat only mounts when `{#if $developerChat && $developerChatOpen}` (`DeveloperChat.svelte:13`). By contrast, the home-screen twin `GenerateSampleData` *is* gated behind `{#if $developerChat}` (`GenerateSampleData.svelte:52`). There is no AI/agent fallback in `generateSampleData`. Note the backend default for `developer_chat` is `"true"` (`runtime/feature_flags.go:54`), so the flag is normally on for local Rill Developer — the fully-silent path requires an explicit `developer_chat: false` opt-out in `rill.yaml`; the more common failure is the agent being unable to stream (e.g. AI unavailable when not logged in).
- **Failure scenario (flag off, e.g. explicit `developer_chat: false`):** User clicks "Generate sample data", submits a prompt. An empty project is created (`generateSampleData(..., initializeProject=true, ...)`); `startChat` sets `developerChatOpen=true` but the chat never mounts (flag off), so `chatMounted` never becomes true and `start-chat` fires into the void after the inner `waitUntil` default 30 s timeout. Meanwhile the outer `await waitUntil(() => get(conversation.isStreaming))` (30 s default) never sees streaming, then `await waitUntil(() => !get(conversation.isStreaming), -1)` returns immediately (already not streaming). Net: ~30 s spinner, then the user is left on an empty project with no data, no dashboard, and no error.
- **Failure scenario (flag on, AI unavailable):** The chat mounts and streams, but the agent call fails; the user is left with an empty project and a chat panel showing an error rather than a generated dataset.
- **Recommendation:** Gate the splash CTA with the same `$developerChat` (and `$ai`) condition used by the twin; when those are off or the agent can't be reached, hide the CTA or fall back to a deterministic local mock-data generator. Give `generateSampleData` a bounded timeout with a visible error + retry instead of the infinite `-1` wait.

**Verification:** CONFIRMED — `OnboardingGenerateSampleData` is rendered with no flag gate on the splash (`web-local/src/routes/(misc)/welcome/+page.svelte:41`) and calls `void generateSampleData(...)` (`OnboardingGenerateSampleData.svelte:32`), while its home-screen twin is wrapped in `{#if $developerChat}` (`web-common/src/features/sample-data/GenerateSampleData.svelte:52`). The chat panel only mounts under `{#if $developerChat && $developerChatOpen}` (`web-common/src/features/chat/DeveloperChat.svelte:13`), and `generateSampleData` has no non-chat fallback: it does `developerChatActions.startChat(prompt)` → `waitUntil(() => get(conversation.isStreaming))` (default 30 s, `web-common/src/lib/waitUtils.ts:7`) → `waitUntil(() => !get(conversation.isStreaming), -1)` (`generate-sample-data.ts:59-64`); `startChat` itself waits on `chatMounted` (`sidebar-store.ts:66-71`). When the chat never mounts, the second wait returns immediately (already not streaming) and the flow ends "successfully" on an empty project with no error notification (the catch at `generate-sample-data.ts:65-70` only fires on a thrown error, and `waitUntil` timing out does not throw). Backend default `developer_chat: "true"` confirmed at `runtime/feature_flags.go:54`, so the fully-silent path requires an explicit opt-out; the AI-unavailable path is the common one.

**Manual Reproduction Steps (for QA):**
1. Create an empty directory and add a `rill.yaml` containing only `features:` / `  developer_chat: false` — or simpler: start `rill start` in an empty directory, then before step 3, add `features:\n  developer_chat: false` to the generated `rill.yaml`. (Alternative failure mode: leave the flag on but be logged out / offline so the AI agent cannot stream.)
2. Run `rill start` in an empty directory so the welcome splash appears.
3. Observe (bug part 1): the "Generate sample data" card is still shown on the splash even with `developer_chat: false`, while the equivalent home-screen button would be hidden.
4. Type a prompt (e.g. "Generate a model with mock data for: e-commerce transactions") and press Enter.
5. Expected: sample data is generated and a model appears, or a clear error explains why not.
6. Actual (flag off): an empty project is created, a spinner/overlay shows briefly, the chat sidebar never opens, and after roughly 30 seconds nothing happens — no data, no model, no error message; the user is stranded on an empty project. Actual (flag on, not logged in / AI unreachable): the chat panel opens and shows a chat error, but the project is still empty and no dashboard is produced.

### plg-first-run-02 [MEDIUM] Standalone "Generate dashboard with AI" can spin forever when the backend call hard-errors
- **Category:** product-improvement  **Confidence:** high  **Location:** `web-common/src/features/entity-management/actions/actions.ts:162-179` (`pollForFileCreation`); `web-common/src/features/metrics-views/ai-generation/generateMetricsView.ts:226-251` and `:405-425`; `runtime/server/generate_metrics_view.go:125-135,178-186`
- **Problem:** The standalone generate CTAs fire the request as `void runtimeServiceGenerateMetricsViewFileWithSignal(...)` / `void runtimeServiceGenerateMetricsViewFile(...)` and detect completion by polling for the output file to appear. `pollForFileCreation` loops `while (!abortSignal.aborted)` with no timeout; the two hand-rolled loops in `generateMetricsView.ts` loop `while (!isAICancelled)` with no timeout. `GenerateMetricsViewFile` writes a fallback (simple-generator) file only when the *AI step* fails after the table lookup and OLAP connection succeeded (`generate_metrics_view.go:170-175`). On a hard error — OLAP connect failure (`:125-128`), table not found (`:132-135`, e.g. a source that failed to ingest), or repo write failure (`:183-186`) — it returns an error *before writing any file*, so the polled file never appears and the `void` rejection is swallowed.
- **Failure scenario:** User clicks "Generate dashboard with AI" on a table whose server-side lookup fails; the backend returns an error that is dropped by `void`; the file is never written; the overlay ("Hang tight! …") spins forever with only a "Cancel" button. Cancel is the sole escape (it re-requests with `useAi=false`, which will also fail if the table genuinely doesn't exist).
- **Note:** The add-data import flow is *not* affected here — `runCreateMetricsViewStep`/`runCreateCanvasStep` (`import.ts:297,368`) **await** the generate call, so a hard error throws and surfaces in `GenerateDashboardStatus`'s try/catch. The gap is specific to the fire-and-forget standalone CTAs.
- **Recommendation:** Await the generate call (or surface its rejection) and add a max-wait to `pollForFileCreation` and the manual loops that transitions to a visible error with the backend message plus Retry / Edit YAML.

**Verification:** CONFIRMED — `useCreateMetricsViewFromTableUIAction` fires `void runtimeServiceGenerateMetricsViewFileWithSignal(...)` (`generateMetricsView.ts:114`) and then awaits `pollForFileCreation` (`:128`), which loops `while (!abortSignal.aborted)` with no timeout (`web-common/src/features/entity-management/actions/actions.ts:168-178`). The hand-rolled loops at `generateMetricsView.ts:237` and `:412` similarly loop `while (!isAICancelled)` after `void` calls at `:226` and `:405`. On the backend, `GenerateMetricsViewFile` returns an error before writing any file on OLAP connect failure (`runtime/server/generate_metrics_view.go:125-128`), table lookup failure (`:132-134`), or `repo.Put` failure (`:183-185`); the simple-generator fallback (`:170-174`) only runs after the lookup succeeded. So the polled file never appears and the rejection of the `void` promise is dropped. The add-data import flow is indeed unaffected: `import.ts:297` and `:368` await the generate calls.

**Manual Reproduction Steps (for QA):**
1. Start `rill start` on a project and create a source that fails to ingest (e.g. add a source YAML pointing at a non-existent file such as `path: data/missing.csv`), so a model/source resource exists but its table was never created in DuckDB.
2. In the left navigation, open the "..." menu on that broken source/model and click "Generate dashboard" (or use the "Create dashboard" CTA in the model workspace header — both go through `useCreateMetricsViewFromTableUIAction`).
3. Expected: an error such as "table not found" with a Retry or Edit-YAML option.
4. Actual: the full-screen overlay "Hang tight! AI is personalizing your dashboard" spins forever; the backend error is silently dropped. The only escape is "Cancel", which retries with `useAi=false` and also fails (table still doesn't exist), leaving the user stuck or with another swallowed error.

### plg-first-run-08 [LOW] `waitForResourceReconciliation` compares `stateVersion` as strings, which is wrong across digit boundaries
- **Category:** correctness  **Confidence:** medium  **Location:** `web-common/src/features/entity-management/actions/actions.ts:96-99`; caller `web-common/src/features/add-data/manager/steps/connector.ts:97-104,128-134`
- **Problem:** When `prevStateVersion` is supplied, the "new version arrived" check is `newStateVersion > prevStateVersion` on **strings** (`actions.ts:98`). `meta.stateVersion` is proto `int64` serialized as a string (`resources.proto:48` → `stateVersion?: string`), so this is a lexicographic comparison of numeric strings: `"10" > "9"` is `false`. The only caller that passes `prevStateVersion` is the add-connector validate flow (`connector.ts:133`, `connectorStartingVersion = meta.stateVersion` of an existing connector). When a re-validated connector crosses a base-10 digit boundary (version 9→10, 99→100, …), `newVersionArrived` stays `false`, so the `RECONCILE_STATUS_IDLE` branch never fires and the `while (true)` loop (no timeout, `:84`) keeps polling every 2 s indefinitely — hanging the "Add connector" validate step.
- **Secondary (lower confidence):** All four import calls (`import.ts:246,306,350,375`) *omit* `prevStateVersion`, so `newVersionArrived` defaults to `true` and the helper returns on the first observed IDLE. For a re-triggered existing model that is momentarily still IDLE from a prior reconcile (`runCreateModelStep` triggers a refresh then immediately polls), this can return before the new reconcile completes and generate a metrics view from stale schema. This is a timing-dependent race that could not be confirmed statically.
- **Recommendation:** Compare versions numerically (`Number(a) > Number(b)`), add an overall timeout to the `while (true)` loop, and capture/pass the pre-write `stateVersion` in the import steps.

**Verification:** CONFIRMED — `web-common/src/features/entity-management/actions/actions.ts:96-99` compares `newStateVersion > prevStateVersion` where both are typed `stateVersion?: string` (proto int64 → string, `web-common/src/runtime-client/gen/index.schemas.ts:2392`), so the comparison is lexicographic (`"10" > "9"` is false); the enclosing loop is `while (true)` with no timeout (`actions.ts:84`). The one caller passing `prevStateVersion` is the add-connector validate flow: `connectorStartingVersion` is read from the resource cache (`web-common/src/features/add-data/manager/steps/connector.ts:98-104`) and passed at `:128-134`. The secondary note also checks out: all four `waitForResourceReconciliation` calls in `import.ts` (`:246,306,350,375`) omit `prevStateVersion`, making `newVersionArrived` default true.

**Manual Reproduction Steps (for QA):**
1. Precondition: an existing connector resource whose `stateVersion` is at 9 (or 99). Each edit-and-revalidate cycle bumps the version, so: run `rill start`, add a connector (e.g. ClickHouse or Postgres) via "Add data", then repeatedly edit and re-save/re-test the same connector until its `meta.stateVersion` reaches 9 (inspect via `http://localhost:9009/v1/instances/default/resources` or the API response in devtools).
2. With `stateVersion = "9"`, open the Add data flow for that same connector name again and click Test/Connect so the validate step runs (this is the path that passes `prevStateVersion`).
3. Expected: validation completes when the connector reconciles to version 10.
4. Actual: `"10" > "9"` is false as strings, so `newVersionArrived` never becomes true; the validate step polls every 2 s forever and the wizard hangs on the connecting/testing state with no timeout. (Timing-sensitive: if the cached starting version read in step 2 is not exactly at a digit boundary, the bug does not trigger — retry across the 9→10 boundary.)

### plg-first-run-13 [LOW] `UnpackExample` can leave a partially-unpacked, broken project if a file write fails mid-loop

## Product Improvements
The product-improvement findings above are: **01** (splash sample-data dead-end — highest priority), **02** (infinite AI spinner on the standalone CTA), **04** (silent unpack failures), **05** (5 s example delay), **06** (four resources per source), **11** (missing quick-pick error state), **12** (dimension-less dashboards), **13** (partial unpack). Common theme: the first-run happy path is polished, but the failure and "AI unavailable" paths lack timeouts, fallbacks, and user-visible errors, so friction turns into silent dead-ends precisely when a new user is least equipped to recover.

## New Feature Ideas
1. **Offline/deterministic sample-data generator (M).** A bundled DuckDB-based mock generator (templated `range()`/`random()` datasets for common domains) used as the fallback whenever the AI agent is unavailable. Directly removes the finding-01 dead-end and makes "Generate sample data" work with no login and no network.
2. **One-click seeded datasets on the splash (M).** Ship a few small Parquet datasets (e-commerce, web analytics, ad spend) selectable on the welcome screen so a user with no data of their own reaches a real dashboard in one click — the fastest possible aha for the no-data segment.
3. **Reconciliation-driven "first dashboard" progress + skip (M).** Replace the fixed 5 s reload (finding 05) and the opaque spinners with a live progress panel bound to resource reconcile status, including "continue in background" and per-step timeouts.
4. **Guided onboarding checklist on the home screen (M).** A persistent "Import data → Model → Metrics → Dashboard → Deploy/Share" tracker with live completion state, giving new users orientation and a clear next action at every step.
5. **"Test connection" + table preview before import (M).** In `ConnectorForm`, validate credentials and preview available tables before writing YAML, converting silent post-import failures into an inline, correctable error (complements findings 02/11).
6. **Post-deploy share funnel (S).** After a successful deploy, present an explicit share step — copy public URL, invite teammates, open in Cloud — turning the current terminal endpoint of the funnel into a viral loop.
7. **Backend-driven example gallery with reachability badges (M).** Drive the welcome cards from `ListExamples`, label examples that need network/credentials (e.g., the ClickHouse GitHub-analytics example), and pre-flight-check reachability before unpacking so a broken example never lands the user on an errored dashboard (addresses findings 04/10/13).
8. **Consistent error-recovery affordances across generate/import (M).** Standardize a Retry / Retry-without-AI / Edit-YAML / Fix-with-AI action set on every failure surface (`ImportDataStatus`, the overlay spinners), so no state is a dead-end (addresses finding 02).
9. **First-run activation funnel instrumentation (S).** Fix `emitStartEvent` (finding 07) and add explicit funnel events (welcome_viewed → source_added → metrics_created → dashboard_viewed → deployed) so the PLG funnel is measurable and optimizable.
10. **CLI "deploy to share" nudge (S).** After `rill start` detects a working dashboard, print a clickable `rill deploy` hint in the terminal to pull local users toward the share/cloud step.
