# Runtime Core (controller, caches, security) — Code Review

**Scope:** `runtime/*.go` root files (`controller.go`, `catalog_cache.go`, `connection_cache.go`, `connections.go`, `registry.go`, `runtime.go`, `security.go`, `resolver.go`, `resources.go`, `repos.go`, `query.go`, `api.go`, `canvases.go`, `config_reloader.go`, `health.go`, `feature_flags.go`, `request_source.go`), `runtime/storage`, `runtime/canvas`. Cross-referenced `runtime/resolvers`, `runtime/metricsview/executor`, `runtime/pkg/conncache`, `runtime/server/auth`, `admin/server/runtime_jwt.go`. | **Health:** needs-attention

## Overview

This is the heart of the data plane: `controller.go` schedules and runs reconcilers over a DAG, `catalog_cache.go` is the in-memory resource store, `registry.go` manages per-instance controller lifecycles, `security.go` resolves row/field access policies, and `resolver.go`/`query.go` implement the two query-caching frameworks. The code is dense but generally high quality — the scheduler's mark/sweep invariants, the buffered single-token notification channels, and the RWMutex/flush interplay are carefully reasoned and largely correct. The biggest risk is at the security boundary: the newer resolver query cache omits the claims' `AdditionalRules` from its cache key (a cross-security-context data-leak vector for magic-auth tokens on the resolver-based query paths). A permanent goroutine hang on the instance-deletion error path, a global lock held across security template evaluation, and a copy/paste error in the scheduler's descendent-error clearing round out the notable findings. Several items originally rated medium were downgraded after verification (see Verification Notes).

## Findings

### runtime-core-01 [HIGH] Resolver query cache key omits `AdditionalRules`, leaking row-filtered data across security contexts

**Status (2026-07-25):** ✅ Fixed and merged in [#9704](https://github.com/rilldata/rill/pull/9704).

- **Category:** security  **Confidence:** high  **Location:** `runtime/resolver.go:210-218` (claims contribution in `Runtime.Resolve`)
- **Problem:** When building the query cache key (`resolver.go:206-240`), only `opts.Claims.UserAttributes` is hashed. `claims.AdditionalRules` and `Permissions` are excluded. The metrics resolver applies security derived from the *full* claims: `newMetrics` calls `ResolveSecurity(ctx, instanceID, opts.Claims, res)` and passes the resulting row filter / field access into the executor (`resolvers/metrics.go:71-85`), and `AdditionalRules` flows into that resolution via `expandTransitiveAccessRules` / `resolveRules` (`security.go:255-261`). The resolver's own `CacheKey` is purely data-freshness + the client query (`metrics.go:106-122`, backed by `cacheKeyForMetricsView` which resolves with `SkipChecks: true` — `resolvers/util.go:32-39`), so it contributes no security context. Two `SecurityClaims` differing only in `AdditionalRules` therefore collide on one cache key. Note: access allow/deny is *not* bypassed, because `newMetrics` checks `security.CanAccess()` per request before the cache lookup (`metrics.go:76`); the leak is specifically of **row-filtered / field-limited result data** between two callers who can both access the view but should see different rows/fields.
- **Failure scenario:** A non-streaming metrics view (result caching is ON by default — `executor.CacheKey` returns cacheable for non-streaming Rill-managed tables, `metricsview/executor/executor.go:116-124`). Magic-auth token A embeds row filter `region = 'US'`; token B embeds `region = 'EMEA'`. Both are anonymous/shared links, so `Attributes` (→ `UserAttributes`) is empty/equal (`admin/server/runtime_jwt.go:119-124`: `attr = mdl.Attributes`, `rules = securityRulesFromMagicAuthToken(...)`). A viewer runs the same metrics query under both tokens through a resolver-cached path — the AI agent metrics tool (`runtime/ai/metrics_view_query.go:266`) or a custom API defined with `resolver: metrics` (`runtime/server/api.go:77-83`), both of which pass real request claims. Token A populates the cache with US-filtered rows; token B gets a cache hit and is served US rows instead of EMEA. The legacy `Query` framework does **not** have this bug because `Key()` marshals the whole struct including `SecurityClaims` (`queries/metricsview_aggregation.go:50-51` + `SecurityClaims.MarshalJSON` at `security.go:103`), and the gRPC dashboard aggregation handler uses that safe path (`server/queries_metrics.go:85`) — this asymmetry confirms the resolver path is the wrong one.
- **Recommendation:** Fold the full resolved security context into the resolver cache key. Simplest correct fix: hash the entire `opts.Claims` (via its `MarshalJSON`, as the legacy path does) instead of just `UserAttributes`; or hash the `ResolvedSecurity` (row filter + field access + query filter) that will actually be applied. Guard with a test that two claims differing only in `AdditionalRules` produce different keys.

**Verification:** CONFIRMED — `runtime/resolver.go:206-240` hashes only `opts.Claims.UserAttributes` (`:210-218`) plus the resolver cache key and refs; nothing else about the claims enters the key. The metrics resolver's own `CacheKey` (`runtime/resolvers/metrics.go:106-122`) is data-freshness + query JSON only, while `newMetrics` applies security resolved from the full claims (`runtime/resolvers/metrics.go:71-85`), and `AdditionalRules` (defined at `runtime/security.go:77-79`) flows into that resolution via `expandTransitiveAccessRules` at `runtime/security.go:255`. Magic-auth tokens set `attr = mdl.Attributes` and rules via `securityRulesFromMagicAuthToken` (`admin/server/runtime_jwt.go:119-120`), so two tokens with identical attributes but different embedded row filters collide on one resolver cache key. Reachable via the AI metrics tool (`runtime/ai/metrics_view_query.go:264-268`) and custom APIs (`runtime/server/api.go:71-82`), both of which pass request claims into `Runtime.Resolve`.

**Manual Reproduction Steps (for QA):**
1. Deploy a project to Rill Cloud with a non-streaming metrics view (DuckDB-backed, result caching on by default) that has a dimension such as `region`, and a custom API file (e.g. `apis/leak_test.yaml`) using `type: api` with the `metrics` resolver (`metrics_view: <name>` plus a query aggregating by `region`).
2. Create two magic-auth share tokens for the dashboard: token A with row filter `region = 'US'`, token B with row filter `region = 'EMEA'`. Do not attach user-specific attributes (use plain anonymous share links).
3. With token A's JWT as the bearer token, call `GET /v1/instances/<instance_id>/api/leak_test` and note the rows returned (US only).
4. Within the cache TTL, call the same endpoint with token B's JWT.
5. Expected: only EMEA rows. Actual (bug): US rows are returned — token B receives token A's cached, US-filtered result.

### runtime-core-02 [HIGH] `DeleteInstance` blocks forever when the registry store delete fails
- **Category:** concurrency  **Confidence:** high  **Location:** `runtime/registry.go:114-120` (with `registryCache.delete` at `:398-402`)
- **Problem:** `registryCache.delete` returns `(nil, err)` when `store.DeleteInstance` fails. The caller logs the error but does not return, then executes `<-completed` on the `nil` channel. A receive from a `nil` channel blocks forever, and there is no `select`/`ctx.Done()` guard, so even request-context cancellation cannot free it.
- **Failure scenario:** During deployment teardown (`admin/deployments.go` → gRPC `DeleteInstance`) or `rill sudo runtime delete-instance`, a transient metastore error makes `store.DeleteInstance` fail. The handling goroutine hangs permanently, the RPC never returns (ignoring client cancellation), and the instance is left present in both the registry DB and the in-memory cache. Repeated failures leak a goroutine each.
- **Recommendation:** After logging the error, return it (or `return nil` for idempotency) before the receive; and/or guard the receive with `select { case <-completed: case <-ctx.Done(): }`. At minimum, nil-check `completed` before receiving.

**Verification:** CONFIRMED — `runtime/registry.go:398-402`: `registryCache.delete` returns `(nil, err)` when `r.store.DeleteInstance` fails (and also at `:409` when the instance is missing from the in-memory map). The caller `DeleteInstance` (`runtime/registry.go:114-120`) only logs the error and then unconditionally executes `<-completed` at `:120` with no `select`/`ctx.Done()` guard; a receive from a nil channel blocks forever.

**Manual Reproduction Steps (for QA):**
Not cleanly user-reproducible without fault injection (requires the metastore delete to fail). With fault injection:
1. Run a cloud dev stack (`rill devtool start cloud`) with a deployed project, then make the runtime's registry store fail deletes (e.g. stop or firewall the runtime's metastore DB, or revoke DELETE on the instances table).
2. Run `rill sudo runtime delete-instance <instance_id>` (or trigger project hibernation/teardown from the admin service).
3. Expected: the RPC returns an error and can be retried. Actual (bug): the RPC never returns, even after client cancellation; each retry leaks another permanently blocked goroutine (visible in the runtime's `/debug/pprof/goroutine` dump as a goroutine parked in `chan receive` at `registry.go:120`).
Confirm in code: `runtime/registry.go:398-402` (nil channel on error) and `:114-120` (unguarded receive).

### runtime-core-03 [MEDIUM] `resolveSecurity` holds one global mutex across template evaluation
- **Category:** performance  **Confidence:** high  **Location:** `runtime/security.go:280-341`
- **Problem:** `p.lock.Lock()` is taken at `:280` and held until `:341`, covering not just the LRU cache `Get`/`Add` but the entire cache-miss computation: building `TemplateData` and running `ResolveTemplate` / `EvaluateBoolExpression` for every access/field/row-filter rule. `securityEngine` has a single `sync.Mutex` shared across all resources and users of the runtime, so all cache-miss security resolutions are fully serialized instance-wide (and cache hits also contend on the same mutex). Cache hits are the common, fast case; the concern is serialized cache-miss computation.
- **Failure scenario:** A burst of concurrent dashboard/API requests each triggering a security cache miss (e.g. after a metrics-view state bump invalidates keys) serializes on this mutex, adding latency proportional to template-resolution cost even though the work is independent per request.
- **Recommendation:** Hold the lock only around `cache.Get` and `cache.Add`. Compute the `ResolvedSecurity` outside the lock (accepting occasional duplicate computation on concurrent misses), or use a per-key singleflight. This matches how the query caches are structured. Consider sharding the cache/lock per instance.

**Verification:** CONFIRMED — `runtime/security.go:280-281`: `p.lock.Lock()` with `defer p.lock.Unlock()`, so the single `securityEngine` mutex is held from the cache `Get` at `:283` through the entire cache-miss computation (building `TemplateData` at `:292-300`, evaluating every access/field/row-filter rule at `:304-331`) until the function returns at `:342`. `securityEngine` has one `sync.Mutex` and one LRU shared runtime-wide (`newSecurityEngine` at `:245`), serializing all instances' security resolutions.

**Manual Reproduction Steps (for QA):**
Not directly user-reproducible as a functional bug — it manifests only as latency under concurrency. To observe:
1. Create a project with a metrics view whose security policy uses templated rules (e.g. a row filter referencing `{{ .user.email }}`).
2. Load-test the runtime with many concurrent users (distinct emails, so each is a cache miss) querying the dashboard, e.g. 100 concurrent requests immediately after editing the metrics view (which bumps `StateUpdatedOn` and invalidates all cached policies).
3. Expected: security resolutions proceed in parallel. Actual: they serialize; a mutex profile (`/debug/pprof/mutex`) shows contention on `securityEngine.lock`, and p99 latency grows roughly linearly with concurrency.
Confirm in code: `runtime/security.go:280-342` (lock scope spans template evaluation).

### runtime-core-04 [LOW] Built-in alert/report owner check can grant access on an empty user id
- **Category:** security  **Confidence:** medium  **Location:** `runtime/security.go:451` (alert) and `runtime/security.go:527` (report)
- **Problem:** The owner check is `if spec.Annotations != nil && userID == spec.Annotations["admin_owner_user_id"]`. When the annotation key is absent, the map lookup yields `""`; if `userID` is also `""`, the comparison is true and the caller is treated as the owner (`explicitAllow = true`). The analogous canvas rule guards against exactly this with `ownedByUser := userID != "" && userID == spec.Annotations["admin_owner_user_id"]` (`:610`), showing the intended semantics — the alert and report rules lack the `userID != ""` guard.
- **Failure scenario:** An alert/report whose `spec.Annotations` is non-nil but does not contain `admin_owner_user_id` — reachable because project-YAML alerts/reports accept arbitrary annotations (`parser/parse_alert.go:382`, `parser/parse_report.go:278`) — is accessed by a principal whose resolved `id` attribute is empty (anonymous / empty-subject JWT; `runtime/server/auth/claims.go` defaults `id` to the empty `Subject`). The owner check passes and access is granted (including exposure of notifier recipient emails) despite the caller not being owner, recipient, or admin. Reachability is narrow: it requires both the specific annotation shape *and* an empty-subject caller. Admin-created alerts/reports always set `admin_owner_user_id` and so are unaffected.
- **Recommendation:** Mirror the canvas guard: only treat the caller as owner when `userID != "" && userID == spec.Annotations["admin_owner_user_id"]`. Extract a shared helper so all three built-in rules stay consistent.

**Verification:** PLAUSIBLE — the missing guard is real: `runtime/security.go:451` (alert) and `:527` (report) both read `if spec.Annotations != nil && userID == spec.Annotations["admin_owner_user_id"]`, so an absent annotation key (`""`) matches an empty `userID` (which stays `""` when `claims.UserAttributes` is empty, `:444-448` / `:520-524`). The canvas rule has the intended `userID != ""` guard at `:610`. Rated PLAUSIBLE rather than CONFIRMED because exploitation requires the conjunction of a non-admin-created alert/report carrying some annotation other than `admin_owner_user_id` AND a caller whose resolved `id` attribute is empty — both uncommon.

**Manual Reproduction Steps (for QA):**
1. In a project, define an alert in YAML (e.g. `alerts/test.yaml`) with an `annotations:` block containing any key except `admin_owner_user_id` (e.g. `annotations: {team: growth}`), and no email/Slack recipients matching the test caller.
2. Issue a runtime JWT whose resolved user attributes contain an empty `id` (empty-subject token) and which is not an admin, then call `GetResource` for the alert (e.g. `GET /v1/instances/<id>/resource?name.kind=rill.runtime.v1.Alert&name.name=test`).
3. Expected: access denied (caller is not owner, recipient, or admin). Actual (bug): the owner check passes (`"" == ""`) and the alert spec, including notifier recipient emails, is returned.
Note: step 2 requires crafting an empty-subject token, which is not achievable through the standard Rill Cloud UI; if that is impractical, confirm in code: `runtime/security.go:451` and `:527` (no `userID != ""` guard) versus `:610` (canvas guard present).

### runtime-core-05 [LOW] Security resolution cache key omits the resource kind
- **Category:** correctness  **Confidence:** medium  **Location:** `runtime/security.go:874-901` (`computeCacheKey`)
- **Problem:** The cache key hashes `instanceID`, `environment`, `r.Meta.Name.Name`, `r.Meta.StateUpdatedOn`, and the claims JSON — but not `r.Meta.Name.Kind`. `resolveRules` branches heavily on kind, so two resources of different kinds with the same name produce genuinely different policies that can in principle collide on one key.
- **Failure scenario:** A metrics view and an explore (or canvas) sharing a name would collide only if their `StateUpdatedOn` timestamps are identical *to the nanosecond* and the claims are identical. Because `StateUpdatedOn` is a per-resource wall-clock timestamp bumped via `timestamppb.Now()` on each state update (`catalog_cache.go:377`), such a collision is effectively unreachable in practice. This is a latent-correctness / defense-in-depth gap with a trivial fix, not an exploitable bug.
- **Recommendation:** Add `r.Meta.Name.Kind` to the hash. One-line change that removes the ambiguity entirely.

**Verification:** PLAUSIBLE — `runtime/security.go:874-901` (`computeCacheKey`) hashes `instanceID`, `environment`, `r.Meta.Name.Name` (`:884`), `r.Meta.StateUpdatedOn` (`:888`), and the claims JSON; `r.Meta.Name.Kind` is indeed absent, and `resolveRules` branches on kind (`:348`). Rated PLAUSIBLE (latent) because a collision additionally requires two same-named, different-kind resources with nanosecond-identical `StateUpdatedOn` timestamps, which is effectively unreachable since each resource's timestamp is set independently via wall-clock on state updates.

**Manual Reproduction Steps (for QA):**
Not user-reproducible — the collision requires two resources of different kinds with the same name and bit-identical `StateUpdatedOn` nanosecond timestamps. Confirm in code: `runtime/security.go:874-901` (only `Name.Name` at `:884`, no write of `Name.Kind`) together with `resolveRules` kind-branching at `:348`.

### runtime-core-06 [LOW] `markPending` clears the ancestor's error instead of each descendent's
- **Category:** correctness  **Confidence:** high  **Location:** `runtime/controller.go:1166`
- **Problem:** Inside the DAG visit that marks descendents pending, the IDLE branch calls `c.catalog.updateErrorAndWarning(n, nil, nil)` — passing `n` (the ancestor being processed, already cleared at `:1124`) rather than the visited descendent `dn`. The adjacent `updateStatus(dn, ...)` correctly uses `dn`, and `updateStatus` does not clear the error (`catalog_cache.go:404-419`), so descendents' stale reconcile errors are never cleared when they are marked pending — contradicting the function's own docstring intent (`:1099`).
- **Failure scenario:** Resource A is edited to fix an error that also broke downstream B. `markPending(A)` marks B pending but leaves B's old error string in place; the UI shows B as still-errored (Pending) until B finishes re-reconciling — defeating the stated intent of the clear. No data loss, but a real UX regression.
- **Recommendation:** Change the call to `c.catalog.updateErrorAndWarning(dn, nil, nil)`.

**Verification:** CONFIRMED — `runtime/controller.go:1166`: inside the DAG `Visit` callback (iterating descendents `dn`), the IDLE branch calls `c.catalog.updateErrorAndWarning(n, nil, nil)` with the ancestor `n` (whose error was already cleared at `:1124`), while the adjacent `updateStatus` at `:1170` correctly uses `dn`. This contradicts the docstring at `:1099` ("clears errors on every resource marked pending").

**Manual Reproduction Steps (for QA):**
1. In Rill Developer, create model `a.sql` and a downstream model `b.sql` that selects from `a` and is deliberately slow to build (e.g. a large cross join), so its Pending window is observable.
2. Break `a.sql` (invalid SQL) and save; wait until both `a` and `b` show errors (`b` errors due to the failed upstream).
3. Fix `a.sql` and save. Immediately inspect `b` in the UI resource status (or via `GET /v1/instances/<id>/resource` for model `b`).
4. Expected: while `b` is Pending, its old reconcile error is cleared. Actual (bug): `b` shows status Pending but still carries the stale error string until its own reconcile finishes.

**Verification:** CONFIRMED — `runtime/connections.go:73-77`: on the `!ok` branch, `Repo()` calls `release()` and then `return nil, release, fmt.Errorf(...)`, handing back the already-invoked release func. Conncache release decrements a refcount and is not idempotent (`runtime/pkg/conncache/conncache.go`). **Manual Reproduction Steps (for QA):**

### runtime-core-08 [LOW] Hung reconcilers leak on the unbuffered `completed` channel during shutdown
- **Category:** concurrency  **Confidence:** medium  **Location:** `runtime/controller.go:325-350` (drain loop) with the send at `:1332` and the channel created unbuffered at `:148`
- **Problem:** During shutdown the drain loop waits up to 30s for in-flight invocations to finish. If a reconciler is genuinely hung past that deadline, the loop breaks out while `c.invocations` is non-empty and `Run` returns. When such a goroutine later returns, its `defer` does `c.completed <- inv` on an unbuffered channel with no remaining reader, blocking it forever and pinning whatever resources (handles, memory) it holds.
- **Failure scenario:** A reconciler stuck in an uncancellable driver call outlives the 30s grace; the controller closes but the goroutine leaks permanently. (The 10-minute `hangingTicker` treats such hangs as fatal during normal operation, so this is bounded to shutdown, but it is still an unbounded leak on a bad-driver path.)
- **Recommendation:** Give `completed` a small buffer sized to the max in-flight invocations, or make the send non-blocking / select on a shutdown-done channel so a late completion cannot block forever.

**Verification:** PLAUSIBLE — `runtime/controller.go:148`: `completed: make(chan *invocation)` is unbuffered; the reconciler goroutine's deferred send is at `:1332` (`c.completed <- inv`); the shutdown drain loop (`:325-350`) breaks out on a 30-second timeout (`:321`, `:342-349`) while `c.invocations` may still be non-empty, after which no reader remains. Rated PLAUSIBLE (latent) because the leak only occurs when a reconciler is genuinely hung past the 30s grace during controller shutdown — a bad-driver path, not normal operation.

**Manual Reproduction Steps (for QA):**
Not user-reproducible without a deliberately hung driver. Confirm in code: `runtime/controller.go:148` (unbuffered channel), `:325-350` (drain loop breaks on 30s timeout leaving invocations in flight), `:1332` (deferred send with no remaining reader after `Run` returns). A test could inject a reconciler that ignores context cancellation and sleeps longer than 30s, close the controller, and then observe the leaked goroutine parked in `chan send` at `controller.go:1332` in a goroutine dump.

### runtime-core-10 [LOW] Transitive access rules are re-expanded on every security resolution, outside the cache
- **Category:** performance  **Confidence:** medium  **Location:** `runtime/security.go:255` (with `expandTransitiveAccessRules` at `:786-819`)
- **Problem:** `resolveSecurity` calls `expandTransitiveAccessRules` — which does `controller.Get` plus `reconciler.ResolveTransitiveAccess` for each transitive rule (`security.go:801-818`) — *before* computing the cache key and *before* the cache lookup at `:283`. For claims that carry transitive access rules (magic-auth tokens with resource restrictions — `admin/server/runtime_jwt.go:265-278`), this expansion re-runs on every security resolution even when the resolved result is already cached, so the `ResolvedSecurity` cache never amortizes it. For claims without transitive rules the expansion is a cheap slice loop, so the cost is confined to magic-token principals.
- **Failure scenario:** A magic-link dashboard/API with resource-restriction rules issues many requests; each request re-runs the transitive expansion (controller Gets + per-ref transitive resolution) that the cache was meant to avoid, adding avoidable per-request work under load.
- **Recommendation:** Perform the transitive expansion inside the cached computation (include the transitive rules in the cache key and expand only on a miss), or cache the expanded rules separately keyed on the claims' transitive rules.

**Verification:** CONFIRMED — `runtime/security.go:255`: `resolveSecurity` calls `p.expandTransitiveAccessRules(ctx, instanceID, claims)` before the cache key is computed at `:275` and before the cache lookup at `:283`. The expansion (`:786-871`) does `p.rt.Controller(...)` plus `ctr.Get(...)` and `reconciler.ResolveTransitiveAccess(...)` per transitive rule (`:801-818`), so for magic-auth claims carrying transitive rules this work re-runs on every security resolution even when the resolved result is a cache hit. For claims without transitive rules it is a cheap slice loop, confirming the cost is confined to magic-token principals.

**Manual Reproduction Steps (for QA):**
Not user-reproducible as a functional bug — it is redundant per-request work, observable only via profiling. Confirm in code: `runtime/security.go:255` (expansion call) precedes `:283` (cache `Get`). To observe empirically: load-test a magic-auth share link that carries resource-restriction (transitive access) rules with repeated identical requests, and CPU-profile the runtime; `expandTransitiveAccessRules` / `ResolveTransitiveAccess` appear on every request despite the `ResolvedSecurity` cache hitting.

## Product Improvements

- **runtime-core-09 [product-improvement] Health check does O(#metrics_views) per-probe work, with live time-range queries for uncached metrics views.** In `runtime/health.go:162-203`, for every metrics view `InstanceHealth` acquires OLAP, checks `MayBeScaledToZero`, and resolves `metrics_time_range`. The health-specific cache is reused only when `MayBeScaledToZero` is true. The underlying `metrics_time_range` resolve is itself cached via the resolver query cache for cacheable metrics views (non-streaming Rill-managed MVs cache by default), so those are largely cache hits; but metrics views with caching disabled or streaming MVs (short-TTL cache key) run a live query on each probe, and every MV incurs nested resolve/security overhead regardless. For always-on OLAPs (e.g. ClickHouse/Druid) with many such metrics views this makes each health call expensive. Consider a short TTL cache regardless of scale-to-zero, or probing a bounded sample, so health endpoints stay cheap on large projects.

## New Feature Ideas

- **Cache-key correctness lint / assertion harness (S–M).** A test helper that, for every registered resolver and legacy query, asserts that varying each security dimension (`UserAttributes`, `AdditionalRules`, `Permissions`) changes the cache key. Would have caught finding 01 and guards against regressions as new resolvers are added. High value for a low cost.
- **Per-instance security-engine cache + sharded lock (M).** Replace the single global `securityEngine` mutex/LRU with per-instance shards (keyed by instanceID) and hold the lock only around `Get`/`Add`. Removes the cross-tenant contention behind finding 03 and bounds one noisy project's policy churn from evicting another's cached policies.
- **Structured reconcile-error surface with "cleared" semantics (M).** Formalize pending-state error handling (finding 06) so the UI can distinguish "stale error, re-checking" from "current error", including a resource-level timestamp of when the error was last confirmed. Improves the debugging experience during cascading re-reconciles.
- **Graceful-delete status for instances (M).** Make `DeleteInstance` return a typed status (deleted / retrying / failed) and drive teardown to completion asynchronously with retries, instead of a single blocking `<-completed`. Fixes finding 02's failure mode and gives the admin service observability into stuck deletions.
- **Connection-cache key introspection endpoint (S).** Expose `generateKey`-derived keys and refcounts (debug-only) so operators can diagnose connection churn/eviction and double-release bugs like finding 07 in production.

## Notes & Missing Test Coverage

- No test exercises the resolver query cache across two claims that differ only in `AdditionalRules` (finding 01). This is the single most important missing test; it should assert distinct cache keys and distinct row-filtered results through the `metrics` resolver.
- `runtime/controller_test.go` covers scheduling/rename/delete flows well, but there is no test asserting that descendents' errors are cleared on `markPending` (finding 06) — add one that errors a downstream resource, edits the upstream, and asserts the downstream error is cleared while Pending.
