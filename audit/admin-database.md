# Admin Database Layer — Code Review

**Scope:** `admin/database/database.go`, `admin/database/errors.go`, `admin/database/validate.go`, `admin/database/postgres/` (`postgres.go`, `tx.go`, `migrate.go`, `migrations/*.sql`, tests)  |  **Health:** fair

## Overview

This is the admin (Rill Cloud) control-plane persistence layer: a large `DB` interface (~230 methods) with a single Postgres implementation built on `sqlx` + `pgx/v4`. The code is uniform and readable: nearly every method threads the request context through `getDB(ctx)` (which transparently uses a transaction if one is stored in the context), builds parameterized SQL (no string interpolation of user values — SQL injection risk is low), and maps errors through a shared `parseErr` helper that translates `sql.ErrNoRows` and Postgres unique-violation codes into typed `database` errors. Column-level AES-GCM encryption for secrets/variables is implemented correctly (random nonce per encryption, length checks on decrypt).

The biggest risks are localized rather than systemic: four billing read methods silently bypass the transaction context by calling `c.db` directly; one membership insert path discards its validated/normalized input; and the migration runner takes a session-level advisory lock over a connection pool without pinning a connection. There is also a scattering of robustness gaps (panics in the persistence layer, an unguarded dynamic INSERT, dead/partially-implemented code, and a few unpaginated list queries). Test coverage exists via testcontainers but is concentrated on orgs/projects/pagination/attributes and misses the transactional and concurrency edge cases flagged below.

## Findings

### admin-database-01 [MEDIUM] Four billing read methods bypass the transaction context
- **Category:** correctness  **Confidence:** high  **Location:** `admin/database/postgres/postgres.go:3082,3096,3105,3119`
- **Problem:** Every method in this file reads/writes through `c.getDB(ctx)`, which returns the active transaction when one is stored in the context (see `tx.go:getDB`). But `FindBillingIssuesForOrg`, `FindBillingIssueByTypeForOrg`, `FindBillingIssueByType`, and `FindBillingIssueByTypeAndOverdueProcessed` call `c.db.SelectContext`/`c.db.GetContext` directly, hitting the connection pool and ignoring any transaction in `ctx`.
- **Failure scenario:** A caller opens a transaction with `NewTx(ctx, ...)`, calls `UpsertBillingIssue` (which correctly writes through the tx), then calls `FindBillingIssueByTypeForOrg(txCtx, ...)` expecting to read back what it just wrote. Because the read runs on a different pooled connection outside the transaction, it returns stale/committed data (or `ErrNotFound`), producing inconsistent billing-issue state. **Verified latent, not active:** every current transaction block that touches billing issues — `credit_balance_event_handlers.go:141`, `trial_checks.go:147`, `admin/server/billing.go:832` — only *writes* inside the tx (`UpsertBillingIssue`/`DeleteBillingIssue`, which correctly use `getDB`) and performs its `FindBillingIssue*` reads *before* opening the tx. So no caller reads a billing issue inside a transaction today, but it is a footgun that will silently misbehave the first time someone does. (Category corrected from `concurrency`: this is a transaction-isolation/read-consistency issue, not a data race.)
- **Recommendation:** Replace `c.db` with `c.getDB(ctx)` in all four methods so they honor the transaction context like every other method.

**Verification:** PLAUSIBLE — the bypass is real in current code: `FindBillingIssuesForOrg` uses `c.db.SelectContext` at `admin/database/postgres/postgres.go:3082`, `FindBillingIssueByTypeForOrg` uses `c.db.GetContext` at 3096, `FindBillingIssueByType` at 3105, and `FindBillingIssueByTypeAndOverdueProcessed` at 3119, while every neighboring method (e.g. `FindOrganizationForBillingCustomerID` at 3072) goes through `c.getDB(ctx)`. However, no current caller reads a billing issue inside a transaction (the tx blocks in `admin/billing/payment/credit_balance_event_handlers.go`, `admin/worker/trial_checks.go`, and `admin/server/billing.go` only write inside the tx), so the failure is latent, not active.

**Manual Reproduction Steps (for QA):**
Not user-reproducible — no production code path currently reads a billing issue inside an open transaction, so no user-visible misbehavior occurs today. Confirm in code: `admin/database/postgres/postgres.go:3080-3131`, note the four `c.db.SelectContext`/`c.db.GetContext` calls versus `c.getDB(ctx)` used everywhere else; and `admin/database/postgres/tx.go` (`getDB`) for how the transaction is extracted from `ctx`. Alternatively, an engineer can write a Go test that opens `NewTx`, calls `UpsertBillingIssue` in the tx, then calls `FindBillingIssueByTypeForOrg` with the tx context — it will return `ErrNotFound` instead of the just-written row.

### admin-database-02 [LOW] `InsertOrganizationMemberUser` discards validated attributes in the `ifNotExists` branch
- **Category:** correctness  **Confidence:** medium  **Location:** `admin/database/postgres/postgres.go:2124` (function `2099`–`2136`)
- **Problem:** The method computes `attrs, err := c.validateAttributes(attributes)`, which normalizes a `nil` map to a non-nil `{}` (see `validateAttributes`, `postgres.go:4096-4099`). The `!ifNotExists` branch correctly inserts `attrs` (line 2106), but the `ON CONFLICT ... DO NOTHING` (`ifNotExists`) branch inserts the raw, un-normalized `attributes` parameter instead (line 2124). Note the two are identical for any non-nil input (`validateAttributes` returns the same map reference); the branches only diverge when `attributes == nil`, giving `{}` vs. `nil`.
- **Failure scenario:** The guest-membership flow reaches this branch with `attributes == nil` (`admin/user.go`, guest-role path), so the two branches persist different values for the same logical operation. **Severity downgraded from medium — the "at worst the INSERT fails" claim is refuted:** the arg is a typed-nil `map[string]any` (a non-nil interface), so pgx routes it through `pgtype.JSON.Set`, whose `src == nil` check is false and which falls to the default `json.Marshal(nil-map)` → `"null"` with `Status: Present`. That stores JSONB `null` (not SQL `NULL`), which satisfies the `NOT NULL` column and is normalized back to `{}` on read. The realistic effect is therefore benign — a stored `null` instead of `{}` — but the validated value is still silently thrown away, and the two branches should not diverge.
- **Recommendation:** Use `attrs` (the validated/normalized value) in both branches.

**Verification:** CONFIRMED — at `admin/database/postgres/postgres.go:2099-2136`, the `!ifNotExists` branch inserts `attrs` (line 2106) while the `ON CONFLICT ... DO NOTHING` branch inserts the raw `attributes` parameter (line 2124). The divergent branch is exercised in production: `admin/user.go:64` calls `InsertOrganizationMemberUser(..., attributes, true)` from `InsertProjectMemberUser`, and callers of that path can pass `nil` attributes. The effect is benign (JSONB `null` stored instead of `{}`, normalized back to `{}` on read), which is why severity is LOW.

**Manual Reproduction Steps (for QA):**
The user-visible effect is nil (values are normalized on read), so this is effectively not user-reproducible through the UI. To observe the stored difference, database access is needed:
1. In Rill Cloud, invite a user directly to a *project* (not the org) — e.g. via the project's Members/Share UI or `rill project share` — for a user who is not yet an org member. This triggers the guest-membership path with nil attributes.
2. Separately, add another user as a direct *org* member (org Members UI or `rill user add`).
3. Ask an engineer to run `SELECT user_id, attributes FROM users_orgs_roles WHERE org_id = '<org>'` against the admin Postgres database: the project-invited guest's row shows JSONB `null` while the direct org member's row shows `{}`.
If DB access is unavailable: confirm in code at `admin/database/postgres/postgres.go:2106` vs. `2124` (`attrs` vs. `attributes`).

### admin-database-03 [MEDIUM] `Migrate` holds a session-level advisory lock across a connection pool
- **Category:** concurrency  **Confidence:** medium  **Location:** `admin/database/postgres/migrate.go:40-50`
- **Problem:** `Migrate` acquires `pg_advisory_lock($1)` via `c.db.ExecContext` and releases it with `pg_advisory_unlock($1)` via `c.db.ExecContext` in a deferred call. `c.db` is a `*sqlx.DB` pool, and session-level advisory locks are bound to the specific backend connection that acquired them. The lock, the version checks, the per-migration transactions (`migrateSingle` opens its own `BeginTx`), and the unlock can each run on different pooled connections. No `SetMaxOpenConns(1)` is configured (`admin/admin.go` opens the DB without pool limits), so nothing forces a single connection.
- **Failure scenario:** In the common sequential path, `database/sql` reuses the most-recently-used idle connection, so lock and unlock land on the same backend and it works. But if any other query touches the pool during migration, or the connection is recycled (idle/lifetime timeout) mid-run, the deferred `pg_advisory_unlock` executes on a backend that does not hold the lock — it returns `false` and the original lock leaks until that connection is physically closed, blocking all subsequent migrations that wait on `pg_advisory_lock`.
- **Recommendation:** Pin a single connection for the whole migration (`conn, _ := c.db.Conn(ctx)`; run lock, checks, migrations, and unlock on `conn`), or use `pg_advisory_xact_lock` inside a transaction so the lock auto-releases. This is what the referenced `tern` implementation does (it runs on one dedicated connection).

**Verification:** PLAUSIBLE — `admin/database/postgres/migrate.go:38-50` acquires `pg_advisory_lock` and releases `pg_advisory_unlock` via `c.db.ExecContext` (the shared `*sqlx.DB` pool), and `migrateSingle` opens separate transactions; grep confirms no `SetMaxOpenConns`/connection pinning anywhere in `admin/`. Session-level advisory locks are connection-bound, so the described leak is real but requires a pooled-connection swap (concurrent query or connection recycling) during a migration run — timing-dependent, hence latent rather than deterministically reproducible.

**Manual Reproduction Steps (for QA):**
Not reliably user-reproducible — the failure depends on connection-pool timing during service startup migrations. Best-effort check for an engineer:
1. Start the admin service (`rill devtool start cloud`) against a Postgres with pending migrations while another process holds open queries on the same DB, or set aggressive `idle_in_transaction`/connection-lifetime limits.
2. After migration completes, run `SELECT * FROM pg_locks WHERE locktype = 'advisory' AND objid IS NOT NULL;` in Postgres — a leftover row for lock key 5103805673824918 indicates a leaked lock; a subsequent admin start will then hang on `pg_advisory_lock`.
How to confirm in code: `admin/database/postgres/migrate.go:38-50` — lock and unlock both run on `c.db` (pool), not a pinned `*sql.Conn`.

### admin-database-04 [LOW] `FindDeploymentsToStop` can hibernate dev deployments using the prod TTL
- **Category:** correctness  **Confidence:** medium  **Location:** `admin/database/postgres/postgres.go:647-660`
- **Problem:** The predicate is `(prod_ttl_seconds IS NOT NULL AND used_on + prod_ttl < now()) OR (environment = 'dev' AND used_on + dev_ttl < now())`. The first clause has no environment filter, so it applies to dev deployments too, not just production ones.
- **Failure scenario:** A project configured with `dev_ttl_seconds` longer than `prod_ttl_seconds` (an unusual but permitted configuration) will have its dev deployments hibernated as soon as the shorter prod TTL elapses, ignoring the intended, longer dev TTL. Conversely the intent (prod uses prod TTL, dev uses dev TTL) is only satisfied when `dev_ttl <= prod_ttl`.
- **Recommendation:** Scope the first clause to non-dev deployments, e.g. `(d.environment != 'dev' AND prod_ttl_seconds IS NOT NULL AND ...)`, so each environment respects only its own TTL.

**Verification:** PLAUSIBLE — confirmed at `admin/database/postgres/postgres.go:647-660`: the query's first clause `(p.prod_ttl_seconds IS NOT NULL AND d.used_on + p.prod_ttl_seconds * interval '1 second' < now())` has no `d.environment` filter, so dev deployments are matched by the prod TTL too. Misbehavior only manifests with the unusual configuration `dev_ttl_seconds > prod_ttl_seconds`, both of which are settable via `rill project edit --prod-ttl-seconds/--dev-ttl-seconds` (`cli/cmd/project/edit.go:62-69,116-117`).

**Manual Reproduction Steps (for QA):**
1. On a Rill Cloud project, run `rill project edit <project> --prod-ttl-seconds 300 --dev-ttl-seconds 86400` (prod TTL 5 minutes, dev TTL 24 hours).
2. Start a dev deployment for the project (e.g. open the project in dev mode / Rill's cloud dev environment) and then leave it idle.
3. Wait a bit over 5 minutes without using the deployment, letting the hibernation background job run (`rill sudo project get <project>` can show TTLs; deployment status is visible via `rill project status`).
4. Observe the dev deployment gets stopped/hibernated after ~5 minutes (the prod TTL) instead of surviving up to the configured 24-hour dev TTL.

### admin-database-05 [LOW] `UpsertProjectVariable` builds an unguarded dynamic INSERT
- **Category:** correctness  **Confidence:** high  **Location:** `admin/database/postgres/postgres.go:3214-3250`
- **Problem:** The method concatenates one `VALUES (...)` tuple per entry in `vars` into a single multi-row `INSERT ... ON CONFLICT (project_id, environment, lower(name)) DO UPDATE`. It has two edge-case defects: (1) if `vars` is empty the query becomes `INSERT ... VALUES  ON CONFLICT ...`, a syntax error (the sibling `DeleteProjectVariables` explicitly guards `len(names) == 0`, but this method does not); (2) if `vars` contains two keys differing only in case (e.g. `FOO` and `foo`), the two generated rows both conflict on the case-insensitive unique index within one statement, which Postgres rejects with "ON CONFLICT DO UPDATE command cannot affect row a second time."
- **Failure scenario:** The current sole caller guards `len(vars) > 0` (`admin/projects.go:273`), so empty input is not hit today, but the exported DB method is unsafe for any future caller; case-colliding variable names fail hard rather than being coalesced.
- **Recommendation:** Return early (or error) when `len(vars) == 0`, and de-duplicate keys by lowercased name before building the statement (mirroring the `lower(name)` conflict target).

**Verification:** CONFIRMED — `UpsertProjectVariable` (`admin/database/postgres/postgres.go:3213-3262`) builds one `VALUES` tuple per map entry with no empty-map guard and no lowercase de-duplication, while the conflict target is `(project_id, environment, lower(name))`. The sibling `DeleteProjectVariables` (line 3264) does guard `len(names) == 0`. The sole caller guards emptiness (`admin/projects.go:273`, `if len(vars) > 0`), so the empty-input half is latent, but the case-collision half is user-reachable via `rill env push` (a `.env` file may legally contain both `FOO` and `foo`).

**Manual Reproduction Steps (for QA):**
1. In a Rill project deployed to Rill Cloud, create/edit the local `.env` file to contain two variables differing only in case, e.g. `foo=1` and `FOO=2`.
2. Run `rill env push` for the project.
3. Observe the command fails with a Postgres error like "ON CONFLICT DO UPDATE command cannot affect row a second time" instead of a clear validation message (or the last-written value winning).
(Empty-`vars` half: not user-reproducible today because `admin/projects.go:273` guards `len(vars) > 0`; confirm in code at `admin/database/postgres/postgres.go:3228-3247` — no `len(vars) == 0` guard.)

### admin-database-06 [LOW] Persistence-layer panics can crash the admin service
- **Category:** tech-debt  **Confidence:** high  **Location:** `admin/database/postgres/postgres.go:3969-3971,3987-3989,2132-2134,2166-2168,1048-1051`
- **Problem:** `checkUpdateRow`/`checkDeleteRow` panic when `RowsAffected() > 1`, `InsertOrganizationMemberUser`/`UpdateOrganizationMemberUserAttributes` panic when more than one row is affected, and `InsertManagedUsergroups` panics when it does not insert exactly 3 rows. These are "should never happen" invariants, but they are enforced with `panic` inside a shared library used by every admin request handler and background job.
- **Failure scenario:** A future schema change, a missing/duplicated unique constraint, or an unexpected data state turns a recoverable data anomaly into a process-wide crash (or a panicking goroutine) in the cloud control plane, rather than a returned error that the caller can log and surface.
- **Recommendation:** Return a descriptive error instead of panicking for data-dependent conditions; reserve `panic` for genuine programmer errors that cannot depend on database contents.

**Verification:** CONFIRMED — all five panic sites exist in current code: `checkUpdateRow` panics on `n > 1` (`admin/database/postgres/postgres.go:3971`), `checkDeleteRow` likewise (line 3988), `InsertOrganizationMemberUser` panics on `rows > 1` (line 2133), `UpdateOrganizationMemberUserAttributes` panics on `rows > 1` (line 2167), and `InsertManagedUsergroups` panics on `rows != 3` (line 1050). These conditions depend on database state (unique constraints holding), not purely on programmer error.

**Manual Reproduction Steps (for QA):**
Not user-reproducible — the panics only fire if a unique constraint is missing or violated (e.g. after a faulty schema migration), which cannot be induced through the product. Confirm in code: `admin/database/postgres/postgres.go` — search for `panic(fmt.Errorf("expected to update` and `panic(fmt.Sprintf("expected 3 rows` (lines 3971, 3988, 2133, 2167, 1050). An engineer can demonstrate by dropping the `users_orgs_roles` unique index in a test database and updating a member's role for a user with two membership rows: the admin request crashes with a panic instead of returning an error.

### admin-database-09 [LOW] Inconsistent error mapping and fragile migration-version detection
- **Category:** readability  **Confidence:** high  **Location:** `admin/database/postgres/postgres.go:3280` (`DeleteProjectVariables`), `admin/database/postgres/migrate.go:28` (`FindMigrationVersion`)
- **Problem:** `DeleteProjectVariables` returns the raw driver error (`return err`) instead of routing through `parseErr` like every other method, so its errors are not normalized to the `database` error types callers switch on. Separately, `FindMigrationVersion` detects a missing version table with `strings.Contains(err.Error(), "does not exist")`, matching a driver-specific, locale-sensitive substring rather than the Postgres error code (`42P01`, `undefined_table`).
- **Failure scenario:** Callers of `DeleteProjectVariables` cannot reliably `errors.Is(...)`-classify failures; and a driver/version/locale change to the error text would make `FindMigrationVersion` surface a raw error instead of returning version `0`, breaking first-run bootstrap.
- **Recommendation:** Wrap the delete error with `parseErr`, and detect the missing table via the `pgconn.PgError` code (`42P01`) instead of substring matching.

**Verification:** CONFIRMED — `DeleteProjectVariables` ends with `return err` on the raw `ExecContext` error (`admin/database/postgres/postgres.go:3283-3284`), unlike sibling methods that wrap with `parseErr`; and `FindMigrationVersion` detects the missing version table via `strings.Contains(err.Error(), "does not exist")` (`admin/database/postgres/migrate.go:28`). The latter is exercised on every fresh bootstrap (`FindMigrationVersion` is called from `admin/admin.go` before migrations create the table), so the fragile match genuinely guards first-run.

**Manual Reproduction Steps (for QA):**
Not user-reproducible under normal conditions — both issues only surface when errors occur (a failed variable delete surfaces an unnormalized driver error; a pgx error-text change would break first-run bootstrap). Confirm in code: `admin/database/postgres/postgres.go:3283-3284` (`return err` without `parseErr`) and `admin/database/postgres/migrate.go:26-31` (substring match on "does not exist" instead of Postgres error code `42P01`). Sanity check that the happy path works: point a fresh (empty) Postgres at the admin service and start it — bootstrap succeeds only because the substring currently matches pgx's error text.

## Product Improvements

- **Expose pending project access requests (from admin-database-07).** The DB already stores access requests and `FindProjectAccessRequests` exists but is unused and incomplete. Completing it and wiring a listing endpoint would let project admins see and act on pending requests instead of only handling them one-by-one by ID.
- **Clearer attribute-limit feedback.** `validateAttributes` (`postgres.go:4096`) hard-codes limits (≤50 keys, ≤256-char string values, alphanumeric/underscore keys) and returns ad-hoc `fmt.Errorf` errors that are not the typed `ErrValidation`. Surfacing these as structured validation errors (like `database.Validate`) would give API consumers consistent, actionable messages.

## New Feature Ideas

- **Connection-pinned migration runner (S).** Refactor `Migrate` to run on a single dedicated `*sql.Conn` (or use `pg_advisory_xact_lock`), eliminating the pooled-advisory-lock hazard in admin-database-03 and making concurrent-deploy migrations provably safe.
- **A `WithTx(ctx, fn)` helper that forbids raw `c.db` (M).** Provide a single transaction-scoping helper and a small lint/test that asserts implementation methods never touch `c.db` directly. This structurally prevents the entire class of "bypasses the transaction" bugs (admin-database-01).
- **Down-migrations / migration test harness (M).** There are 95 forward-only migrations and no rollback path or automated per-migration up/down test. A lightweight harness that applies each migration against a testcontainer and checks reversibility would catch schema regressions before deploy.
- **Bulk membership operations (M).** Adding N users/usergroups to an org or project currently issues one round-trip per member. Batch insert/update methods (multi-row INSERTs with `ON CONFLICT`) would cut latency for invite acceptance and bulk imports.
- **Slow-query / query-count observability (S).** `otelsql` already instruments the driver; adding per-method query counting and slow-query logging (especially for the correlated-subquery member listings) would make N+1 and hot-path regressions visible in the control plane.
- **Soft-delete + audit trail for orgs/projects/members (L).** Deletes are hard `DELETE`s relying on FK cascades. A soft-delete/audit-log layer would enable recovery of accidentally deleted projects (the code already special-cases this with the 7-day asset/git-repo retention windows) and give a compliance trail for membership changes.

## Notes & Missing Test Coverage

- **Untested transactional/concurrency paths.** `TestPostgres` (testcontainers) covers orgs, projects, pagination, members, attributes, and project variables, but there is no test that (a) reads a billing issue inside a transaction (would expose admin-database-01), (b) exercises `InsertOrganizationMemberUser` with `ifNotExists=true` and `nil` attributes (admin-database-02), or (c) runs `Migrate` concurrently (admin-database-03). These are the highest-value gaps to close.
- **`pgx` nil-map encoding for admin-database-02 (resolved by tracing).** A typed-nil `map[string]any` is a non-nil interface, so pgx's `pgtype.JSON.Set` skips its `src == nil` branch and `json.Marshal`s the nil map to `"null"` with `Status: Present` — i.e. JSONB `null`, which satisfies the `NOT NULL` column and is normalized to `{}` on read. The outcome is benign (hence the severity downgrade), and the fix (use `attrs`) is still correct. A test would still be worthwhile to pin the behavior.
- **Secret exposure to verify at the server layer (out of DB scope).** `magicAuthTokenWithUserFromDTO` (`postgres.go:3570`) and thus `FindMagicAuthTokensWithUser`/`FindMagicAuthTokenWithUser` always decrypt and return the token `Secret`, unlike `FindMagicAuthToken(withSecret=false)` which nils it out. This is likely intentional (to render magic-link URLs), but it is worth confirming that the server does not serialize these `Secret` bytes to unauthorized clients when listing tokens.
- **Minor doc bug.** The comment on `encrypt` (`postgres.go:4048`) says it "returns the base64 encoded ciphertext," but it returns raw bytes; base64 is applied by the caller only for project variables (`UpsertProjectVariable`), not for magic-token secrets. Harmless but misleading.
- **Redundant `lower(...) ILIKE`.** `FindOrganizationMemberUsers`/`CountOrganizationMemberUsers` use `lower(u.email) ILIKE $n` (confirmed at `postgres.go:2029`); `ILIKE` is already case-insensitive, so the `lower()` wrapper is redundant (and could defeat a case-sensitive index if one were added). Cosmetic. The dynamic `not`/`ILIKE` construction here uses only constant fragments plus positional `$n` placeholders, so there is no injection risk.
